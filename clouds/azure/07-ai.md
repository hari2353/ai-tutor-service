## The 30-second version

Microsoft's GenAI platform has rebranded twice in two years — **Azure AI Studio** (Nov 2023) → **Azure AI Foundry** (Nov 2024) → **Microsoft Foundry** (Nov 2025) — and the current name matters less than the underlying shape, which has stayed consistent: **Azure OpenAI** (now formally "Azure OpenAI in Microsoft Foundry Models") gives you OpenAI's frontier models behind Azure's enterprise perimeter (VNet integration, Entra ID auth, regional data residency, content filtering), billed either **pay-as-you-go** (per-token, quota-gated by **TPM/RPM** — tokens-per-minute and requests-per-minute, with RPM auto-set at roughly **6 RPM per 1,000 TPM**) or **Provisioned Throughput Units (PTU)** — a fixed hourly reservation (**~$1/PTU-hour, ~$260/month reserved** for GPT-4o-class models) that guarantees dedicated capacity regardless of token volume, with a break-even against pay-as-you-go typically landing around **150-200M tokens/month**. **Foundry Agent Service** (GA June 2025) is Microsoft's managed agent runtime — deep-integrated with Microsoft 365/Teams (a genuine differentiator no competitor matches) and, notably, the fact that **GPT-5 and OpenAI's frontier lineup are available as first-party models only through Azure AI Foundry or directly via OpenAI's own API** — not through Bedrock or Vertex. **AI Search** (formerly Cognitive Search) is Azure's managed retrieval layer: hybrid search combining BM25 keyword scoring, vector similarity, and an optional **semantic ranker** re-ranking step, tiered Free/Basic/Standard(S1-S3)/Storage-Optimized(L1-L2) with vector-memory quota scaling per partition (roughly **35GB vector quota per partition on post-April-2024 S1 services**). ## Lineage: past → present → future

**What came before.** Azure's pre-GenAI AI story was Azure Cognitive Services (2016 onward) — a grab-bag of individually-provisioned APIs (Vision, Speech, Language, Translator) with no unified model-hosting or agent-orchestration story, and separately, Azure Machine Learning / ML Studio for classical/custom model training and deployment. The pain: building an LLM-based application meant stitching together a model endpoint, a vector store, and orchestration code with no first-party managed layer connecting them, the same fragmentation problem SageMaker faced before Bedrock and Vertex AI's unified GenAI surfaces emerged. Microsoft's OpenAI partnership (announced 2019, deepened with a multi-billion-dollar investment in 2023) gave Azure privileged, first-party access to GPT-series models specifically — a structural advantage neither AWS nor GCP has an equivalent exclusive relationship for.

**Where it stands now.** The platform itself has rebranded twice: **Azure AI Studio** (GA May 2024) → **Azure AI Foundry** (Ignite Nov 2024, explicitly positioning agent development and evaluation as first-class) → **Microsoft Foundry** (Ignite Nov 2025 — dropping "Azure" specifically to signal agents are a cross-Microsoft-product concern, not just an Azure service). **Foundry Agent Service** reached GA on **June 16, 2025** after preview at Ignite 2024, and by early 2026 reported **10,000+ customers** on the platform — its differentiators are deep Microsoft 365/Teams integration (one-click Teams deployment for an agent) and first-party access to OpenAI's frontier lineup (GPT-5 and beyond) that Bedrock and Vertex don't get. [Foundry Agent Service GA — Microsoft Community Hub](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/announcing-general-availability-of-azure-ai-foundry-agent-service/4414352) — accessed 2026-08-08. The live competitive disagreement: **Bedrock AgentCore** (preview July 2025, GA **Oct 13, 2025**) is the most model/framework-agnostic of the three, built around microVM-per-session isolation tuned specifically for long-running (~8 hour) agentic sessions, with episodic memory available at GA — while Foundry's own native agent memory only reached **public preview in Q1 2026**, a real capability gap as of this writing. **Vertex AI Agent Builder** originated the **Agent-to-Agent (A2A) protocol** and shipped the first managed multi-agent runtime built around it, with its Agent Development Kit (ADK) reporting **7 million downloads by Q1 2026** and the deepest low-code agent-authoring tooling of the three. [Bedrock AgentCore vs Azure vs Vertex Q2 2026 — AgentMarketCap](https://agentmarketcap.ai/blog/2026/04/09/aws-bedrock-agentcore-vs-azure-ai-agent-service-vs-google-vertex-ai-agents-q2-2026) — accessed 2026-08-08.

**Where it's heading.** Microsoft's stated direction is embedding agents as first-class citizens across the entire Microsoft 365/Copilot surface rather than treating them as an isolated Azure product line — high confidence given the deliberate "drop Azure from the name" rebrand. AgentCore's memory and isolation model advantages are likely to narrow as Foundry's memory feature matures out of preview, but the timeline is genuinely uncertain — worth a fresh check near interview time given how fast this specific three-way race is moving. AI Search's trajectory points toward deeper native integration with Foundry's agent and RAG tooling (reducing the "stitch together AI Search plus Foundry plus your own orchestration" pattern into something more unified) — moderate confidence.

## How it actually works

### Azure OpenAI — quota mechanics and PTU economics

Azure OpenAI enforces quota **per region, per model, per subscription** — not globally. A published TPM ceiling (e.g., **240,000 TPM for GPT-4o in East US**) can be split across deployments however you like: one 240K-TPM deployment, two 120K-TPM deployments, or spread across multiple Azure OpenAI resources in that region as long as the sum stays under the regional ceiling. **RPM auto-scales with TPM at roughly 6 RPM per 1,000 TPM** assigned (the exact ratio varies by model), meaning a token-heavy but request-light workload (long prompts, few calls) can hit its RPM ceiling well before exhausting TPM, or vice versa for many small requests. [Azure OpenAI quotas and limits — Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/openai/quotas-limits) — accessed 2026-08-08.

**Provisioned Throughput Units (PTU)** flip the billing model entirely: instead of per-token pay-as-you-go, you reserve a fixed amount of dedicated model capacity, billed **hourly regardless of actual token consumption** — roughly **$1.00/PTU-hour (~$260/month reserved rate)** for GPT-4o-class deployments, with annual commitment discounts stacking an additional **~35% off** the monthly rate. [Azure OpenAI pricing 2026 — Redress Compliance](https://redresscompliance.com/azure-openai-enterprise-pricing-guide) — accessed 2026-08-08. The economics only favor PTU once sustained volume clears the pay-as-you-go break-even, typically cited around **150-200 million tokens/month** for GPT-4o — below that threshold, PTU is simply paying for idle capacity, the same trap as over-provisioning any reserved-capacity compute.

```python
# untested sketch — Azure OpenAI client, illustrating deployment-name-based
# routing (a real Azure-specific mechanic AWS/GCP SDKs don't have) between
# a pay-as-you-go deployment and a PTU-backed deployment for the same model
from openai import AzureOpenAI

client = AzureOpenAI(
    azure_endpoint="https://my-resource.openai.azure.com/",
    api_version="2026-03-01-preview",
    azure_ad_token_provider=token_provider,  # managed identity, not a static key
)

# "deployment" here is an Azure-specific concept -- the model + its assigned
# TPM/PTU capacity, NOT the raw model name the way OpenAI's own API takes it
response = client.chat.completions.create(
    model="gpt4o-ptu-prod",  # routes to a PTU-backed deployment
    messages=[{"role": "user", "content": "..."}],
)
```

### Foundry Agent Service

The managed agent runtime layer: tool/function calling, code interpreter, file search (backed by AI Search under the hood), and native orchestration for multi-step agent workflows, with first-class **thread/run** primitives similar in shape to OpenAI's own Assistants API but Azure-hosted with VNet integration and Entra ID-based auth. The standout differentiators versus Bedrock and Vertex: **one-click deployment into Microsoft Teams** as a bot/agent surface, and being one of only two places (the other being OpenAI's own API directly) where **GPT-5 and OpenAI's frontier model lineup are available as first-party models** — Bedrock and Vertex do not get first-party GPT-5 access. Native agent **memory** (persisting extracted facts and resolving conflicts across sessions automatically) reached **public preview in Q1 2026** — behind Bedrock AgentCore, which shipped episodic memory at its October 2025 GA.

### AI Search — hybrid retrieval and tiers

**Hybrid search** combines three signals in one query: BM25 keyword scoring, dense vector similarity, and an optional **semantic ranker** (a re-ranking step using a cross-encoder-style model) applied to the fused BM25+vector result set — this is the same "cascade" pattern discussed generically in the RAG track's reranking module, offered here as a managed, tier-gated feature. Semantic ranking is **not available on the Free tier** (compute cost) and uses an internal **queuing system** for concurrent requests — when the queue fills, further requests are rejected outright rather than degrading gracefully, a real capacity-planning consideration for high-QPS RAG applications.

Tiers: **Free** (shared, dev/testing only) → **Basic** (~$0.10/hour) → **Standard S1/S2/S3** (increasing compute/storage, up to **~$1.39/hour** for S3) → **Storage Optimized L1/L2** (for very large indexes prioritizing storage over query throughput). **Vector index size is a memory quota, not a disk quota** — HNSW-indexed vector fields must reside fully in memory during query execution (exhaustive KNN fields load into memory dynamically in pages instead, so they don't consume the same vector quota), and quota scales **per partition**: a post-April-2024 S1 service scaled to 6 partitions gets roughly **35GB × 6 = 210GB** total vector quota. [Vector index size and limits — Microsoft Learn](https://learn.microsoft.com/en-us/azure/search/vector-search-index-size) — accessed 2026-08-08.

```python
# untested sketch — AI Search hybrid query combining BM25 + vector + semantic ranking
from azure.search.documents import SearchClient
from azure.search.documents.models import VectorizedQuery

results = search_client.search(
    search_text="contract termination clauses",     # BM25 keyword signal
    vector_queries=[VectorizedQuery(
        vector=query_embedding, k_nearest_neighbors=50, fields="content_vector"
    )],                                               # dense vector signal
    query_type="semantic",                            # enables semantic re-ranking
    semantic_configuration_name="default",
    top=10,
)
```

## Build it from scratch

Minimal end-to-end shape: a Foundry Agent Service agent grounded on an AI Search index, matching `labs/python/07-ai/`:

```python
# untested sketch — Foundry Agent Service agent with AI Search grounding
from azure.ai.projects import AIProjectClient
from azure.ai.agents.models import AzureAISearchTool
from azure.identity import DefaultAzureCredential

project = AIProjectClient(
    endpoint="https://my-foundry-project.services.ai.azure.com",
    credential=DefaultAzureCredential(),  # managed identity, no static key
)

search_tool = AzureAISearchTool(
    index_connection_id="my-ai-search-connection",
    index_name="docs-hybrid-index",
    query_type="semantic",  # exercises the hybrid + semantic ranker path
)

agent = project.agents.create_agent(
    model="gpt-5",  # first-party frontier model, Foundry-exclusive alongside OpenAI's own API
    name="docs-assistant",
    instructions="Answer only from the grounded search results; cite sources.",
    tools=search_tool.definitions,
    tool_resources=search_tool.resources,
)

thread = project.agents.create_thread()
project.agents.create_message(thread_id=thread.id, role="user", content="...")
run = project.agents.create_and_process_run(thread_id=thread.id, agent_id=agent.id)
```

## How it's done in production

A typical production GenAI stack: **Azure OpenAI** deployments split between pay-as-you-go for spiky/experimental traffic and PTU-reserved capacity for the sustained-volume production path once break-even is confirmed by actual usage data — never provisioned PTU speculatively ahead of real traffic. **AI Search** running Standard tier with semantic ranking enabled for the primary RAG index, vector quota monitored against partition count as the corpus grows, and a separate lower-tier index for less latency-sensitive exploratory/internal search. **Foundry Agent Service** hosts the customer-facing and internal-tooling agents, with Teams deployment used specifically for internal-facing agents where Microsoft 365 integration is a genuine product requirement, not a default. **Managed identity** (see `C-AZ-identity`) authenticates every service-to-service call — Azure OpenAI, AI Search, and Foundry Agent Service — with zero static API keys in production configuration.

| Symptom | Cause | Fix |
|---|---|---|
| Azure OpenAI requests fail with quota errors despite the account having "plenty" of TPM in another region | Quota is enforced per-region, per-model, per-subscription — TPM assigned in one region doesn't help a deployment in another | Check quota specifically for the region/model/deployment combination hitting the error, not account-wide totals |
| A workload with long prompts but few calls hits rate limits well before expected TPM exhaustion | RPM is auto-set proportionally to TPM (~6 RPM per 1,000 TPM) — a token-heavy, request-light pattern can exhaust RPM while TPM remains unused, or vice versa | Model the actual RPM-vs-TPM shape of the workload, not just aggregate token volume, when sizing a deployment |
| PTU-reserved capacity costs more than expected pay-as-you-go spend would have been | PTU committed ahead of confirmed sustained volume, below the ~150-200M tokens/month break-even for GPT-4o-class models | Only commit to PTU after measuring real sustained token volume against the break-even threshold; use pay-as-you-go until volume is proven |
| AI Search RAG pipeline underperforms compared to expectations for "hybrid search" | Semantic ranking wasn't enabled (unavailable on Free tier, or not configured on a paid tier that supports it) — the pipeline is running BM25+vector only, without the re-ranking step | Confirm the search tier supports semantic ranking and that `query_type=semantic` with a configured semantic configuration is actually set on the query |
| AI Search requests start getting rejected outright under high concurrent query load | Semantic ranker's internal request queue filled — it rejects rather than gracefully degrading once the queue is full | Scale up replicas/tier for higher concurrent semantic-ranking throughput, or fall back to non-semantic hybrid search under extreme load if latency/availability matters more than ranking quality |
| A team assumes GPT-5 will be available on Bedrock or Vertex the same way it is on Azure | GPT-5 and OpenAI's frontier lineup are first-party exclusive to Azure AI Foundry / Microsoft Foundry and OpenAI's own API | Plan model-availability-dependent architecture decisions around this exclusivity explicitly; a multi-cloud model-agnostic design needs a different frontier model choice for Bedrock/Vertex deployments |

## Tradeoffs & when NOT to use it

- **Don't commit to PTU capacity without measured sustained volume data.** Below the roughly 150-200M tokens/month break-even for GPT-4o-class models, PTU is paying for idle reserved capacity that pay-as-you-go would have covered more cheaply.
- **Don't assume Foundry Agent Service's memory feature is as mature as AgentCore's.** As of Q1 2026 it's public preview, meaningfully behind Bedrock AgentCore's GA-day episodic memory — verify current maturity before committing a memory-dependent agent design to Foundry without a fallback plan.
- **Don't reach for AI Search's semantic ranker on the Free tier expecting it to be available.** It's explicitly excluded there; budget for at least Basic/Standard tier if semantic re-ranking is part of the RAG design.
- **Don't design a multi-cloud, model-agnostic agent architecture assuming GPT-5 parity across Bedrock/Vertex/Azure.** GPT-5 and OpenAI's frontier lineup are Azure/OpenAI-exclusive; a genuinely cloud-agnostic design needs a different frontier model per platform or accepts Azure-specific lock-in for that model tier.
- **Don't ignore AI Search's per-partition vector memory quota when planning corpus growth.** A growing vector corpus without partition-count planning will hit the memory ceiling before hitting any storage ceiling, since HNSW vector fields must reside fully in memory.
- **Don't default to Foundry Agent Service purely because it's "the Microsoft option" if the team has no Microsoft 365/Teams integration requirement and needs the most framework-agnostic runtime.** Bedrock AgentCore's framework-agnosticism and Vertex's A2A-native multi-agent tooling are each the better fit for specific requirements Foundry doesn't uniquely serve.

## Interview questions

### Q1 — Trace Microsoft's GenAI platform rebrand history and explain why the November 2025 name change is more than cosmetic.
**Testing:** currency on a genuinely confusing, fast-moving rebrand history.
**Answer:** Azure AI Studio (GA May 2024) → Azure AI Foundry (Ignite Nov 2024, positioning agent development/evaluation as first-class) → Microsoft Foundry (Ignite Nov 2025). The 2025 rename specifically drops "Azure" to signal that agents are meant to be a first-class citizen across the entire Microsoft ecosystem (365, Copilot, Teams) rather than scoped to Azure as just another cloud service — a positioning shift, not a mere UI refresh.
**Follow-up trap:** *"Does the underlying product architecture change with each rebrand, or just the name?"* — the underlying platform has evolved substantially alongside the naming (agent service GA, memory features, model catalog expansion), so it's not purely cosmetic, but the specific rebrand events themselves are naming/positioning changes layered on top of continuous underlying product evolution — conflating "renamed" with "rearchitected" for a specific event is an easy mistake.

### Q2 — Explain why a workload can hit Azure OpenAI rate limits in one region while having unused quota in another, and why this surprises teams.
**Testing:** the region/model/subscription-scoped quota mechanic.
**Answer:** Azure OpenAI quota (TPM, and RPM derived from it) is enforced per region, per model, per subscription — not as a global account-wide pool. A deployment in East US draws only against East US's quota for that model; unused West Europe quota for the same model provides zero relief. Teams used to a single global rate-limit mental model (common in some other API providers) are surprised when "we have plenty of quota" turns out to mean quota in the wrong region.
**Follow-up trap:** *"Does deploying the same model in multiple regions effectively multiply available throughput?"* — yes, mechanically it does (each region's quota is independent), which is a legitimate scaling pattern, but it introduces real architecture complexity: request routing across regions, potential data residency concerns depending on the workload, and needing to handle partial regional failures gracefully rather than treating multi-region deployment as a free throughput multiplier.

### Q3 — A team wants to move a production Azure OpenAI workload from pay-as-you-go to PTU. What do you need to know before recommending it?
**Testing:** the break-even economics, not just "PTU is for production."
**Answer:** PTU bills a fixed hourly rate (~$1/PTU-hour, ~$260/month reserved for GPT-4o-class) regardless of actual token consumption, so it only pays off once sustained monthly token volume clears the pay-as-you-go break-even — typically cited around 150-200 million tokens/month for GPT-4o. Below that threshold, PTU is effectively paying for idle capacity that per-token billing would have covered more cheaply. Need actual measured sustained volume data, not a projection, before committing.
**Follow-up trap:** *"Does PTU also guarantee lower latency, separate from the cost consideration?"* — yes, that's a real secondary benefit: PTU capacity is dedicated, so it isn't subject to the same request-queueing/throttling behavior a heavily-shared pay-as-you-go pool can exhibit under load — but the primary decision driver in an interview answer should still be the volume-based cost break-even, with latency predictability as a secondary justification that can tip a borderline case.

### Q4 — Compare Foundry Agent Service, Bedrock AgentCore, and Vertex AI Agent Builder on their single most differentiating capability each.
**Testing:** synthesizing the three-way competitive landscape rather than reciting a static feature table.
**Answer:** Foundry Agent Service's standout is first-party GPT-5/OpenAI-frontier model access plus deep Microsoft 365/Teams integration (one-click Teams deployment) — capabilities the other two structurally cannot match given the OpenAI partnership's exclusivity. Bedrock AgentCore's standout is being the most framework-agnostic runtime with a microVM-per-session isolation model purpose-built for long-running (~8 hour) agentic sessions, plus episodic memory available at GA. Vertex AI Agent Builder's standout is originating the Agent-to-Agent (A2A) protocol and shipping the deepest low-code agent-authoring tooling, evidenced by ADK's 7M+ downloads.
**Follow-up trap:** *"If a team has no Microsoft 365 dependency and no strong framework preference, which should they default to?"* — there's no universally correct default; the honest answer weighs the team's actual model preference (GPT-5 access pulls toward Foundry), session-duration/isolation requirements (long-running sessions pull toward AgentCore), and multi-agent orchestration complexity (A2A-native needs pull toward Vertex) — picking one without naming the actual requirement driving the choice is the weak answer.

### Q5 — As of early 2026, how does Foundry Agent Service's native memory feature compare to Bedrock AgentCore's, and why does this matter for a design decision?
**Testing:** a specific, current, and non-obvious capability gap.
**Answer:** Foundry's native agent memory (automatically extracting and reconciling facts across sessions) reached public preview only in Q1 2026, while Bedrock AgentCore shipped episodic memory at its October 2025 GA — a real maturity gap as of this writing. This matters concretely for any agent design that depends on persistent cross-session memory as a core capability rather than a nice-to-have: choosing Foundry today for such a design either requires building custom memory management on top of Foundry's primitives or accepting preview-stability risk.
**Follow-up trap:** *"Is this gap permanent, or does it reflect Microsoft's actual investment priority?"* — nothing about the gap suggests it's permanent; it's a timing/maturity gap in a fast-moving area, and the responsible answer explicitly flags this as something to re-verify near interview time rather than asserting it as a fixed competitive weakness.

### Q6 — Explain how AI Search's hybrid search pipeline works mechanically, and why "hybrid search" alone doesn't guarantee semantic ranking is active.
**Testing:** the specific tier-gating and configuration trap.
**Answer:** Hybrid search fuses BM25 keyword scoring with dense vector similarity in one query — that fusion happens regardless of tier (once vector search is available at all, which excludes only the most limited Free-tier scenarios). Semantic ranking is a separate, optional re-ranking step applied to the fused result set, using a cross-encoder-style model, and it is specifically unavailable on the Free tier and must be explicitly configured (a semantic configuration referencing which fields to rank) even on tiers that support it — a pipeline can run genuine hybrid (BM25+vector) search while silently missing the semantic re-ranking layer if that configuration step was skipped.
**Follow-up trap:** *"Does enabling semantic ranking always improve relevance enough to justify its cost and latency?"* — not universally; semantic ranking's biggest measured gains are typically on long-tail, ambiguous, or natural-language queries where pure lexical/vector scoring underperforms — for narrow, well-structured query patterns the improvement may not justify the added latency and the queuing-related availability risk under high concurrency.

### Q7 — A high-concurrency RAG application using AI Search's semantic ranker starts seeing outright request rejections under load, not degraded latency. Diagnose.
**Testing:** the specific queue-then-reject behavior, a real production capacity-planning trap.
**Answer:** Semantic ranking uses an internal queuing system to manage concurrent requests; once that queue itself fills, further requests are rejected outright rather than the system gracefully degrading (e.g., silently falling back to non-semantic ranking). This is a hard capacity ceiling tied to the service's tier/replica configuration, not a soft degradation curve.
**Follow-up trap:** *"What's the mitigation — just add more replicas?"* — scaling replicas/tier raises the concurrent semantic-ranking ceiling and is the primary fix, but a resilient design should also have an explicit fallback path (catching the rejection and falling back to non-semantic hybrid search) for traffic bursts that exceed even a well-provisioned ceiling, rather than treating "add capacity" as a complete solution on its own.

### Q8 — Explain the mechanical difference between Azure OpenAI's "deployment" concept and how the raw OpenAI API or Bedrock/Vertex handle model access.
**Testing:** an Azure-specific mechanic that trips engineers used to calling a model name directly.
**Answer:** Azure OpenAI requires creating a **deployment** — a named binding of a specific model version to an assigned capacity (TPM quota, or a PTU reservation) within an Azure OpenAI resource — and API calls reference the deployment name, not the raw model name directly. This differs from calling OpenAI's own API (model name specified directly per request) and is architecturally similar in spirit to how a team might name environment-specific model endpoints elsewhere, but it's a mandatory Azure-specific indirection layer that trips engineers expecting to pass `"gpt-4o"` directly the way they would against OpenAI's own API.
**Follow-up trap:** *"Does this deployment indirection provide any benefit beyond being an extra step?"* — yes: it's what enables per-deployment TPM/PTU capacity assignment and per-deployment content-filter configuration, letting one Azure OpenAI resource host multiple differently-configured deployments of the same or different models (e.g., a stricter-filtered customer-facing deployment and a looser internal-tooling deployment) — the indirection is the mechanism that makes fine-grained capacity and policy control possible.

### Q9 — Design the model/agent architecture for an enterprise wanting deep Teams integration, GPT-5 access, and a fallback if Foundry's agent memory preview proves unstable.
**Testing:** synthesizing platform selection with a concrete risk-mitigation plan.
**Answer:** Foundry Agent Service is the correct platform choice given the explicit Teams integration and GPT-5-access requirements — no competitor offers both. For the memory-stability risk, since native memory is still preview-stage, design the agent to persist its own session-relevant facts explicitly (writing extracted state to a Cosmos DB or AI Search-backed store the application controls) rather than depending solely on Foundry's built-in memory feature, allowing a graceful fallback if the preview feature proves unstable or changes behavior before GA.
**Follow-up trap:** *"Isn't building custom memory management redundant work if Foundry's native memory eventually reaches GA?"* — some rework is likely, but for a production system with real reliability requirements, depending on a preview-stage feature without a fallback is the higher risk; the redundant engineering cost is the reasonable price of derisking a production dependency on an immature capability, and the custom layer can be simplified or retired once native memory proves stable at GA.

### Q10 — Why does Azure's exclusive first-party access to GPT-5 matter architecturally, not just commercially, for a team designing a genuinely cloud-agnostic AI system?
**Testing:** the deeper design implication of model exclusivity, beyond "Azure has a good deal with OpenAI."
**Answer:** A cloud-agnostic architecture typically abstracts model access behind an interface allowing provider swap-out, but if a specific frontier model's capability (reasoning quality, specific benchmark performance, specific tool-use behavior) is a genuine product requirement and that model is Azure/OpenAI-exclusive, true multi-cloud portability for that capability doesn't exist — the abstraction layer can swap *providers offering comparable-tier models*, but can't swap to an equivalent GPT-5 elsewhere. This means "cloud-agnostic" architecture decisions need to explicitly decide whether frontier-model-exclusivity is an acceptable lock-in point or whether the design commits to a different (available-everywhere) model tier to preserve true portability.
**Follow-up trap:** *"Does this mean any interviewer expecting a 'multi-cloud is always better' answer is testing for the wrong thing?"* — yes, and naming that directly is the strong answer: genuine multi-cloud portability for the absolute frontier model tier is not achievable today given real exclusivity arrangements, and a good architecture decision states that tradeoff explicitly rather than pretending full provider-agnosticism is free.

## Red flags that fail you

- Not knowing the Azure AI Studio → Azure AI Foundry → Microsoft Foundry rebrand history, or treating "Azure AI Foundry" as still the current name without noting the Nov 2025 change.
- Claiming Azure OpenAI quota is a single global pool rather than per-region, per-model, per-subscription.
- Recommending PTU without any reference to measured sustained volume or the pay-as-you-go break-even.
- Assuming GPT-5 is equally available on Bedrock and Vertex.
- Not knowing Foundry's native agent memory is still preview-stage as of early 2026, behind Bedrock AgentCore's GA-day memory.
- Claiming "hybrid search" on AI Search automatically includes semantic ranking without naming the tier gate and explicit configuration requirement.
- Not knowing AI Search's vector quota is a per-partition memory constraint, not a flat account-wide storage limit.
