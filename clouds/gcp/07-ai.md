# GCP AI Deep: Vertex AI, Agent Builder/ADK, Gemini API, Vector Search

> **Track:** C-GCP Google Cloud Atlas · **Time:** 2.5h · **Prereqs:** C-GCP-data · **Updated:** 2026-08-23
> **Module id:** `C-GCP-ai` · **Tags:** ai,critical

## The 30-second version

Four layers stack into GCP's AI surface. **Vertex AI** is the platform: Model Garden (200+ models including Google and third-party like Claude), custom training on managed compute, pipelines, registry, and the managed **Agent Engine** runtime for stateful agents. **ADK** (Agent Development Kit) is Google's open-source, code-first agent framework — Python/TypeScript/Go/Java/Kotlin, model-agnostic but Gemini-optimized — which compiles to deployments on Agent Engine or anywhere else. The **Gemini API** exposes the frontier models: Gemini 2.5-class with 1M-token context windows (tiered pricing below/above ~200K tokens), context caching for repeated prefixes, batch mode at ~50% off, and thinking/reasoning variants. **Vector Search** (formerly Matching Engine, built on ScaNN) serves billion-scale approximate nearest neighbor queries with filtered search. The interview core: knowing when each layer earns its cost — Agent Engine versus rolling your own runtime on Cloud Run, RAG versus long context as genuinely different tradeoffs, and Vector Search versus pgvector-class options by scale ceiling.

## Why this gets asked

Because AI infrastructure interviews now probe judgment under churn: models deprecate quarterly, frameworks rename yearly (Vertex AI Search & Conversation became Agent Builder became parts of a Gemini-branded enterprise platform; Reasoning Engine became Agent Engine), and candidates who memorized product names rather than mechanisms expose themselves immediately. Interviewers who run these stacks ask questions with stable answers underneath the churn: what does a managed agent runtime actually buy you over containers plus a framework (session/state persistence, auth wiring, evaluation harnesses — and what it costs); when does 1M-token context beat retrieval (freshness of corpus, citation needs, per-query economics); where does Vector Search's ANN index type choice matter (recall/latency/QPS tradeoffs, streaming updates versus batch rebuilds). His own resume carries production RAG at scale and LLM serving — this module is where he proves the GCP-specific translation of that experience.

## Lineage: past → present → future

**What came before.** Google's internal lineage runs through its recommendation/search ML stack: ScaNN (the 2020 ICML paper on anisotropic vector quantization enabling billion-scale ANN with high recall) became Vertex AI Matching Engine, publicized 2021. The pre-unification era was fragmented: separate AI Platform (training/prediction), AutoML products, Dialogflow (conversation), and Enterprise Knowledge Graph–adjacent search — each with its own APIs and IAM surfaces. Vertex AI launched 2021 to unify training, prediction, pipelines, feature store under one console and API family. The pain driving consolidation: teams assembling LLM-era systems needed one identity/network/quota boundary across embedding generation, vector serving, and model inference instead of five.

**Where it stands now.** The current shape: Model Garden hosts Google models plus third-party (Anthropic, Mistral, Meta among them) behind unified endpoints; Gemini 2.5-generation models carry 1M-token contexts with tiered pricing and thinking budgets; context caching went production-grade in 2025 making repeated-prefix workloads materially cheaper (~50%+ input savings on cache hits region-dependent ~); batch prediction halves costs further (~). On agents: ADK (open-sourced April 2025) is the code-first framework — workflow agents for deterministic orchestration, LLM agents for reasoning loops, multi-agent trees, evaluation tooling — deploying to Agent Engine (managed runtime with session/memory persistence) or Cloud Run/GKE. The enterprise umbrella keeps renaming (Agent Builder → Agentspace → Gemini-flavored platform naming through 2025–2026), which is exactly why mechanism-first knowledge wins interviews. [ADK docs](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/adk); accessed 2026-08-23. [Gemini API long-context guide](https://apiscout.dev/guides/google-gemini-api-long-context-window-2026); accessed 2026-08-23. Live disagreement: RAG versus long context — vendors of both oversimplify; the honest position is workload-dependent (corpus volatility, citation requirements, query multiplicity against shared corpora).

**Where it's heading.** High confidence: agent governance hardening — dedicated agent identities (tying back to the IAM module), registries, gateways, and audit trails are already shipping because unmanaged agent credentials are the new security hole. High confidence: context management becoming a framework-level concern (ADK explicitly manages context rather than concatenating strings), with memory banks persisting across sessions. Medium confidence: price/performance convergence between Flash-class and Pro-class blurring model-choice decisions toward automatic routing. Speculative: on-device/hybrid Gemini distribution changing where inference happens; treat any specific claim skeptically until GA documentation exists.

## How it actually works

### Gemini API mechanics

Models expose token-based pricing per million input/output tokens; the 2.5-generation introduced **tiered input pricing** — rates differ below versus above ~200K tokens (~), so stuffing context has a step-function cost. Three cost levers matter in production:

- **Context caching**: store a large immutable prefix (system prompt + reference docs) and pay reduced rates on subsequent cache-hit tokens; cache lives for a configurable TTL and bills storage while alive. Wins big when many queries share one prefix; worthless for unique-per-request prompts.
- **Batch mode**: async submission at ~50% discount across models (~) — the answer when latency tolerance exists.
- **Thinking budgets** (on thinking-capable variants): cap reasoning-token spend per request, trading depth for latency/cost.

Operational numbers to hold: ~360 requests/min Flash-class and ~60/min Pro-class on pay-as-you-go tiers (~); first-token latency at 500K-token prompts measured in tens of seconds (~30–90s ~) — long context is not a real-time pattern. Retrieval quality degrades with distance from context edges ("lost in the middle"), and needle-recall at 1M tokens outperforms complex reasoning over the same span — "the window is real; uniform quality isn't."

### Vertex AI platform services

Model Garden: catalog of Google plus third-party models behind consistent endpoints/IAM/quota surfaces — the operational value is one security boundary. Custom training: container-based jobs onto managed compute (including GPU pools), hyperparameter tuning service, Pipelines (Kubeflow-derived) for orchestration, Model Registry for versioning, online prediction endpoints with autoscaling or dedicated provisioned throughput for LLM serving. For self-hosted LLMs (his vLLM-on-SageMaker experience translates directly): deploy inference containers with attached accelerators; the tradeoff versus Gemini API is control plus data residency versus zero ops.

### ADK + Agent Engine

ADK's model is standard software development: `Agent(name, model, instruction, tools)` as the unit; workflow agents (sequential/parallel/loop) compose deterministic structure around LLM agents; tools are Python functions, OpenAPI specs, or built-ins (Google Search, code execution); multi-agent trees delegate via sub-agents; evaluation runs as testable artifacts. Deployment targets: **Agent Engine** (managed: persists session state, integrates Memory Bank for cross-session recall, handles auth wiring to Vertex endpoints, exposes eval hooks) or anywhere containers run (`adk deploy` to Cloud Run/GKE). The honest comparison: Agent Engine buys state/session management and Google-ecosystem wiring at platform pricing and some lock-in; Cloud Run hosting keeps portability and makes you own persistence (checkpointing to a database) — the same durable-execution tradeoffs from earlier modules.

### Vector Search

ScaNN-based ANN service: build an index over embeddings (two index families — brute-force for exactness at small scale, tree-AH or the newer streaming-friendly types ~), query returns approximate nearest neighbors in tens of milliseconds at high QPS, with **filtering** (restrict by metadata namespaces/tags) executed alongside the search rather than post-filtering. Index builds are batch-oriented; streaming updates supported on certain index types with update-latency tradeoffs (~). Scale positioning: billion-vectors territory. The alternatives ladder matters more than loyalty: pgvector/AlloyDB AI (millions of vectors, operational simplicity), BigQuery vector search (analytics-adjacent, no extra infra), Vertex Vector Search (billion-scale QPS-heavy). Choosing Vector Search for a 500k-document corpus pays platform tax for headroom nobody uses.

## Build it from scratch

An ADK agent with a retrieval tool, minimal:

```python
# untested sketch - ADK shape
from google.adk import Agent
from google.adk.tools import google_search

def lookup_policy(query: str) -> str:
    """Retrieval tool: embed query, search index, return top chunks."""
    emb = embeddings_client.embed(query)          # text-embedding model call
    hits = vector_search_client.neighbors(emb, k=5, filter={"team": "hr"})
    return "\n\n".join(h.chunk_text for h in hits)

agent = Agent(
    name="hr_assistant",
    model="gemini-flash-latest",        # pin explicit versions in prod, not -latest
    instruction="Answer HR policy questions using only retrieved context; "
                "cite section numbers; say 'not in policy' when absent.",
    tools=[lookup_policy],
)
```

```python
# untested sketch
def rag_cost(queries_per_day, chunks_per_query=8, chunk_tokens=500,
             embed_once_tokens=1_000_000):
    input_per_query = chunks_per_query * chunk_tokens          # ~4k tokens
    return queries_per_day * 30 * input_per_query / 1e6 * FLASH_IN_PRICE

def longctx_cost(queries_per_day, corpus_tokens=400_000, cached=True):
    effective = corpus_tokens * (0.25 if cached else 1.0)      # cache hit discount ~
    return queries_per_day * 30 * effective / 1e6 * PRO_IN_PRICE_TIERED

# 50 queries/day against a stable 400k-token corpus:
#   RAG re-embeds once (~$0.13 one-off), then pays ~2k tokens/query
#   Long context re-sends 400k tokens every query unless cached - and cache TTLs expire.
```

## How it's done in production

Reference estate: embeddings generated via Vertex endpoints into Vector Search (or AlloyDB AI below billion-scale); Gemini Flash-class for high-volume paths with Pro-class routed for hard queries; context caching on shared system+knowledge prefixes with TTL matched to knowledge refresh cadence; batch mode for offline enrichment; agents built in ADK deployed to Agent Engine where session persistence matters, Cloud Run elsewhere; evaluations as CI artifacts (golden sets, rubric scoring) gating prompt/model changes; governance via dedicated agent service identities, quota monitoring, and content filters. Model-version discipline: pin exact versions (`gemini-2.5-flash@...` style identifiers), test against new versions in staging before switching off `-latest` aliases.

| Symptom | Cause | Fix |
|---|---|---|
| Answer quality collapses mid-conversation | Context overflow silently truncating earliest turns | Token accounting per turn; summarize/compact history; framework-managed context (ADK) |
| LLM bill doubles after "improvement" | Longer prompts shipped without measuring tier crossing | Track tokens/request vs 200K tier boundary (~); caching on shared prefixes |
| Vector Search returns irrelevant neighbors | Post-filtering instead of filtered search, or stale index | Use native filtering namespaces; schedule index refresh; recall@k evals |
| Agent works in demo, fails in prod | No evaluation harness; state lost between sessions | Golden-set CI gates; Agent Engine sessions or explicit checkpoint store |
| Rate limits hit during traffic spike | Single-model architecture at PAYG limits | Multi-model routing (Flash/Pro split), batch where async possible, quota requests |
| `-latest` model alias changed behavior overnight | Alias moved to new version | Pin explicit versions; staging canary per model release |

## Tradeoffs & when NOT to use it

- **Don't default to Agent Engine** — teams with existing platform engineering and custom runtime needs often pay lock-in tax for features they'll rebuild anyway; conversely, two-developer teams rebuilding session stores are burning runway to avoid platform pricing.
- **Long context is not RAG replacement** — repeated queries against a changing corpus with citation requirements stay RAG-shaped; long context wins one-shot holistic analysis of static documents. Cost scales linearly with corpus size per query; retrieval doesn't.
- **Vector Search is wrong below ~10M vectors (~)** — pgvector/AlloyDB AI or BigQuery vector types serve smaller corpora with less infrastructure; the ANN platform earns its keep at scale and QPS.
- **Gemini API versus self-hosted open models:** data residency, fine-tune depth, or unit economics at extreme volume justify vLLM-on-GKE; otherwise managed frontier models win on capability-per-ops-dollar almost always.
- **Thinking models everywhere is waste** — reasoning variants cost multiples for latency; route simple extraction/classification to non-thinking Flash-class and reserve thinking budgets for genuinely hard steps.

## Interview questions

### Q1 — Design a production RAG system on GCP for 50M documents. Walk through every layer.
**Testing:** end-to-end synthesis matching his actual resume experience.
**Answer:** Ingestion: chunk documents (~500-token chunks with overlap), embed via Vertex embedding endpoints in batch mode (~50% off ~), write vectors plus metadata to Vector Search (billion-scale headroom, filtered namespaces per tenant). Serving: query embeds at runtime → filtered ANN top-k (k=5–10) → rerank if quality demands → Gemini Flash with retrieved context and citation instructions; context caching over the static system+instruction prefix. Governance: golden-set evals gating prompt/index changes, agent identity isolation, token/cost dashboards per feature.
**Follow-up trap:** *"Why Vector Search over AlloyDB AI's ScaNN indexes?"* — corpus size: 50M chunks sits where managed ANN horizontal scaling pays; a 2M-chunk corporate wiki stays simpler in-database. State the scale threshold rather than loyalty.

### Q2 — When does Gemini's 1M-token context beat RAG? Be precise about the economics.
**Testing:** the tradeoff depth-bar item.
**Answer:** Long context wins for one-shot holistic analysis of static documents (whole-codebase review, single mega-contract): no retrieval infra, full cross-document attention, citations less critical. RAG wins when queries repeat against shared corpora (cost scales per-query against re-sent tokens), corpora change frequently (re-embedding beats re-sending), or citations must trace to sources. Numbers that decide it: 400K-token corpus × daily queries = 400K tokens/query re-sent unless cached; cache hits discount but TTLs expire; tiered pricing above ~200K tokens raises marginal cost further (~).
**Follow-up trap:** *"Doesn't needle-in-haystack near-perfection make retrieval obsolete?"* — recall of simple facts holds at 1M; complex multi-hop reasoning over the same span degrades measurably ("context rot"), and latency at 500K tokens runs tens of seconds — benchmarks measure retrieval, not reasoning-uniformity or latency budgets.

### Q3 — ADK versus LangGraph versus rolling your own loop: how do you choose?
**Testing:** framework judgment from someone who has shipped agents.
**Answer:** ADK: code-first, workflow agents give deterministic structure around LLM steps, first-class Agent Engine deployment, Google-ecosystem tools — pick when GCP-native and managed runtime appeal. LangGraph: graph state machine maturity, checkpointers across many stores, larger community patterns — pick when portable across clouds or deep graph control matters. Own loop: total control, zero abstraction leakage, all persistence/auth/evals yours — justified only with platform team bandwidth and specific runtime needs. All three converge conceptually: state, transitions, tools, checkpoints; interviews reward describing those primitives over brand loyalty.
**Follow-up trap:** *"What does Agent Engine actually buy?"* — session/state persistence without your datastore, Memory Bank integration, auth wiring to Vertex endpoints, eval hooks; costs are platform pricing plus lock-in. The counter is ADK-on-Cloud-Run with explicit checkpointing — same architecture you'd build anyway, portable.

### Q4 — Explain Vector Search index types and their recall/latency/update tradeoffs.
**Testing:** ANN mechanics beyond "it does embeddings."
**Answer:** Brute-force indexes: exact, fine at small scale. Tree-AH (asymmetric hashing tree): high-QPS approximate serving built via batch jobs — rebuilds are batch operations, so fresh-data latency depends on index-update cadence. Streaming-friendly index types support incremental upserts with update-propagation lag (~). Filtering executes during search via namespace restrictions (pre-filtering) which preserves recall far better than post-filtering results. Recall@k against latency/QPS is tunable via leaf-count/neighbor-count parameters; benchmark with your own query distribution, not vendor defaults.
**Follow-up trap:** *"Your filtered search returns fewer than k results — why?"* — pre-filtering restricts candidates before ANN traversal, so sparse filters legitimately return short result sets (correct behavior); post-filtering would pad with irrelevant neighbors instead. Knowing which behavior your system exhibits is the tested detail.

### Q5 — Your agent platform bill tripled month-over-month. Diagnose systematically.
**Testing:** FinOps instincts applied to AI spend specifically.
**Answer:** Token accounting by feature first (`usage_metadata` per call): likely culprits — conversation histories growing unboundedly into prompts (context overflow territory), thinking tokens enabled globally, `-latest` alias moving traffic to pricier versions, cache misses after TTL misconfiguration, retry storms multiplying calls. Fixes ranked: compact/summarize histories, cap thinking budgets per endpoint, pin versions, align cache TTLs with prefix volatility, route simple paths to Flash-lite classes, batch offline workloads. Establish per-feature unit-cost dashboards so regressions page someone.
**Follow-up trap:** *"Caching didn't reduce costs — why?"* — caches bill storage while alive and pay off only above hit-rate thresholds; unique prefixes (per-user personalization baked into system prompts) never hit. Restructure so volatile content lives in the message tail, not the cached prefix.

### Q6 — How do you evaluate an LLM agent before and after deployment?
**Testing:** evaluation maturity — his FastMCP/LangGraph background makes this table stakes.
**Answer:** Offline: golden sets (input → expected outcome/tool-calls) run in CI; rubric-based LLM-as-judge scored against human-labeled subsets; trajectory evaluation asserting tool-call sequences, not just final text. Online: task-completion rates, human-handoff rates, cost/task, latency distributions. Version-gate everything: prompt changes, model version bumps, and tool changes each run the same harness. Shadow new model versions against live traffic before switching aliases.
**Follow-up trap:** *"Judge models disagree with humans 20% of the time — still useful?"* — yes as regression detectors, not ground truth: absolute scores drift, relative deltas between versions remain informative when judge prompts are frozen. Human-label a calibration subset continuously.

### Q7 — Model Garden hosts third-party models like Claude next to Gemini. When does that matter architecturally?
**Testing:** whether Model Garden is understood as an ops surface, not a catalog.
**Answer:** One IAM/quota/networking boundary across heterogeneous models means swapping providers per workload without new security reviews; useful for capability routing (different strengths), redundancy, and negotiation leverage. Tradeoffs: pricing/features differ per provider behind the unified surface; data-residency and terms vary; deep provider-specific features (prompt caching implementations, fine-tune APIs) diverge. Architecturally it enables a router pattern: policy-based model selection with consistent observability.
**Follow-up trap:** *"Any hidden coupling?"* — yes: request/response schema conventions, rate-limit shapes, and error semantics differ subtly; abstraction layers leak. Teams standardizing on one provider's SDK idioms pay migration tax later — keep the adapter thin and explicit.

### Q8 — Self-hosted vLLM on GKE versus Gemini API: give the real decision criteria.
**Testing:** direct translation of his SageMaker/vLLM experience to GCP.
**Answer:** Choose self-hosted when: data residency prohibits external processing, model weights are custom/open-only, throughput justifies committed accelerators (steady high volume amortizes A3/GPU pools), or fine-grained serving control (custom quantization, batching policies) matters. Choose API when: frontier capability required (open weight gaps), traffic spiky (idle GPUs bleed money), ops capacity scarce. Middle path exists: provisioned throughput on Vertex endpoints — dedicated capacity without cluster ops.
**Follow-up trap:** *"Break-even intuition?"* — sustained utilization above roughly half of GPU capacity favors owning; below that, API's zero-idle wins. Compute tokens/sec/dollar both ways including ops labor; most teams underestimate labor until they run 24/7 GPU fleets.

### Q9 — How should agent identities be governed on GCP?
**Testing:** ties this module back to the IAM module — the senior synthesis.
**Answer:** Dedicated service identities per agent (never reuse human or shared credentials), least-privilege roles scoped to that agent's tools, Principal Access Boundary caps on reachable resources, audit-log attribution making every tool call attributable to one agent identity, org-policy constraints preventing key creation so agents authenticate via attached SAs/WIF. Agent registries/gateways formalize inventory and routing as estates grow. The failure being prevented: an agent borrowing broad human credentials turns any prompt-injection success into privilege escalation.
**Follow-up trap:** *"Agent acts for a user — whose permissions apply?"* — design choice with real consequences: agent-identity permissioning (safer, may lack user context) versus delegated user scopes (dangerous: injection runs as the user). Production answer usually: agent identity + application-level authorization checks inside tools, not raw credential delegation.

### Q10 — What actually changed in GCP's agent product naming through 2024–2026, and why does it matter operationally?
**Testing:** currency plus healthy skepticism about churn.
**Answer:** Vertex AI Agent Builder (2023–24) encompassed search/conversation grounding; Reasoning Engine became Agent Engine; Agentspace appeared as enterprise agent workspace; through 2025–2026 pieces consolidated under Gemini-branded enterprise platform naming while ADK remained the stable open-source core. Operationally: APIs underneath outlive marketing names; docs redirect frequently; teams should anchor on ADK repo, Agent Engine endpoints, and Vertex API surfaces — and treat name-driven migrations skeptically until deprecation notices force them.
**Follow-up trap:** *"So which do I put on my architecture diagram?"* — the durable primitives: model endpoints (Vertex/Gemini API), agent runtime (Agent Engine or self-managed), retrieval (Vector Search), orchestration (ADK). Diagrams naming only umbrella products age badly and hide the seams where failures occur.

### Q11 — Grounding and attribution: how do you stop hallucinated answers reaching users in a RAG agent?
**Testing:** correctness engineering beyond vibes.
**Answer:** Layers: grounding instructions requiring section-cited answers with explicit "not found" behavior; structured output schemas forcing answer-plus-citations format validated programmatically; retrieval-side confidence gates (skip generation below similarity thresholds); verification passes checking cited sections actually contain claims (cheap NLI-style checks); UI rendering citations clickable so verification is user-visible. Evaluation: refusal-behavior tests alongside accuracy tests — a RAG system graded only on answered questions rewards hallucination.
**Follow-up trap:** *"Model cites sources but misrepresents them."* — citation presence isn't fidelity: add claim-level entailment checks against retrieved chunks, sample-audit judge agreement, and log low-confidence paths for review. Perfect prevention doesn't exist; measured degradation detection does.

## Red flags that fail you

- Reciting product umbrella names without knowing what runs underneath (Agent Builder vs Agent Engine vs ADK).
- Claiming long context makes RAG obsolete, or vice versa — workload-dependent answers are the correct ones.
- Using `-latest` model aliases in production without version pinning.
- Recommending Vector Search for sub-10M-vector corpora without justifying the platform tax.
- No evaluation story for agents ("we tested manually").
- Ignoring thinking-token costs or context-tier pricing boundaries in cost models.
- Letting agents run under broad shared/human credentials.
