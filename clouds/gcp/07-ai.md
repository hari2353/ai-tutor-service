# Vertex AI, Gemini Enterprise Agent Platform, Gemini API, Vector Search

> **Track:** C-GCP Google Cloud Atlas · **Time:** 3.0h · **Prereqs:** `C-GCP-iam`, `C-GCP-storage-db` · **Updated:** 2026-08-08

## The 30-second version

Vertex AI is GCP's unified ML platform (training, Model Registry, Endpoints, Model Garden with 200+ models including Gemini, Claude, Llama, Mistral) — as of **April 22, 2026**, Google rebranded the agent-building layer on top of it into the **Gemini Enterprise Agent Platform**, which absorbed the old Vertex AI Agent Builder and Agentspace products, inverted the console hierarchy so agents are first-class and model training is a sub-feature, and made the **A2A protocol v1.0** the default agent-to-agent interoperability layer. The **Agent Development Kit (ADK)** is the open-source, code-first Python/Go/Java framework for building the agent logic itself — model-agnostic, deployable to **Agent Engine** (the managed runtime with GA **Sessions** and **Memory Bank** as of early 2026) or anywhere else. The **Gemini API** is the direct model-inference layer: Gemini 3.1 Pro (2M-token context, $2/$12 per M input/output tokens under 200K, $2.50/$15 above) and Gemini 3.5 Flash (1M context, $1.50/$9) are the current top-tier models, with Batch API giving 50% off and context caching cutting repeated-prompt cost up to ~90%. **Vector Search** is Google's managed vector database, built on the same **ScaNN** algorithm powering Google Search and YouTube, offering brute-force (exact) and tree-AH/ANN (approximate, ~99% recall, sub-10ms at billion-vector scale) index types. Compared honestly: **Bedrock AgentCore** has the more modular, composable primitives (Runtime, Memory, Identity, Gateway, Policy sold separately) and the strongest zero-trust/multi-tenant story; **Azure AI Foundry** wins decisively for Microsoft 365-native orgs via one-click Teams/Copilot integration; **Gemini Enterprise/ADK** wins on raw model-catalog breadth and the tightest data-platform integration (BigQuery, Vector Search, Spanner) but is the newest of the three to reach this shape and carries real rebrand-driven documentation churn risk through 2026.

## Why this gets asked

The interviewer has watched a team pick a GenAI platform based on which cloud they already had credits on, then discover mid-project that the agent framework's memory model, tool-calling contract, or multi-tenant isolation story doesn't match what production actually needs. They've also personally lived through at least one platform rebrand (Vertex AI Agent Builder to Gemini Enterprise being the freshest example) where documentation, SDK imports, and console navigation all shifted under a team's feet mid-build. They want to know you can name the actual architectural primitives underneath the marketing layer — Runtime vs Memory vs Identity vs Gateway is not the same concept across AWS/Azure/GCP even though all three now ship something called "agent memory" — and that you won't blindly trust a platform's agent story just because the model quality is good.

## Lineage: past → present → future

**What came before.** Vertex AI itself launched in **May 2021**, unifying what had been a scattered set of separate products — AutoML, AI Platform (the older training/prediction service), and various point solutions — into one MLOps platform with a shared Model Registry and Endpoints abstraction. The pain that unification solved: teams building on GCP's pre-Vertex AI stack had to stitch together AutoML for no-code model training, AI Platform Notebooks for custom training, and a separate prediction-serving product, each with its own IAM model and API surface, which meant real integration tax on every ML project. The agent layer's own prehistory is shorter and messier: 2023-2024 saw an explosion of DIY agent frameworks (LangChain, early AutoGPT-style loops) with no standard way for agents to call tools safely, no standard memory model beyond stuffing conversation history into a prompt, and no standard way for two agents built by different teams (or different companies) to talk to each other at all — every multi-agent system was bespoke integration work.

**Where it stands now.** All three major clouds reached a comparable agent-platform maturity milestone within roughly the same window: **AWS Bedrock AgentCore**, **Azure AI Foundry Agent Service**, and Google's agent platform all hit meaningful enterprise GA between October 2025 and Q1 2026. [Bedrock AgentCore vs Azure vs Vertex — AgentMarketCap](https://agentmarketcap.ai/blog/2026/04/09/aws-bedrock-agentcore-vs-azure-ai-agent-service-vs-google-vertex-ai-agents-q2-2026) — accessed 2026-08-08. Google's specific move, announced at Cloud Next '26 on **April 22, 2026**: Vertex AI Agent Builder and Agentspace were absorbed into the new **Gemini Enterprise Agent Platform**, which ships **Agent Studio** (a visual low-code builder), an **Agent Gateway**, first-class access to 200+ Model Garden models, and the **A2A protocol v1.0** as the default interoperability layer — existing Vertex AI workloads run unchanged under the new namespace with no breaking API/SDK changes, but as of May 21, 2026 "Vertex AI" no longer appears as a standalone label in the Cloud Console. [Introducing Gemini Enterprise Agent Platform — Google Cloud Blog](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform) — accessed 2026-08-08; [Vertex AI Is Now Gemini Enterprise Agent Platform — GCP Study Hub](https://gcpstudyhub.com/blog/vertex-ai-replaced-by-gemini-enterprise-agent-platform) — accessed 2026-08-08. The live disagreement industry-wide is less "which model is smartest" (all three catalogs now include near-frontier models from multiple vendors) and more which agent *runtime primitives* are the right abstraction — AWS's AgentCore ships Runtime, Memory, Identity, Gateway, and Policy as separately composable services; Azure's Foundry bundles memory and multi-agent orchestration (Magentic-One, now stable) more tightly into one Agent Service; Google's ADK+Agent Engine ships a code-first framework plus a managed runtime with GA Sessions/Memory Bank, betting that most teams want an opinionated framework rather than assembling primitives themselves. **A2A**, donated to the Linux Foundation in June 2025, reports 150+ supporting organizations and integration across Google, Microsoft, and AWS platforms as of April 2026 — real cross-cloud momentum, though independent assessments note the actual production-adoption picture is messier than the press-release numbers suggest, and A2A complements rather than replaces MCP (which handles agent-to-tool, not agent-to-agent, communication). [A2A Protocol Marks One Year — HPCwire](https://www.hpcwire.com/aiwire/2026/04/09/linux-foundation-a2a-protocol-marks-one-year-with-broad-enterprise-and-cloud-adoption/) — accessed 2026-08-08.

**Where it's heading.** High confidence: all three clouds continue converging model-catalog breadth (Vertex AI's Model Garden already carries Claude and Llama alongside Gemini; Bedrock and Foundry both carry multi-vendor catalogs too), so model choice is decreasingly a cloud-lock-in decision and increasingly a per-workload one. Moderate confidence: A2A and MCP both continue maturing as complementary standards rather than either displacing the other, given the Linux Foundation governance structure removes single-vendor control as a blocker to broader adoption. Moderate-to-low confidence, worth a fresh check near interview time: whether Google's Gemini Enterprise rebrand fully stabilizes documentation and SDK naming through 2026, since a platform-wide rebrand this large four months before this module was written is exactly the kind of change that produces stale blog posts and mismatched console screenshots for a while. Speculative: which platform's agent-memory model (episodic memory in AgentCore, built-in memory tools in Foundry, Memory Bank in Agent Engine) becomes the de facto pattern other frameworks copy — too early to call.

## How it actually works

### Vertex AI / Gemini Enterprise: what's underneath the rebrand

The **rebrand is organizational and console-level, not a rewrite** — Model Registry, custom training, AutoML, and Endpoints (the classic Vertex AI ML platform surface) still exist and still work with the same APIs; they're now presented as sub-features under an agent-first navigation rather than the top-level product. [Vertex AI Is Now Gemini Enterprise Agent Platform — GCP Study Hub](https://gcpstudyhub.com/blog/vertex-ai-replaced-by-gemini-enterprise-agent-platform) — accessed 2026-08-08. For interview purposes this matters mechanically in one specific way: **endpoint billing didn't change with the rebrand** — you still pay for every model deployed to an endpoint whether or not it's serving traffic, and you must explicitly undeploy to stop the charge. [Vertex AI Pricing 2026 — nOps](https://www.nops.io/blog/vertex-ai-pricing/) — accessed 2026-08-08. This is the single most common Vertex AI cost surprise: a team deploys a fine-tuned model for a demo, the demo ends, nobody undeploys, and the endpoint bills 24/7 indefinitely.

**Model Garden** hosts 200+ models — Gemini (Google's own), Claude (Anthropic), Llama (Meta), Mistral, Jamba (AI21), and open-weight models — behind one deployment and billing surface. [Vertex AI vs Bedrock vs Azure AI Foundry — Index.dev](https://www.index.dev/skill-vs-skill/ai-aws-bedrock-vs-azure-ai-vs-vertex) — accessed 2026-08-08. Third-party model pricing on Model Garden is set by the model vendor (Claude via Model Garden costs roughly what Claude costs via Bedrock, give or take), so the platform choice for a specific model is rarely about that model's price — it's about which platform's surrounding tooling (data connectors, agent runtime, observability) fits the workload.

### Gemini API: pricing mechanics that actually change design decisions

Gemini 3.1 Pro has the largest current context window at **2M tokens**, priced at **$2.00/1M input tokens for prompts up to 200K tokens, rising to $2.50/1M above 200K** (output: $12/1M under 200K, $15/1M above) — the **long-context surcharge** is the mechanical detail that changes RAG-vs-long-context design tradeoffs: stuffing a 500K-token document directly into context costs meaningfully more per token than the same content chunked and retrieved via RAG at under 200K effective context per call. Gemini 3.5 Flash (1M context, $1.50/$9) is the faster, cheaper tier for latency-sensitive or high-volume paths; Gemini 2.5 Flash-Lite ($0.10/$0.40) remains the cheapest tier for simple classification/extraction tasks that don't need frontier reasoning. [Gemini pricing 2026 — CloudZero](https://www.cloudzero.com/blog/gemini-pricing/) — accessed 2026-08-08. Two cost levers worth knowing cold: the **Batch API gives a flat 50% discount** on any model with a 24-hour processing SLA — the correct default for any workload that doesn't need synchronous responses (nightly summarization, bulk classification); **context caching** cuts the cost of repeated large-context prompts (a long system prompt or document reused across many calls) by up to roughly 90%, since cached tokens bill at a steep discount versus fresh input tokens. [Gemini API Pricing Guide 2026 — Curlscape](https://curlscape.com/blog/google-gemini-api-pricing-guide-2026) — accessed 2026-08-08. As of April 1, 2026, the free tier covers only Flash and Flash-Lite models — Pro-tier models are paid-only, a real gotcha for anyone assuming free-tier prototyping automatically covers the top model.

```python
# untested sketch -- Gemini API call with context caching, the lever that
# makes a large repeated system prompt/document cheap on repeated calls
from google import genai
from google.genai import types

client = genai.Client()

# Create a cache for a large, reused document (e.g. a long policy doc
# used as grounding context across many user queries)
cache = client.caches.create(
    model="gemini-3.1-pro",
    config=types.CreateCachedContentConfig(
        contents=[large_policy_document],
        ttl="3600s",
    ),
)

response = client.models.generate_content(
    model="gemini-3.1-pro",
    contents="Does this policy cover remote work stipends?",
    config=types.GenerateContentConfig(cached_content=cache.name),
    # Tokens in `large_policy_document` bill at the cached rate on this
    # and every subsequent call reusing cache.name within the TTL --
    # NOT the full input-token rate every time.
)
```

### ADK and Agent Engine: the code-first framework plus managed runtime

**ADK** (Agent Development Kit) is open-source, code-first (Python primary, Go and Java also shipped), and explicitly **model-agnostic and deployment-agnostic** — it's optimized for Gemini but not locked to it, and can deploy outside Vertex/Gemini Enterprise entirely. [Agent Development Kit — Google Developers Blog](https://developers.googleblog.com/en/agent-development-kit-easy-to-build-multi-agent-applications/) — accessed 2026-08-08. Core primitives: a **hierarchy of specialized agents** composed for multi-agent systems, a **rich tool ecosystem** for wiring in third-party APIs and custom code, a **graph-based workflow runtime** supporting routing, fan-out/fan-in, loops, retries, and human-in-the-loop steps, and **ADK Web**, a built-in dev UI exposing events, traces, artifacts, and evaluations for local debugging. [Hands-on with ADK — InfoWorld](https://www.infoworld.com/article/4153857/hands-on-with-the-google-agent-development-kit.html) — accessed 2026-08-08.

**Agent Engine** is the managed runtime ADK agents deploy to: it handles tool-call orchestration, state management, and scaling. **Sessions** persist chronological interaction history for contextual continuity across requests; **Memory Bank** (reached GA in early 2026) extracts salient facts from sessions and stores them for cross-session retrieval — the mechanical distinction that matters: Sessions is short-term, per-conversation state, Memory Bank is longer-term, cross-conversation knowledge extraction, and conflating the two leads to either bloating every prompt with full session history (expensive, hits context limits) or losing genuinely useful long-term context (agent "forgets" a user's stated preference from three sessions ago). [Memory Bank overview — Google Cloud](https://cloud.google.com/agent-builder/agent-engine/memory-bank/overview) — accessed 2026-08-08. Sessions, Memory Bank, and Code Execution were free through January 28, 2026; metered charges now apply alongside existing Agent Engine runtime fees, with Google noting core runtime pricing was trimmed to soften that transition. [Memory Bank quickstart — Google Cloud](https://cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/memory-bank/quickstart-adk) — accessed 2026-08-08.

```python
# untested sketch -- minimal ADK agent with a tool, deployable to Agent Engine
from google.adk.agents import Agent
from google.adk.tools import FunctionTool

def check_order_status(order_id: str) -> dict:
    """Look up an order's status by ID."""
    return {"order_id": order_id, "status": "shipped"}  # stub

order_agent = Agent(
    name="order_status_agent",
    model="gemini-3.5-flash",  # cheaper/faster tier for a narrow, high-volume task
    instruction="Answer questions about order status using the check_order_status tool.",
    tools=[FunctionTool(check_order_status)],
)
# Deploying `order_agent` to Agent Engine hands session persistence,
# scaling, and (if enabled) Memory Bank cross-session recall to the
# managed runtime -- the application code above stays the same whether
# it's run locally via ADK Web or deployed.
```

### Vector Search: ScaNN, index types, and where it fits

Vertex AI Vector Search is built on **ScaNN**, the same algorithm behind Google Search, YouTube, and Google Play recommendation — Vector Search 2.0 is described as fully managed and self-tuning. [Vector Search 2.0 — Kaz Sato/Medium](https://medium.com/google-cloud/introducing-vertex-ai-vector-search-2-0-from-zero-to-billion-scale-90ed666dac43) — accessed 2026-08-08. Two index types: **brute force**, exact linear search with no tunable parameters, appropriate only for small datasets or as a ground-truth baseline to validate ANN recall against; and **tree-AH (ANN)**, ScaNN's tree-structured asymmetric-hashing approach, which trades a small accuracy loss (reported around 99% recall) for sub-10ms query latency even at billion-vector scale — this is the index type for any real production deployment. [Configure Vector Search for billion-scale search — OneUptime](https://oneuptime.com/blog/post/2026-02-17-how-to-configure-vertex-ai-vector-search-indexes-for-billion-scale-similarity-search/view) — accessed 2026-08-08. Google's **SOAR** algorithm layers controlled redundancy on top — assigning vectors to multiple clusters as backup search paths — improving search efficiency at smaller index sizes. Operationally, Vector Search nodes bill per hour regardless of query traffic and endpoints stay billable until explicitly undeployed — the exact same "forgot to undeploy" cost trap as Vertex AI prediction endpoints generally.

The honest positioning question in an interview: **when is Vector Search the wrong choice?** If the vector workload naturally lives alongside an existing operational database that already needs to serve the same data transactionally, **AlloyDB AI**'s built-in ScaNN index or Spanner's vector index avoids running a second, separately-billed system just for embeddings. Vector Search earns its keep specifically as a dedicated, massively-scaled ANN service decoupled from any one operational database — the GCP-native answer to what Aurora pgvector, OpenSearch, or a dedicated system like Pinecone solve on AWS.

## Build it from scratch

Minimal illustration of a Vector Search-backed retrieval step feeding into a Gemini call, matching the shape of a from-scratch RAG pipeline (no lab folder ships with this module):

```python
# untested sketch -- query a Vertex AI Vector Search index, then ground
# a Gemini call with the retrieved chunks (the RAG pattern, mechanically)
from google.cloud import aiplatform
from google import genai

aiplatform.init(project="my-project", location="us-central1")

index_endpoint = aiplatform.MatchingEngineIndexEndpoint("projects/.../indexEndpoints/...")
query_embedding = embed_text("What's our refund policy for enterprise plans?")

# ANN search: tree-AH index, ~99% recall, sub-10ms even at large scale
neighbors = index_endpoint.find_neighbors(
    deployed_index_id="prod_v1",
    queries=[query_embedding],
    num_neighbors=5,
)
retrieved_chunks = [fetch_chunk_text(n.id) for n in neighbors[0]]

client = genai.Client()
response = client.models.generate_content(
    model="gemini-3.5-flash",  # cheaper tier is usually enough once retrieval narrows context
    contents=f"Context:\n{retrieved_chunks}\n\nQuestion: What's our refund policy for enterprise plans?",
)
```

## How it's done in production

A typical GCP GenAI stack: **Gemini Flash tiers** for high-volume, latency-sensitive paths (chat, classification), **Gemini Pro** reserved for tasks that genuinely need frontier reasoning or the largest context window, with the **Batch API** for anything that can tolerate a 24-hour SLA and **context caching** for any repeated-large-context pattern (a shared system prompt, a grounding document reused across many calls). **Vector Search** as the dedicated ANN layer for RAG at meaningful scale, or **AlloyDB AI/Spanner vector indexes** when the vector workload can live alongside an existing operational table without justifying a separate system. **ADK** for the agent logic itself, developed and debugged locally via ADK Web, deployed to **Agent Engine** once it needs managed scaling, session persistence, and (if the use case needs cross-session recall) Memory Bank. **A2A** wired in specifically for the subset of workflows that need to hand off between genuinely separate agents, possibly from different vendors or teams — not used as the default communication mechanism between components of a single team's own agent, where a direct function call or ADK's in-process multi-agent composition is simpler and cheaper.

| Symptom | Cause | Fix |
|---|---|---|
| Vertex AI / Gemini Enterprise endpoint bill doesn't drop after a project ends | Model deployed to an endpoint bills per hour regardless of traffic; deployment wasn't explicitly undeployed | Explicitly undeploy the model from the endpoint; audit for orphaned endpoints on a schedule, don't rely on traffic dropping to zero to stop billing |
| Agent's responses ignore something the user said two sessions ago | Conflating Sessions (short-term, per-conversation) with Memory Bank (long-term, cross-session); Memory Bank not enabled or not being written to | Confirm Memory Bank is enabled and the agent is explicitly extracting/storing salient facts, not just relying on Session history that resets per conversation |
| RAG answers cite content that doesn't exist / hallucinated specifics | Vector Search index using brute force on a large dataset without validating ANN recall first, or embeddings stale relative to source documents | Validate ANN (tree-AH) recall against a brute-force ground truth on a sample; confirm index re-sync cadence matches source document update frequency |
| Long-context Gemini calls cost far more than budgeted | Prompts consistently exceeding the 200K-token pricing threshold, triggering the long-context surcharge on every call, with no caching | Chunk and retrieve via RAG instead of stuffing full documents into context where possible; use context caching for any content reused across multiple calls |
| Multi-agent workflow spanning two different vendors' agent platforms fails silently at the handoff | No shared interoperability protocol — one side expects a bespoke API contract the other doesn't implement | Adopt A2A for the specific cross-vendor/cross-team handoff points; keep in-process ADK multi-agent composition for agents built and owned by the same team |
| Team can't find previously-bookmarked Vertex AI console pages after April 2026 | Gemini Enterprise rebrand moved/renamed console navigation; "Vertex AI" no longer a standalone top-level label as of May 21, 2026 | Re-navigate via Gemini Enterprise Agent Platform entry points; underlying APIs/SDKs for Model Registry, training, and Endpoints are unchanged, only the console hierarchy and branding moved |

## Tradeoffs & when NOT to use it

- **Don't default to the largest/most expensive Gemini model for every call.** A narrow, high-volume task (classification, simple extraction, routing) that runs fine on Flash-Lite or Flash costs an order of magnitude more on Pro for no accuracy benefit that matters to the task.
- **Don't stuff large documents directly into a 2M-token context window as a substitute for RAG.** The long-context surcharge above 200K tokens applies per call, every call — for content queried repeatedly, chunked retrieval via Vector Search plus a smaller context window is usually cheaper and often more accurate (less "needle in haystack" degradation) than relying on raw context length.
- **Don't stand up Vector Search for a small, slow-changing embedding set that fits comfortably in AlloyDB AI or Spanner's vector index.** A dedicated ANN service earns its keep at genuine scale (millions-to-billions of vectors, high QPS); below that, running a second billed system alongside an existing operational database is unnecessary complexity.
- **Don't use A2A as the default communication mechanism between agents your own team built and owns.** It's designed for genuine cross-boundary (cross-vendor, cross-team, cross-org) agent handoffs; for in-house multi-agent composition, ADK's native workflow/sub-agent hierarchy is simpler, faster, and doesn't need protocol-level negotiation.
- **Don't assume the Gemini Enterprise rebrand changed underlying billing or API contracts.** It's console/organizational, not a rewrite — but do expect documentation and blog posts from before April 2026 to reference "Vertex AI Agent Builder" by a name that no longer appears in the console, which is a real source of confusion when following older tutorials.
- **Don't pick a platform purely on model quality benchmarks.** All three major clouds now carry near-frontier models from multiple vendors via their model catalogs; the actual differentiator is the surrounding runtime/memory/identity/tool-access architecture and how well it matches the org's existing cloud footprint (Microsoft 365-heavy orgs get real, measurable time-to-value from Foundry's M365 integration that neither AWS nor GCP currently matches).

## Interview questions

### Q1 — Explain what actually changed when Vertex AI Agent Builder became the Gemini Enterprise Agent Platform in April 2026, mechanically, not just the name.
**Testing:** whether the candidate tracks real platform changes versus assuming a rename is purely cosmetic or, conversely, panicking that everything broke.
**Answer:** The rebrand absorbed Vertex AI Agent Builder and Agentspace into one namespace, inverted the console hierarchy so agents are the top-level concept and model training/AutoML/Endpoints are sub-features rather than the primary product, made A2A v1.0 the default interoperability layer, and added Agent Studio (low-code) and an Agent Gateway. Underlying APIs, SDKs, and billing for existing Vertex AI workloads (Model Registry, custom training, Endpoints) are unchanged — this is an organizational/console-level rebrand, not a rewrite. "Vertex AI" stopped appearing as a standalone console label around May 21, 2026.
**Follow-up trap:** *"So does that mean old Vertex AI tutorials and blog posts are now useless?"* — no, the underlying API calls in most of them still work; the trap is that console navigation instructions and some product names in those tutorials are stale, so a candidate should know to verify against current docs for anything console-navigation-specific while trusting API-level code samples more.

### Q2 — A team is deciding between Vector Search and AlloyDB AI's built-in ScaNN index for a RAG system with about 500K document chunks. Walk through the decision.
**Testing:** whether "always use the dedicated vector database" is a reflex or an actual evaluated tradeoff.
**Answer:** 500K vectors is comfortably within range where an operational database's built-in vector index (AlloyDB AI, or Spanner's vector index) can perform well without needing Vector Search's purpose-built, billion-scale ANN architecture. If the same data already needs to live in AlloyDB for transactional reasons, colocating the vector index avoids standing up and paying for a second system (Vector Search bills per-node-hour regardless of traffic, plus endpoint management overhead). Vector Search becomes the better call once scale grows toward millions-to-billions of vectors, or once query QPS requirements exceed what a single operational database instance's vector index can comfortably serve alongside its transactional load.
**Follow-up trap:** *"Wouldn't Vector Search's ScaNN algorithm always give better recall/latency regardless of scale?"* — at genuinely small-to-medium scale, an operational database's vector index can meet accuracy and latency requirements just fine — "always use the more specialized tool" is exactly the kind of reflexive answer that misses the actual tradeoff, which is operational complexity and cost of running a second system, not raw algorithm superiority at every scale.

### Q3 — Distinguish Sessions from Memory Bank in Agent Engine, and describe a concrete bug that results from conflating them.
**Testing:** precise understanding of the two-tier memory model, a common point of confusion for anyone new to agent frameworks.
**Answer:** Sessions persist chronological interaction history within one conversation, giving contextual continuity across requests in that conversation. Memory Bank extracts salient facts across sessions and stores them for cross-session retrieval — it's the long-term-knowledge layer, separate from any one conversation's transcript. A concrete bug: an agent that relies only on Session history "forgets" that a user stated a dietary restriction three conversations ago, because that fact was never extracted into Memory Bank — each new session starts with no knowledge of prior sessions' content unless Memory Bank is explicitly enabled and populated.
**Follow-up trap:** *"Couldn't you just always pass the full history of all past sessions into every new session's context to avoid this?"* — that works only until token/cost limits make it impractical — full session history grows unbounded over a user's lifetime, hits context window limits, and costs more per call (especially above the 200K-token long-context surcharge threshold); Memory Bank's fact-extraction approach exists specifically because raw history replay doesn't scale.

### Q4 — Compare AgentCore's architectural philosophy to ADK's, and explain when each is the better fit.
**Testing:** whether the candidate can articulate the modular-primitives-vs-opinionated-framework tradeoff rather than just naming both.
**Answer:** AgentCore ships Runtime, Memory, Identity, Gateway, and Policy as separately composable services — a team assembles exactly the pieces it needs, which suits organizations wanting fine-grained control (e.g., swapping in a custom identity provider, or using only Gateway without the rest). ADK is a code-first framework with an opinionated agent-definition model (Agent, tools, workflow graph) that deploys as a unit to Agent Engine — faster to get a working multi-agent system running with less integration work, at the cost of less flexibility to swap out individual pieces of the runtime. A team prioritizing fast time-to-a-working-agent with GCP-native data integration (BigQuery, Vector Search) fits ADK better; a team needing fine-grained, independently-swappable primitives for a complex zero-trust/multi-tenant deployment fits AgentCore's model better.
**Follow-up trap:** *"Is one of these objectively more production-ready than the other?"* — both reached comparable enterprise GA milestones in the same Oct 2025-Q1 2026 window; the honest answer avoids declaring an overall winner and instead maps the specific requirement (composability vs. opinionated speed) to the better-fitting architecture.

### Q5 — Why does the Gemini API's long-context pricing surcharge above 200K tokens matter for RAG-vs-long-context architecture decisions?
**Testing:** connecting a specific pricing mechanic to a real design tradeoff, not just reciting the number.
**Answer:** Gemini 3.1 Pro's input price rises from $2.00/1M tokens under 200K to $2.50/1M above that threshold (output similarly rises from $12 to $15/1M) — every call using more than 200K tokens of context pays the higher rate for the entire call, not just the excess. For a workload with large, mostly-static source documents queried repeatedly, chunking and retrieving only the relevant portion via RAG (keeping most calls under 200K tokens) is cheaper per call than relying on the full 2M-token context window every time, in addition to generally better retrieval precision than relying on the model to find the relevant needle in a very long haystack.
**Follow-up trap:** *"Doesn't a 2M-token context window mean RAG is becoming obsolete since you can just fit everything in?"* — technically fitting-everything-in is possible, but it doesn't follow that it's the right default: cost (the long-context surcharge, paid every single call) and retrieval precision (models degrade at finding specific facts buried in very long contexts, an empirically documented effect) both still favor RAG for repeated queries against a large, mostly-static corpus — long context is better suited to genuinely one-off, whole-document reasoning tasks.

### Q6 — Explain the difference between Vector Search's brute-force and tree-AH index types, and when using brute force in production would be a mistake.
**Testing:** the exact-vs-approximate tradeoff and its scale-dependent correctness.
**Answer:** Brute force performs exact linear search against every vector — correct, unconfigurable, and computationally expensive as dataset size grows, appropriate for small datasets or as a ground-truth baseline. Tree-AH is ScaNN's approximate nearest-neighbor index, trading roughly 1% recall for sub-10ms latency even at billion-vector scale. Using brute force in production at meaningful scale is a mistake because query latency scales linearly with dataset size — a system that started fine at 10K vectors becomes unacceptably slow at 10M vectors with no configuration change available to fix it, since brute force has no tunable parameters at all.
**Follow-up trap:** *"If ANN only gives ~99% recall, doesn't that mean it sometimes misses the actually-correct answer, which seems risky for something like a legal or medical RAG system?"* — yes, that's a real and legitimate concern; the correct response is that for genuinely high-stakes retrieval, brute force against a curated, appropriately-small candidate set (e.g., pre-filtered by metadata before the vector search step) can be the right call, and running periodic brute-force validation against ANN results is a reasonable production safeguard, not an argument to abandon ANN everywhere.

### Q7 — A team building a customer-support agent needs it to hand off certain tickets to a specialized fraud-investigation agent built by a completely different team on a different tech stack. Would you reach for A2A here, and why?
**Testing:** correctly scoping A2A's actual use case rather than treating it as a universal agent-communication default.
**Answer:** Yes — this is exactly A2A's target scenario: a genuine cross-boundary handoff between agents built by different teams (possibly different vendors/frameworks entirely), where neither side can assume the other's internal implementation. A2A gives a standard protocol for that handoff (task delegation, status, artifacts) without requiring the two teams to negotiate a bespoke API contract. If both agents were built by the same team using ADK, in-process multi-agent composition within ADK's own workflow model would be simpler and avoid the protocol overhead entirely.
**Follow-up trap:** *"Given A2A has 150+ supporting organizations, should it just be the default way any two agents communicate, even within one team?"* — no; adoption breadth signals the protocol's cross-boundary utility, not that it's the cheapest or simplest choice for in-house, single-team agent composition — reaching for A2A by default inside a single codebase adds protocol-negotiation overhead for no benefit when a direct function call or ADK's native sub-agent hierarchy already solves the problem.

### Q8 — Explain why a Vertex AI / Gemini Enterprise endpoint can keep billing after a project's traffic drops to zero, and how you'd prevent it.
**Testing:** the specific always-on endpoint billing model, a very common real cost incident.
**Answer:** Deploying a model to an endpoint reserves and bills for the underlying serving infrastructure per hour regardless of whether any prediction requests arrive — the charge is for the deployed capacity, not per-request. Traffic dropping to zero doesn't stop the bill; only explicitly undeploying the model from the endpoint does. Prevention: treat endpoint deployment as a resource requiring the same lifecycle discipline as a running VM — track deployed endpoints against active projects, alert on endpoints with zero traffic for N days, and build undeploy into the project's teardown process rather than relying on someone remembering.
**Follow-up trap:** *"Isn't this basically the same cost trap as leaving an EC2 instance running?"* — yes, structurally identical (paying for reserved capacity, not usage), and pointing that out is a strong answer — the difference worth naming is that endpoint costs are less visible in day-to-day workflow than a compute console typically is, since teams often interact with the model via API and forget an underlying deployed resource exists at all.

### Q9 — How would you justify choosing Azure AI Foundry over Gemini Enterprise or Bedrock for a specific customer, and what would make that choice wrong?
**Testing:** honest, requirement-driven platform selection rather than loyalty to one cloud.
**Answer:** Foundry is the strongest choice for an organization whose workflows already run heavily through Microsoft 365 — one-click Teams deployment and native Exchange/SharePoint/Graph integration genuinely compress time-to-value to days rather than months for that specific org shape, which reviewers have flagged as a real, measurable advantage, not marketing. It would be the wrong choice for a GCP-native org with data already concentrated in BigQuery/Spanner (where Gemini Enterprise's tighter data-platform integration wins) or an AWS-native org needing AgentCore's modular zero-trust/multi-tenant primitives.
**Follow-up trap:** *"Doesn't Foundry's OpenAI model access make it the obvious pick regardless of cloud footprint, since OpenAI's models are widely considered strong?"* — model access alone doesn't outweigh integration cost — a GCP-native team adopting Foundry purely for model choice takes on real multi-cloud data-egress and identity-federation overhead that a same-cloud agent platform avoids, and Model Garden/Bedrock both offer near-frontier models too, so the platform decision should weigh integration surface area more heavily than any single model's benchmark scores.

### Q10 — Design a cost-conscious architecture for a high-volume (millions of calls/day) customer-support classification agent using Gemini models, naming every lever you'd pull.
**Testing:** synthesizing pricing mechanics (model tier, batch, caching) into one coherent design, a realistic staff-level ask.
**Answer:** Use Gemini Flash-Lite or Flash (not Pro) for the classification task itself — classification doesn't need frontier reasoning, and the per-token cost gap versus Pro is roughly an order of magnitude. Route anything genuinely ambiguous to a smaller escalation tier using Pro only for the subset that needs it, rather than running every call through the expensive model "just in case." Batch-process anything that can tolerate a 24-hour SLA (e.g., end-of-day reclassification/auditing) via the Batch API for a flat 50% discount. If the same system prompt or a shared knowledge-base excerpt is reused across most calls, enable context caching for that shared portion. Keep per-call context under the 200K-token long-context threshold by retrieving only relevant snippets (Vector Search) rather than stuffing a full knowledge base into every call.
**Follow-up trap:** *"If Flash-Lite is 20x cheaper than Pro per token, why not use it for everything, including the escalation tier?"* — Flash-Lite trades reasoning depth for cost/speed; using it for genuinely ambiguous cases that need deeper reasoning produces more misclassifications, and the downstream cost of wrong classifications (bad customer experience, manual correction work) can exceed the per-token savings — the design has to weigh error cost against token cost per tier, not just minimize token cost in isolation.

### Q11 — A candidate says "Agent2Agent (A2A) and MCP solve the same problem, so you only need one." Correct this.
**Testing:** precision on protocol scope, a specific, frequently-blurred distinction.
**Answer:** They solve different problems at different layers. MCP (Model Context Protocol) standardizes how an agent/model calls external tools and data sources — agent-to-tool communication. A2A standardizes how one agent hands off tasks to, or communicates with, another independent agent — agent-to-agent communication, which is a fundamentally different integration surface (task delegation, status reporting, artifact exchange between peer agents rather than a model calling a function). A real system commonly uses both: an agent uses MCP to call its own tools, and A2A to delegate part of a task to a different agent entirely.
**Follow-up trap:** *"Could you build agent-to-agent handoff using MCP alone, treating the other agent as just another tool?"* — you could crudely wrap another agent's interface as an MCP tool, but that loses A2A's purpose-built semantics for task lifecycle, streaming status updates, and artifact exchange between peer-level agents — it works for the simplest one-shot handoff but breaks down for anything requiring ongoing coordination, which is exactly why A2A exists as a distinct protocol rather than MCP being extended to cover it.

### Q12 — Walk through why a team migrating a LangChain-based agent prototype to ADK and Agent Engine might still choose to keep parts of their original stack, rather than a full rewrite.
**Testing:** realistic migration judgment, not blind platform loyalty.
**Answer:** ADK's stated design is model-agnostic and deployment-agnostic specifically so teams aren't forced into an all-or-nothing migration — a team with working, battle-tested LangChain tool integrations or a custom orchestration layer can often keep those components and adopt ADK/Agent Engine specifically for the pieces that add clear value (managed session/memory persistence, GCP-native scaling) rather than rewriting working code for its own sake. The migration calculus should weigh what Agent Engine's managed runtime actually buys (less operational burden, GA Memory Bank) against the real cost and risk of rewriting and re-validating already-working orchestration logic.
**Follow-up trap:** *"Doesn't keeping a mixed stack forfeit the benefits of a unified, fully-managed platform?"* — partially, yes — a mixed stack won't get Agent Engine's full managed-scaling and observability story for the non-ADK components, and that's a real, explicit tradeoff to name rather than gloss over; the point isn't that mixed stacks are free, it's that a full rewrite isn't automatically justified just because a new platform launched, and the decision should be made on migration cost versus incremental benefit for the specific components in question.
