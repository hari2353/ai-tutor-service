# Working on this repo with two people

A private repo shares exactly like a public one -- collaborators get full access. What
actually breaks parallel work here is not access, it is **~11 MB of generated files that
you will both regenerate**. That is solved, but do the one-time setup in §2 or you will
spend your evenings resolving meaningless conflicts inside a 2.7 MB JSON file.

---

## 1. Give your friend access

```powershell
gh repo add-collaborator <their-github-username> --permission push
```

Or: repo -> Settings -> Collaborators -> Add people. Private repos allow collaborators on
every plan; nothing about sharing changes because the repo is private.

They clone normally:

```powershell
git clone https://github.com/hari2353/ai-tutor-service.git
cd ai-tutor-service
```

## 2. One-time setup, in every clone -- both of you

```powershell
pwsh scripts/setup-collab.ps1      # Windows
bash scripts/setup-collab.sh       # macOS / Linux / Git Bash
```

This registers a merge driver and a hooks path. **It is per-clone.** Git deliberately does
not transmit hooks or merge drivers over the wire -- they execute code, so each clone must
opt in. If a merge ever writes conflict markers into `app/data/*.json`, this step was
skipped.

## 3. Why that setup exists

`app/data/` holds two kinds of file, and the distinction is the whole design:

| | Source of truth | Conflicts without setup |
|---|---|---|
| `app/data/cards/<module-id>.json`<br>`app/data/drillsets/<module-id>.json` | **Yes** -- authored, one file per module | Almost never: different modules are different files |
| `curriculum.json`, `flashcards.json`, `drills.json`, all `.js`, `CONTENT-STATUS.md`, `LEARNING-PATH.md` | **No** -- generated by `build_data.py` | Every single merge |

If you both write modules and both run `build_data.py`, you each produce a different 2.7 MB
`flashcards.json`. Git attempts a line-by-line merge of machine-generated JSON and the
result is unresolvable. Worse, resolving it by hand is pointless: neither side is
authoritative, because the correct content is whatever `build_data.py` produces from the
union of both sets of fragments.

So the driver resolves those files without conflict markers, and the post-merge hook
immediately reruns `build_data.py`, rebuilding them from every fragment on disk. Clean
merge first, correct content second.

**The rule that follows: never hand-edit a generated file.** Edit the fragment, rerun
`build_data.py`.

**One sharp edge.** The fragment merge is *additive*. Removing a card from a fragment does
not remove it from the aggregate -- the old copy persists. If you need to delete or rename
a card, edit the fragment *and* remove it from `app/data/flashcards.json`, or regenerate
from scratch. As of the last commit, aggregate and fragments agree exactly (5,503 cards
each), so any future divergence means someone edited an aggregate directly.

## 4. Claim work before you start

The expensive mistake is both of you writing the same module. There is no lock, so use the
cheapest coordination that works: **claim whole tracks, not individual modules.**

Open one GitHub issue per track you take (`T12 DevOps`, `C-GCP`, ...) and assign yourself.
Comment when done. Two lines of ceremony that prevent a wasted evening.

Before starting anything, re-derive what is genuinely unwritten from disk rather than
trusting any document -- including this one:

```bash
python -c "
import json,glob,pathlib
c=json.load(open('app/data/curriculum.json',encoding='utf-8'))
for t in c['tracks']:
    files={pathlib.Path(p).stem for p in glob.glob(str(pathlib.Path(t['dir'])/'*.md'))}
    un=[m['slug'] for m in t['modules'] if not any(f.endswith(m['slug']) for f in files)]
    if un: print(t['id'], len(un), un)
"
```

## 5. Branch per unit of work

Keep `main` green. Do not commit half a track to it.

```powershell
git checkout main
git pull                          # hook regenerates indexes automatically
git checkout -b track/T12-devops

# ... write modules plus their card and drill fragments ...

python app/build_data.py
python app/tests/review_gate.py   # expect 452 pass / 0 fail
bash app/tests/run.sh

git add -A
git commit -m "T12: docker, k8s objects, k8s networking"
git push -u origin track/T12-devops
```

Then open a PR. Even with two people it gives you a diff worth reading and somewhere to
say "this module's lineage section is thin".

`git add -A` takes roughly 45 seconds on this repo over a Windows filesystem. That is
normal for ~1,900 files, not a hang.

## 6. Before every push

```powershell
python app/build_data.py         # regenerate; merges card and drill fragments
python app/tests/review_gate.py  # house format -- expect 452 pass, 0 fail
bash app/tests/run.sh            # DOM and SM-2 tests
python app/learning_path.py      # refresh LEARNING-PATH.md
```

If the gate fails, **read the failure before changing anything.** It has been wrong more
often than the content has: behavioural modules legitimately substitute a practical
exercise for "build it from scratch", a 40-question SQL bank formatted as `**Qn**` counted
as 3, and T15 boss rounds have no lineage by design. Hence the three profiles in
`review_gate.py`. Sending good work back is worse than not checking.

## 7. Writing modules -- the five rules

Every one was learned by something breaking.

1. **`## The 30-second version` is required**, immediately after the metadata block. The
   spec says write it last, so long sessions drop it or append it at the end.
2. **Lineage labels exactly** `**What came before.**` / `**Where it stands now.**` /
   `**Where it's heading.**`, bold containing only the label. A single stray space inside
   the bold failed a module whose content was fine.
3. **10+ interview questions, each with a `**Follow-up trap:**`.** 27 modules landed at
   5-9 and needed a separate repair pass. Cheaper to count as you write.
4. **One module at a time** -- module, then cards, then drills, then the next. Sessions get
   interrupted; this way what survives is complete rather than half-written.
5. **Fragments only.** Write `app/data/cards/<id>.json` and `app/data/drillsets/<id>.json`.
   Never the aggregates, never the `.js`, and never run `build_data.py` while someone else
   is mid-write.

`templates/MODULE-SPEC.md` is the full format.
`curriculum/21-architecture-principles/06-resilience-catalogue.md` and
`curriculum/04-deep-learning/02-backprop-derivation.md` are the quality bar.

## 9. Do not commit

`.gitignore` covers `interview_prep_queue.json` (live job listings), `__pycache__/`,
`.venv/`, `node_modules/` and OS droppings.

**first** -- rewriting history afterwards is far harder than not committing it.
