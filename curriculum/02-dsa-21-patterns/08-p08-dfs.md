# Tree/Graph DFS

> **Track:** T02 DSA: 21 Patterns · **Time:** 2h · **Prereqs:** T02-p07-bfs · **Updated:** 2026-07-27
> **Module id:** `T02-p08-dfs` · **Tags:** pattern, graphs, trees, recursion

## The 30-second version

Depth-First Search explores as far as possible along one branch before backtracking, and it comes in two equally important forms: recursive, where the language's own call stack does the bookkeeping implicitly, and iterative, where you maintain an explicit stack on the heap yourself. Recursive DFS is more natural for tree problems and is the default choice, but recursion depth equals the path length to the deepest node being explored, and that's a real liability, not a theoretical one — a skewed or pathologically deep input (a near-linear tree, a deeply nested JSON/expression tree from untrusted input) can exceed a runtime's call-stack limit (Python's default recursion limit is 1,000 frames; a JVM or Go goroutine's stack, while more elastic, still has a hard ceiling) and crash with a stack overflow, which is a real denial-of-service vector against recursive parsers. The iterative form trades that fixed, small call-stack budget for heap memory, which is typically orders of magnitude larger and configurable, at the cost of managing the traversal state (and especially postorder) by hand. Recognize DFS from "all root-to-leaf paths," "connected component," "cycle detection," "topological order," or any exhaustive path/combination exploration — and reach for the iterative form specifically whenever input depth is attacker-controlled or simply unbounded.

## Why this gets asked

The interviewer wants two things confirmed: that recursion is genuinely second nature for tree/graph problems (not memorized template code), and that you know exactly when recursion becomes a liability rather than a convenience. This maps directly to a real production failure class: recursive descent parsers (JSON, XML, arithmetic expressions, user-submitted rule trees) that crash on deeply nested but otherwise valid-looking input are a well-known reliability and security issue — attackers can construct a payload nested a few thousand levels deep specifically to exhaust the call stack and take down a service, and the fix is either an iterative rewrite or an explicit depth limit. The sharper follow-up that separates levels is directed-cycle detection (Course Schedule) because it requires distinguishing "visited in this DFS branch, still on the call stack" from "fully processed and safe" — collapsing these into one visited set produces false-positive cycle detection on perfectly valid DAGs with diamond-shaped dependencies, which is exactly the kind of subtle correctness bug interviewers use DFS cycle detection to surface.

## Lineage: past → present → future

**What came before.** Depth-first traversal predates computing: Trémaux's algorithm for maze-solving (attributed to Charles Pierre Trémaux, 19th century, described by Gaston Tarry and referenced in Wiener's 1873 maze-solving work) is recognizably DFS with backtracking. In computer science, John Hopcroft and Robert Tarjan's 1973 paper "Efficient Algorithms for Graph Manipulation" formalized DFS as the basis for linear-time connectivity, biconnected-components, and (with Tarjan's later work) strongly-connected-components algorithms, establishing DFS's O(V+E) traversal as foundational graph-algorithm infrastructure rather than just a tree-walking convenience. Before that formalization, ad hoc traversal code often didn't correctly track visited state on general graphs, leading to infinite loops on any input with a cycle.

**Where it stands now.** Recursive DFS is the default, idiomatic choice for tree problems in essentially every language, because it mirrors the tree's own recursive structure and requires no manual stack management. The live, load-bearing distinction in practice is when to convert to iterative: production parsers, compilers, and any code processing externally-supplied nested structures increasingly default to iterative DFS (or bound recursion depth explicitly and reject inputs beyond it) specifically because stack-overflow-via-deep-nesting is a known, exploitable reliability issue — it has appeared as a real vulnerability class in JSON/YAML/XML parsers across multiple ecosystems. For cycle detection specifically, the three-state (white/gray/black, or unvisited/in-progress/done) DFS technique remains the standard answer for directed graphs, while undirected-graph cycle detection is simpler (a single visited set suffices, since you only need to detect revisiting a non-parent neighbor) and is a frequently-tested distinction in its own right.

**Where it's heading.** As more production code parses arbitrary nested structures generated by other systems or by LLMs (deeply nested tool-call arguments, generated ASTs, recursive agent plans), expect "convert this recursive traversal to iterative, and explain exactly why" to keep showing up as a security-adjacent interview question rather than a purely academic one — this is a moderate-to-high confidence prediction given how consistently stack-exhaustion-via-nesting shows up as a real CVE class. The core DFS algorithm itself is closed and unlikely to change; what's shifting is how seriously the recursion-depth tradeoff is weighted in the interview.

## Mental model

```
Recursive DFS (preorder) on:

        A
       / \
      B   C
     /     \
    D       E

call stack grows as we descend, unwinds as we return:

dfs(A) -> dfs(B) -> dfs(D) -> D has no children, return
              <- back in dfs(B), no more children, return
       <- back in dfs(A), visit C
       dfs(A) -> dfs(C) -> dfs(E) -> E has no children, return
                     <- back in dfs(C), return
              <- back in dfs(A), done

visit order: A, B, D, C, E     (preorder: root, then left subtree, then right subtree)

max call-stack depth reached = 3 (A -> B -> D), i.e. the tree's height, not its node count.
```

Iterative DFS with an explicit stack (same preorder, no recursion):

```
stack: [A]
pop A, visit A, push children in REVERSE order so left is processed first: push C, push B
stack: [C, B]
pop B, visit B, push D
stack: [C, D]
pop D, visit D, no children
stack: [C]
pop C, visit C, push E
stack: [E]
pop E, visit E, no children
stack: []  -- done, same order: A, B, D, C, E
```

The key structural fact: **recursion depth equals path depth, not total node count.** A perfectly balanced tree of a million nodes recurses only ~20 levels deep (log2(1,000,000) ≈ 20); a degenerate, linked-list-shaped tree of the same million nodes recurses a million levels deep — and that's the case that blows the call stack.

## Recognition heuristics

- **"All root-to-leaf paths," "any path from X to Y," "path sum," "does a path exist with property Z"** — DFS with backtracking (build up a path list as you descend, undo the last addition as you return up each level).
- **Traversal order matters semantically** — inorder DFS on a BST yields sorted order; postorder DFS is required whenever you need a node's own computation to depend on its children's results first (subtree height, subtree sum, safe deletion order, dependency resolution).
- **"Connected components," "does a path exist" (not shortest), "flood fill," "number of islands"** — DFS and BFS are both correct and equally efficient here; either works, since only reachability matters, not distance.
- **"Detect a cycle"** — in an *undirected* graph, a single visited set suffices (revisiting any already-visited node that isn't your immediate parent means a cycle); in a *directed* graph, you need three states (unvisited / currently-on-the-recursion-stack / fully-done) because revisiting a node that's already fully processed via a different path is completely normal in a DAG and is not a cycle — only revisiting a node still on the *current* call stack indicates one.
- **"Topological order" via DFS** — run DFS to completion, recording each node in a postorder list as it finishes (all its descendants already recorded); reverse that postorder list to get a valid topological order. Contrast with Kahn's algorithm, the BFS-based alternative that tracks in-degrees directly (see `T02-p17-topological-sort`).
- **Exhaustive generation of subsets/permutations/combinations** — this is the backtracking pattern's traversal skeleton (see `T02-p10-subsets` and `T02-p21-backtracking`), built directly on top of DFS.
- **Deeply nested or adversarial-depth input** (long chains, untrusted nested documents) — recursion depth becomes a real risk; prefer iterative DFS with an explicit heap-allocated stack, or impose and enforce an explicit maximum depth.

**Anti-signal:** if the question specifically asks for shortest path or minimum steps on an unweighted graph, DFS is the wrong default — use BFS (`T02-p07-bfs`), since DFS's first-discovery path is not guaranteed shortest.

## Template code (Python, Java, Go)

Both forms — recursive preorder and iterative preorder with an explicit stack — since knowing when and how to convert between them is the point of this module:

**Python**
```python
class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val, self.left, self.right = val, left, right

def dfs_recursive(root: TreeNode | None, out: list[int]) -> None:
    """Preorder DFS, recursive. Stack depth = tree height."""
    if root is None:
        return
    out.append(root.val)
    dfs_recursive(root.left, out)
    dfs_recursive(root.right, out)

def dfs_iterative(root: TreeNode | None) -> list[int]:
    """Preorder DFS, iterative with an explicit heap-allocated stack.
    Use this when input depth is unbounded or attacker-controlled."""
    if root is None:
        return []
    out = []
    stack = [root]
    while stack:
        node = stack.pop()
        out.append(node.val)
        if node.right:      # push right FIRST so left is popped and processed first
            stack.append(node.right)
        if node.left:
            stack.append(node.left)
    return out
```

**Java**
```java
public void dfsRecursive(TreeNode root, List<Integer> out) {
    if (root == null) return;
    out.add(root.val);
    dfsRecursive(root.left, out);
    dfsRecursive(root.right, out);
}

public List<Integer> dfsIterative(TreeNode root) {
    List<Integer> out = new ArrayList<>();
    if (root == null) return out;
    Deque<TreeNode> stack = new ArrayDeque<>();
    stack.push(root);
    while (!stack.isEmpty()) {
        TreeNode node = stack.pop();
        out.add(node.val);
        if (node.right != null) stack.push(node.right);  // push right first
        if (node.left != null) stack.push(node.left);
    }
    return out;
}
```

**Go**
```go
func dfsRecursive(root *TreeNode, out *[]int) {
	if root == nil {
		return
	}
	*out = append(*out, root.Val)
	dfsRecursive(root.Left, out)
	dfsRecursive(root.Right, out)
}

func dfsIterative(root *TreeNode) []int {
	var out []int
	if root == nil {
		return out
	}
	stack := []*TreeNode{root}
	for len(stack) > 0 {
		node := stack[len(stack)-1]
		stack = stack[:len(stack)-1]
		out = append(out, node.Val)
		if node.Right != nil {
			stack = append(stack, node.Right) // push right first
		}
		if node.Left != nil {
			stack = append(stack, node.Left)
		}
	}
	return out
}
```

## Complexity, derived

Every node is visited exactly once and every edge examined exactly once (with a visited set on general graphs to prevent revisiting via cycles), so DFS is **O(V + E) time**, identical to BFS. The space story is where the two implementation forms genuinely diverge, and it's worth deriving precisely rather than asserting it: both recursive and a correctly-implemented iterative DFS use auxiliary space proportional to **O(H)**, where `H` is the height of the tree (or, for a general graph, the length of the longest simple path DFS descends before backtracking) — not `O(V)` in general, because at any instant only one root-to-current-node path's worth of frontier is "in flight" (on the call stack, or in the explicit stack, when you push only one branch's remaining children per level rather than an entire level's siblings, unlike BFS's O(V) queue). For a balanced binary tree, `H = O(log n)`; for a completely skewed tree (effectively a linked list), `H = O(n)`. The critical distinction is *not* asymptotic space complexity — both forms are `O(H)` — it is **which memory pool that O(H) lives in**: the recursive form consumes call-stack memory, a fixed, comparatively small resource per thread (roughly 1MB to 8MB by default depending on OS/runtime, translating to a hard ceiling in the thousands to low tens-of-thousands of frames before a stack overflow, and explicitly ~1,000 frames by default in Python regardless of available RAM), while the iterative form consumes heap memory, which is typically far larger and can grow until the process runs out of RAM. Converting recursive to iterative doesn't change the Big-O space bound; it changes which physical resource limit you hit first.

## The 5 variants interviewers actually ask

1. **Binary Tree Traversals — preorder, inorder, postorder (LC144, LC94, LC145).** The foundational forms; postorder is the notoriously fiddly one to implement iteratively (a single stack alone doesn't naturally produce postorder order — the common tricks are a two-stack approach, producing a reversed "root-right-left" sequence and reversing it to get "left-right-root," or a state-marking approach tracking whether a node's children have already been pushed).
2. **Path Sum II — all root-to-leaf paths summing to a target (LC113).** DFS with backtracking: append the current node to a shared path list on the way down, check the sum condition at leaves, and — critically — pop the current node back off the path list on the way back up before returning to the parent, so sibling branches don't inherit a stale path.
3. **Number of Islands / Max Area of Island (LC200 / LC695).** DFS flood-fill from every unvisited land cell, marking visited cells (in-place, by mutating the grid to a sentinel value, or via a separate visited set) to avoid reprocessing; on very large grids, recursion depth can equal the size of a single connected component, making the iterative form the safer production choice.
4. **Course Schedule — cycle detection in a directed graph (LC207).** Three-state DFS: unvisited, currently on the active recursion path ("gray"), and fully processed ("black"). A cycle exists if and only if DFS ever encounters a gray node — encountering a black node (fully processed via a different earlier path) is normal in a DAG and is not a cycle.
5. **Clone Graph (LC133).** DFS (or BFS) over a general graph with a visited map from original node to its clone, used both to avoid infinite recursion on cycles and to correctly wire up shared neighbor references without duplicating already-cloned nodes.

## Common bugs

- **Missing a visited set on a general graph (not a tree).** Trees have no cycles, so naive recursive DFS never infinite-loops on one; graphs can have cycles, and without tracking visited nodes, DFS recurses forever (or until the stack overflows) the moment it revisits a node it's already processing.
- **Collapsing "currently in progress" and "fully done" into a single visited flag for directed-cycle detection.** This produces false-positive cycle reports on valid DAGs with diamond dependencies (`A -> B -> D`, `A -> C -> D`): `D` gets visited twice via two different valid paths, and a single-state visited check incorrectly flags the second visit as a cycle. The three-state (white/gray/black) distinction exists specifically to avoid this.
- **Forgetting to undo (pop) a shared mutable path/state structure when backtracking out of a DFS branch.** In Path Sum II or Word Search, appending to a shared list on the way down but not removing that entry on the way back up leaks state into sibling branches, producing paths that don't actually exist in the tree/grid.
- **Recursion depth exceeding the runtime's stack limit on adversarially deep or simply very large skewed input.** This is a real production failure mode (`RecursionError` in Python past its default 1,000-frame limit, `StackOverflowError` in Java, similar failures in Go for sufficiently deep unbounded recursion), not just an interview nitpick — deeply nested JSON/XML/expression parsers hitting this on untrusted input is a documented denial-of-service pattern.
- **Getting child-push order backward in iterative preorder DFS.** Pushing left before right onto a stack causes right to be popped and processed first, producing the mirror-wrong traversal order; push right first so left ends up on top and is processed first.
- **Implementing iterative postorder by intuition instead of via the known trick.** Postorder is "left, right, root" — the reliable shortcut is to do an iterative "root, right, left" traversal (preorder with push order swapped) and reverse the output at the end, since reversing "root, right, left" yields exactly "left, right, root."

## Interview questions

### Q1 — Binary Tree Inorder Traversal (LC94)
**Testing:** the base recursive form, and whether you can produce the iterative equivalent on demand.
**Answer:** Recursive: left, visit, right. Iterative: push nodes while descending left, pop and visit when you hit a null left child, then descend right from the popped node.
**Follow-up trap:** *"Do it with O(1) auxiliary space."* — Morris Traversal: temporarily rewire null right-child pointers to point back to the inorder successor (threading), traverse using those temporary links, then restore the tree's original structure afterward; this eliminates both the call stack and any explicit stack, at the cost of transiently mutating the tree during the traversal.

### Q2 — Binary Tree Postorder Traversal (LC145)
**Testing:** the specific implementation difficulty of iterative postorder.
**Answer:** Easiest approach: do an iterative "root, right, left" traversal (preorder with child-push order swapped) and reverse the resulting list at the end to get "left, right, root."
**Follow-up trap:** *"Do it without reversing anything, using a single stack and O(H) space."* — track a `last_visited` pointer; when you'd normally visit a node, first check whether its right child exists and hasn't been visited yet — if so, push the node back and descend right first; this simulates postorder directly at the cost of noticeably fiddlier bookkeeping than the reverse-preorder trick.

### Q3 — Path Sum II (LC113)
**Testing:** the backtracking undo discipline that most DFS-with-shared-state bugs violate.
**Answer:** DFS, appending the current node's value to a shared path list on the way down; at a leaf, check if the running sum matches the target and record a copy of the path if so; pop the current node off the path list before returning to the parent.
**Follow-up trap:** *"Why record a copy of the path, not the path list itself, when you find a match?"* — the path list is mutated (appended and popped) throughout the rest of the traversal after this leaf returns; storing a reference to the live list instead of a snapshot means every recorded "path" ends up reflecting whatever the list looks like at the very end of the entire traversal, not what it looked like at the moment of the match.

### Q4 — Number of Islands (LC200)
**Testing:** whether you recognize recursion-depth risk on large, real-world-sized grids.
**Answer:** DFS (or BFS) flood-fill from each unvisited land cell, marking visited cells in place; count flood-fill starts.
**Follow-up trap:** *"The grid is 10,000 x 10,000 and could contain a single snake-shaped island covering most of it — is your recursive solution safe?"* — no; a single connected component that size can recurse on the order of 10^7-10^8 calls along a winding path, far past any default call-stack limit, and must be converted to iterative DFS (or BFS) with an explicit, heap-allocated stack/queue to avoid a stack overflow in production.

### Q5 — Course Schedule (LC207)
**Testing:** the three-state cycle-detection technique for directed graphs, and whether a candidate defaults to (incorrectly) a single visited set.
**Answer:** DFS with three states per node — unvisited, in-progress (on the current recursion path), done; a cycle exists iff DFS ever revisits an in-progress node. A cycle means the course prerequisites are unsatisfiable.
**Follow-up trap:** *"Why not just use a single boolean visited array?"* — a single visited flag can't distinguish "this node is an ancestor of the current node on the call stack" (a genuine cycle) from "this node was already fully explored via an earlier, unrelated branch" (completely normal in a DAG with shared dependencies) — collapsing the two produces false positives on valid, cycle-free dependency graphs.

### Q6 — Course Schedule II (LC210) — produce a valid ordering, not just detect a cycle
**Testing:** connecting cycle-detection DFS to topological sort.
**Answer:** Run the same three-state DFS; whenever a node finishes (transitions to "done"), append it to a postorder list; if no cycle was found, reverse that postorder list for a valid topological ordering.
**Follow-up trap:** *"Compare this to Kahn's algorithm — when would you prefer one over the other?"* — Kahn's algorithm (BFS-based, repeatedly removing zero-in-degree nodes) naturally detects a cycle by simply not managing to process all nodes, without needing explicit state-coloring, and it's often considered more intuitive to trace by hand; DFS-postorder is often less code once you already have DFS infrastructure in place. Both are O(V+E); the choice is largely about which mental model and existing code you're building on (see `T02-p17-topological-sort` for the Kahn's-side depth).

### Q7 — Clone Graph (LC133)
**Testing:** DFS on a general graph (with cycles) requiring a visited map, not just a visited set.
**Answer:** DFS (or BFS) maintaining a map from original node to its already-created clone; when visiting a neighbor, check the map first — if the clone already exists, reuse it (this is what correctly handles cycles and shared references without infinite recursion or duplicate clones).
**Follow-up trap:** *"What breaks if you use a plain visited set instead of a visited-to-clone map?"* — a plain set tells you *whether* you've seen a node, but not *which clone object* corresponds to it, so you'd either re-clone the same original node multiple times (breaking the "same object, same clone" invariant the problem requires) or have no way to correctly wire up a neighbor reference to the one true corresponding clone.

### Q8 — Validate Binary Search Tree (LC98)
**Testing:** whether you reach for inorder DFS's sorted-output property, versus the more error-prone bounds-passing recursion.
**Answer:** Inorder DFS should produce strictly increasing values for a valid BST; track the previously visited value and compare at each step, failing immediately on any non-increasing pair.
**Follow-up trap:** *"Why is checking 'each node's value is between its immediate parent's bounds' insufficient?"* — a BST's constraint is global to every ancestor, not just the immediate parent: a node deep in the left subtree must be less than *every* ancestor's value on the path back to the root, not merely its direct parent, so a correct bounds-passing recursive solution must thread an evolving `(low, high)` range down through the recursion, updated at each level, rather than comparing only to the immediate parent.

### Q9 — Convert a recursive DFS JSON-tree validator to iterative for untrusted input
**Testing:** the recursion-depth-as-liability half of this module directly.
**Answer:** Replace the recursive descent with an explicit stack holding "work items" (node plus any partial state needed to resume processing it), popping and processing one at a time; this moves the traversal's memory footprint from the call stack (small, fixed) to the heap (large, configurable), removing the stack-overflow risk from adversarially deep nesting.
**Follow-up trap:** *"Does converting to iterative make this problem's memory complexity any better, in Big-O terms?"* — no; both forms remain O(H) auxiliary space where H is the maximum nesting depth. The win isn't an asymptotic improvement, it's moving that O(H) footprint out of a small, fixed-size resource (the call stack, whose overflow crashes the process/thread) into a large, elastic one (the heap, whose exhaustion is a much higher and more controllable bar) — say this precisely rather than claiming iterative is "more efficient."

### Q10 — Diameter of Binary Tree (LC543)
**Testing:** a postorder DFS that computes two things in one pass instead of two separate traversals.
**Answer:** Postorder DFS computing each subtree's height; at each node, update a global/nonlocal "best diameter" using `left_height + right_height` (the longest path passing through this node), while still returning `1 + max(left_height, right_height)` upward for the parent's own height computation. Single O(n) pass.
**Follow-up trap:** *"A naive solution computes height as a separate recursive call at every node — what's its complexity, and why is that worse?"* — that's O(n^2) in the worst case (a skewed tree), since computing height at each of the n nodes independently costs up to O(n) itself; folding the height computation and the diameter update into the same single postorder pass drops it to O(n) total.

### Q11 — Symmetric Tree (LC101)
**Testing:** DFS that walks two subtrees in mirrored lockstep rather than a single tree independently.
**Answer:** A helper DFS taking two node arguments (initially the left and right children of the root); it returns true if both are null, false if exactly one is null or their values differ, and otherwise recurses on `(left.left, right.right)` and `(left.right, right.left)` — the mirrored pairing, not the same-side pairing.
**Follow-up trap:** *"What if you recursed on `(left.left, right.left)` and `(left.right, right.right)` instead?"* — that checks whether the two subtrees are identical, not mirror images of each other; symmetry specifically requires comparing each side against its *mirrored* counterpart, and using the same-side pairing silently checks the wrong property, passing on trees that aren't actually symmetric under any interesting definition.

### Q12 — Word Search (LC79)
**Testing:** DFS/backtracking on a grid with in-place visited marking and mandatory undo.
**Answer:** DFS from every cell matching the first character, backtracking through adjacent cells matching subsequent characters; mark the current cell visited by temporarily overwriting it with a sentinel character (avoiding a separate O(rows*cols) visited array), and restore the original character before returning up, so sibling search branches see the grid in its original state.
**Follow-up trap:** *"What happens if you forget to restore the sentinel-overwritten cell before backtracking?"* — the cell remains permanently marked as "used" even for search branches that never actually used it in their path, incorrectly blocking valid words that should have been found via a different path through that same cell — a direct instance of the general "forgot to undo shared mutable state on backtrack" bug class.

## Red flags that fail you

- Missing a visited set on a general graph, causing infinite recursion or an infinite loop on any cyclic input.
- Using a single visited flag for directed-cycle detection instead of three states, producing false-positive cycles on valid DAGs.
- Forgetting to pop/undo shared mutable state (a path list, a grid's sentinel marking) when backtracking out of a DFS branch.
- Claiming a recursive solution is "fine" for arbitrarily deep or untrusted input without acknowledging the call-stack-overflow risk.
- Getting child-push order backward in iterative preorder DFS, silently producing the wrong traversal order.
- Confusing "convert to iterative" with "reduces asymptotic space complexity" — both forms are O(H); only the memory pool changes.

## Cheat card

```
CORE IDEA       explore one branch fully before backtracking; two implementations, same result
RECURSIVE       call stack does bookkeeping implicitly; natural for trees; depth = path length
ITERATIVE       explicit heap-allocated stack; needed when depth is unbounded/attacker-controlled
CHILD ORDER     iterative preorder: push RIGHT child first so LEFT is popped/processed first
COMPLEXITY      O(V+E) time both forms; O(H) space both forms (H = height/longest path, NOT node count)
RECURSION RISK  Python default limit ~1000 frames; JVM/Go stack has a fixed ceiling too
                skewed/degenerate input -> O(H)=O(n) depth -> real stack-overflow risk in production
NOT ASYMPTOTIC  converting recursive->iterative does NOT change Big-O space; it moves O(H) from
                call stack (small, fixed) to heap (large, elastic) -- say this precisely
UNDIRECTED CYCLE single visited set: revisiting any non-parent visited node = cycle
DIRECTED CYCLE  3 states (unvisited/in-progress/done): revisiting an IN-PROGRESS node = cycle;
                revisiting a DONE node via a different path is normal in a DAG, not a cycle
TOPO SORT (DFS) postorder list, then REVERSE it -- contrast with Kahn's BFS-based in-degree method
BACKTRACK UNDO  pop path list / restore sentinel-marked cell before returning up -- or state leaks
POSTORDER TRICK iterative: do "root, right, left" (preorder with swapped push order), then reverse it
```
