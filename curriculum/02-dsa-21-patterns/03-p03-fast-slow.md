# Fast & Slow Pointers

> **Track:** T02 DSA: 21 Patterns · **Time:** 1.5h · **Prereqs:** T02-p01-two-pointers · **Updated:** 2026-07-26
> **Module id:** `T02-p03-fast-slow` · **Tags:** pattern, linked-list

## The 30-second version

Fast & Slow Pointers (Floyd's tortoise and hare) walks two pointers through a linked structure at different speeds — typically slow advances one node, fast advances two — to answer questions about structure (does a cycle exist, where is the middle, where does a cycle begin) in O(n) time and O(1) space, without a hash set of visited nodes. The core guarantee is: if a cycle exists, fast necessarily laps slow and they meet inside it, because the gap between them shrinks by exactly one node per step once both are in the cycle; if no cycle exists, fast simply reaches the end first. Recognize it from "linked list," "detect a cycle," "find the middle," or from a disguised linked-list — an array where each value points to another index, or a function whose repeated application either cycles or terminates (Happy Number). It's the space-optimal answer whenever the hash-set alternative would cost O(n) extra memory.

## Why this gets asked

The interviewer wants to know whether you can solve "detect a cycle" without reaching for a hash set of visited nodes as the only tool you know — the hash-set approach is correct and easy to derive, but it costs O(n) space, and the interviewer has almost certainly hit exactly this tradeoff for real: iterating a linked data structure (a job queue, a dependency graph represented as next-pointers, a circular buffer) where allocating a visited-set per traversal was the actual production cost that got optimized away. The deeper test is whether you can *prove* Floyd's algorithm works rather than pattern-match the code from memory — specifically, deriving why the two-pointer gap closes at a rate of exactly one node per iteration once inside the cycle, and the modular arithmetic behind why moving one pointer back to the head after the first meeting finds the cycle's start. Candidates who've memorized the code but can't reproduce the proof get exposed immediately by a "why does resetting to head work?" follow-up.

## Lineage: past → present → future

**What came before.** The straightforward way to detect whether you've revisited a node in a traversal is to keep a hash set of every visited node and check membership at each step — O(n) time, O(n) space. This is still the first correct answer most engineers reach for, and it's not wrong; it's simply not space-optimal. Robert Floyd is credited with the cycle-detection two-pointer technique (commonly called "Floyd's cycle-finding algorithm" or "the tortoise and hare"), described informally in the 1960s, though the earliest clean written attribution is often traced to Donald Knuth's *The Art of Computer Programming* exercises, which credit Floyd. The specific problem this solved in practice — detecting a cycle in a sequence generated by repeated application of a function, without unbounded memory — mattered for pseudorandom number generator period-finding and other iterative processes well before it became a linked-list interview staple.

**Where it stands now.** Universally expected as a linked-list fundamental at any interview level; there is no meaningful disagreement about the algorithm itself. The interesting split in practice is between candidates who can *apply* the two-speed trick mechanically (detect a cycle, find a middle) and those who can *transfer* it to non-linked-list structures presented as disguised sequences — Happy Number (repeated digit-square-sum as an implicit "next" function), Find the Duplicate Number (treating array values as pointers into the same array), Circular Array Loop. This transfer is exactly what separates a "I memorized this pattern" answer from a "I understand what makes this technique general" answer, and interviewers lean on it deliberately.

**Where it's heading.** Because Floyd's algorithm is short, self-contained, and has a non-obvious correctness proof, it is one of the more natural candidates for "explain why this works" or "here's cycle-detection code with the reset-to-head step removed, is it still correct" debugging-and-reasoning prompts as interview formats shift toward evaluating understanding over recall in the AI-assisted-interview era. There is little room for this pattern itself to evolve — it is a closed, decades-old result — so the direction of travel is entirely in *how it's tested*, not in the technique changing.

## Mental model

Cycle detection: fast moves 2 steps for every 1 slow moves; if a cycle exists they must meet inside it.

```
head -> A -> B -> C -> D -> E
                  ^         |
                  |_________|   (E points back to C: cycle starts at C)

step 0: slow=A         fast=A
step 1: slow=B         fast=C
step 2: slow=C         fast=E
step 3: slow=D         fast=D    <- MEET (both land on D)

Once both pointers are inside the cycle, the gap between them shrinks by
exactly 1 node every step (fast gains 2, slow gains 1, net -1 per step),
so a finite cycle guarantees they meet -- fast can't "jump over" slow
because the gap closes one node at a time, never skips past zero.
```

Finding the cycle start after the first meeting (the part people can recite but rarely prove):

```
distance from head to cycle start:        a
distance from cycle start to meeting pt:  b
remaining loop length back to start:      c      (cycle length = b + c)

When they meet: slow has traveled a + b
                 fast has traveled a + b + k*(b + c)  for some integer k >= 1
                 fast traveled exactly 2x what slow traveled (2 steps per 1):
                       2(a + b) = a + b + k(b + c)
                   =>       a + b = k(b + c)
                   =>            a = k(b + c) - b = (k-1)(b+c) + c

So walking 'a' steps from head is the same, modulo the cycle length (b+c),
as walking 'c' steps from the meeting point -- i.e. reset one pointer to
head, advance both one step at a time, they meet exactly at the cycle start.
```

## Recognition heuristics

- **"Linked list" + "cycle" / "loop"** — the single strongest signal. Any variant of "does this list have a cycle" or "where does the cycle begin" is this pattern by name.
- **"Find the middle of a linked list" without a separately tracked length or a second pass** — fast/slow gets you there in one pass; slow lands on the middle exactly when fast reaches the end.
- **A function that repeatedly transforms a number/state and you need to know if it eventually cycles or reaches a terminal value** (Happy Number: repeated sum-of-squared-digits either reaches 1 or enters a cycle) — treat "apply f repeatedly" as an implicit linked list where `next = f(current)`.
- **An array where `nums[i]` is used as an index into the same array**, and you're asked to find a duplicate or a cycle — this is a linked list in disguise: `next(i) = nums[i]`.
- **"Palindrome linked list"** — find the middle (fast/slow), reverse the second half, compare — a composition of this pattern with linked-list reversal.
- **You'd otherwise use a hash set to track "have I seen this node/state before" on a structure with a natural "next" step, and space is a stated constraint (O(1) extra space)** — fast/slow replaces the hash set.

**Anti-signal:** if you need to know *which* nodes were visited (not just *whether* a cycle exists or where the middle is), a visited-set is often still necessary — fast/slow tells you existence and location of specific landmarks (start, middle) cheaply, not full traversal history.

## Template code (Python, Java, Go)

Cycle detection plus finding the cycle's start node — the reusable skeleton:

**Python**
```python
class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

def detect_cycle_start(head: ListNode | None) -> ListNode | None:
    """Return the node where the cycle begins, or None if there's no cycle."""
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:
            break
    else:
        return None                 # fast ran off the end -> no cycle

    slow = head                     # reset one pointer to head
    while slow is not fast:         # both now advance one step at a time
        slow = slow.next
        fast = fast.next
    return slow                     # meeting point == cycle start
```

**Java**
```java
public ListNode detectCycleStart(ListNode head) {
    ListNode slow = head, fast = head;
    boolean hasCycle = false;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) {
            hasCycle = true;
            break;
        }
    }
    if (!hasCycle) return null;

    slow = head;
    while (slow != fast) {
        slow = slow.next;
        fast = fast.next;
    }
    return slow;
}
```

**Go**
```go
type ListNode struct {
	Val  int
	Next *ListNode
}

func detectCycleStart(head *ListNode) *ListNode {
	slow, fast := head, head
	hasCycle := false
	for fast != nil && fast.Next != nil {
		slow = slow.Next
		fast = fast.Next.Next
		if slow == fast {
			hasCycle = true
			break
		}
	}
	if !hasCycle {
		return nil
	}
	slow = head
	for slow != fast {
		slow = slow.Next
		fast = fast.Next
	}
	return slow
}
```

## Complexity, derived

Phase 1 (meeting detection): fast moves 2 nodes per iteration, slow moves 1. If there's no cycle, fast reaches `nil`/`None` within `n/2` iterations, so the loop terminates in at most `O(n)` steps. If there's a cycle, once both pointers are inside it the gap between them decreases by exactly one node per iteration (fast gains 2 positions, slow gains 1, net closure rate 1), and the gap is at most the cycle length `c <= n`, so they meet within at most `c` further iterations — bounded by `O(n)` overall. Phase 2 (finding the start): the algebra above shows the head-to-start distance `a` and the meeting-point-to-start distance `c` are congruent modulo the cycle length, so advancing both pointers one step at a time takes at most `O(n)` more steps. Total: **O(n) time, O(1) space** — versus O(n) time *and* O(n) space for the hash-set alternative.

## The 5 variants interviewers actually ask

1. **Cycle detection (boolean only).** Modification: drop the second phase entirely; return `True`/`False` the moment `slow is fast`, or `False` if fast exhausts the list.
2. **Finding the middle of a linked list.** Modification: no cycle logic at all; loop `while fast and fast.next`, advancing both; `slow` lands on the middle (the second of two middles for even-length lists) when the loop ends.
3. **Happy Number.** Modification: there's no explicit linked list — `next(x) = sum of squares of x's digits`; run slow/fast over this implicit sequence; a cycle not containing 1 means "not happy," reaching 1 means "happy" (1 maps to itself, a trivial one-node cycle).
4. **Palindrome Linked List.** Modification: find the middle (variant 2), reverse the second half in place (composing with the linked-list-reversal pattern), then walk two pointers from both ends comparing values; optionally re-reverse to restore the list.
5. **Find the Duplicate Number.** Modification: treat the array itself as an implicit linked list via `next(i) = nums[i]`; because there are `n+1` values in range `[1, n]`, pigeonhole guarantees at least one value repeats, which guarantees a cycle exists in this implicit structure; the cycle's start is exactly the duplicate value, found with the identical two-phase algorithm.

## Common bugs

- **Checking `fast != None` but not `fast.next != None`** in the loop guard — dereferencing `fast.next.next` when `fast.next` is `None` crashes with a null-pointer/attribute error. The guard must check both.
- **Resetting the wrong pointer to head, or resetting both.** Only one pointer resets to `head`; the other stays exactly where it met the first pointer. Resetting both breaks the modular-arithmetic argument that makes phase 2 work.
- **Moving the reset pointer two steps instead of one during phase 2.** After the reset, *both* pointers move one step at a time — this is the part of the proof most candidates get backwards, moving `fast` at its original double speed out of habit.
- **Off-by-one when finding "the middle" for even-length lists** and expecting the *first* middle instead of the second, or vice versa — clarify which one the problem wants before coding; the standard `while fast and fast.next` loop lands `slow` on the *second* middle for even-length lists.
- **Applying this pattern to a doubly linked list or an array-as-linked-list problem without checking that "cycle" is even a meaningful/possible state** — e.g., in Find the Duplicate Number, the pigeonhole argument (n+1 values in range [1,n]) is what *guarantees* a cycle exists; without that guarantee the algorithm's assumption doesn't hold.
- **Forgetting to restore a reversed second half after a Palindrome Linked List check**, if the problem or a follow-up requires the list to remain unmodified afterward.

## Interview questions

### Q1 — Linked List Cycle (LC141)
**Testing:** the base cycle-detection loop.
**Answer:** Slow/fast pointers; return `true` the moment they meet, `false` if fast reaches `null`. O(n) time, O(1) space.
**Follow-up trap:** *"Solve it with O(n) space instead, and explain why you wouldn't."* — a hash set of visited nodes is simpler to write and equally correct, but costs O(n) extra memory; say explicitly that Floyd's technique is chosen specifically to eliminate that cost, not because the hash-set approach is wrong.

### Q2 — Linked List Cycle II (LC142)
**Testing:** whether you can prove, not just recite, why resetting one pointer to head finds the cycle start.
**Answer:** After the first meeting, reset one pointer to `head`; advance both one step at a time; they meet again exactly at the cycle's start node.
**Follow-up trap:** *"Prove it."* — walk through the `a = k(b+c) - b` derivation: the distance from head to cycle start (`a`) is congruent, modulo the cycle length, to the distance from the meeting point back around to the start (`c`), because fast traveled exactly twice slow's distance and the excess is a whole number of cycle laps.

### Q3 — Middle of the Linked List (LC876)
**Testing:** applying the same two-speed idea without any cycle at all.
**Answer:** `while fast and fast.next: slow = slow.next; fast = fast.next.next`; return `slow`. One pass, O(n) time, O(1) space.
**Follow-up trap:** *"For an even-length list, which middle does this return — first or second?"* — the second; if the problem wants the first middle, stop one iteration earlier or adjust the loop condition, and say which one your code produces before being asked.

### Q4 — Palindrome Linked List (LC234)
**Testing:** composing fast/slow (find middle) with linked-list reversal, plus care about mutating shared state.
**Answer:** Find the middle, reverse the second half in place, walk from both ends comparing values, optionally reverse the second half back to restore the original list.
**Follow-up trap:** *"Your interviewer says the list must be unchanged after your function returns. Does your solution satisfy that?"* — only if you re-reverse the second half before returning; candidates who reverse in place and forget to undo it silently mutate the caller's data structure, which is a real production-correctness bug, not just an interview nit.

### Q5 — Happy Number (LC202)
**Testing:** recognizing an implicit linked list where "next" is a function application, not a pointer.
**Answer:** Define `next(x)` as the sum of squares of `x`'s digits; run slow/fast over this sequence; if they meet at a value other than 1, it's not happy; if the sequence reaches 1, it is (1 is a fixed point / trivial cycle).
**Follow-up trap:** *"Why does a cycle have to exist at all if the number isn't happy?"* — sum-of-squared-digits on any number is bounded (a k-digit number's digit-square-sum is at most `81k`, and for k >= 4 this is always less than the number itself), so the sequence is confined to a finite range, and by pigeonhole a sequence over a finite range that doesn't terminate must eventually repeat a value, i.e., cycle.

### Q6 — Find the Duplicate Number (LC287)
**Testing:** the hardest transfer of this pattern — recognizing an array as an implicit linked list.
**Answer:** Treat `nums[i]` as a pointer: `next(i) = nums[i]`. Because there are `n+1` values constrained to `[1, n]`, at least one value repeats (pigeonhole), which forces this implicit structure to contain a cycle; the cycle's entry point is exactly the duplicate value. Run the identical two-phase Floyd's algorithm starting from index 0 (or any fixed start).
**Follow-up trap:** *"The array isn't modified and you used O(1) extra space — what's the alternative and why is it worse here?"* — sorting (O(n log n), and mutates or requires a copy) or a hash set/bit-array (O(n) space) both work; Floyd's is the only one hitting both the "don't modify input" and "O(1) space" constraints simultaneously, which is exactly why this problem is a favorite way to test whether you can transfer the pattern beyond literal linked lists.

### Q7 — Reorder List (LC143)
**Testing:** a three-pattern composition — find middle, reverse second half, merge two lists by interleaving.
**Answer:** Find the middle (fast/slow), reverse the second half, then merge the two halves by alternating nodes from each.
**Follow-up trap:** *"What breaks if you don't split the list into exactly two halves before reversing?"* — reversing across the split point without correctly severing the first half's tail creates either an infinite loop (if the first half's last node still points into the reversed second half) or a corrupted merge; the split (`slow.next` set to `None` before reversing) is easy to forget.

### Q8 — Circular Array Loop (LC457)
**Testing:** applying cycle detection with an added directionality/length constraint the base algorithm doesn't have.
**Answer:** For each starting index, walk with fast/slow using `next(i) = (i + nums[i]) mod n`, but additionally verify the cycle has length > 1 and that all steps along it move in the same direction (all positive or all negative); a length-1 self-loop is explicitly disallowed by the problem.
**Follow-up trap:** *"Your slow/fast meets — is that automatically a valid answer here?"* — no; unlike plain cycle detection, this problem requires validating direction-consistency and minimum length *after* detecting a meeting point, which candidates who copy the vanilla template forget to add.

### Q9 — Remove Nth Node From End of List (LC19)
**Testing:** whether you recognize a *gapped* two-pointer variant as a cousin of fast/slow, even though there's no cycle involved.
**Answer:** Advance a lead pointer `n` steps ahead first, then advance both lead and a trail pointer together until lead reaches the end; trail now sits just before the node to remove.
**Follow-up trap:** *"Is this the same pattern as Floyd's cycle detection?"* — it's the same *family* (two pointers moving through a linked list at a controlled offset) but a different mechanism: a fixed head-start gap versus a 2x speed differential. Conflating the two under interview pressure (e.g., trying to use a 2x speed ratio here) produces a pointer that lands in the wrong place.

### Q10 — Linked List Cycle Length
**Testing:** whether you can extend the meeting-point technique to compute a value (cycle length) the base algorithm doesn't directly return.
**Answer:** After detecting a meeting point, keep one pointer fixed and advance the other one step at a time, counting steps until it returns to the same node — that count is the cycle length.
**Follow-up trap:** *"Can you get the cycle length without ever finding the cycle start first?"* — yes: cycle length only requires the meeting point from phase 1, not the phase-2 head-reset; candidates who assume you must run the full start-finding algorithm first are doing unnecessary work.

---

## Red flags that fail you

- Checking only `fast != null` in the loop guard, missing `fast.next != null`, and crashing on `fast.next.next`.
- Resetting both pointers to head after the meeting point instead of just one.
- Advancing the reset pointer two steps instead of one during phase 2.
- Being unable to explain *why* the cycle-start-finding step works when asked, beyond "that's just how it's done."
- Not recognizing Find the Duplicate Number or Happy Number as this pattern in disguise, and reaching for a hash set or sorting instead when O(1) space is explicitly required.
- Forgetting to restore a reversed second half in Palindrome Linked List when the list must remain unmodified.

## Cheat card

```
LOOP GUARD      while fast and fast.next   (both checks required, or fast.next.next crashes)
SPEEDS          slow += 1 node/step, fast += 2 nodes/step
CYCLE EXISTS    iff slow and fast ever occupy the same node
NO CYCLE        fast reaches null/None first, loop ends without a meeting
FIND START      after meeting: reset ONE pointer to head; advance BOTH one step at a time;
                they meet again exactly at the cycle start (proof: a = k(b+c) - b)
FIND MIDDLE     same loop, no cycle logic; slow lands on 2nd middle for even-length lists
IMPLICIT LISTS  Happy Number: next(x) = sum of squared digits
                Find Duplicate: next(i) = nums[i]  (pigeonhole guarantees a cycle exists)
COMPLEXITY      O(n) time, O(1) space -- vs O(n) time AND O(n) space for a visited hash set
COMPOSES WITH   linked-list reversal (Palindrome LL, Reorder List)
NOT THIS        "remove nth from end" is a FIXED-GAP two pointer, not a 2x-speed pair
```
