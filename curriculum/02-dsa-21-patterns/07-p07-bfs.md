# Tree/Graph BFS

> **Track:** T02 DSA: 21 Patterns · **Time:** 2h · **Prereqs:** none · **Updated:** 2026-07-27
> **Module id:** `T02-p07-bfs` · **Tags:** pattern, graphs, trees, shortest-path

## The 30-second version

Breadth-First Search explores a tree or graph one full level at a time using a FIFO queue, and the property that makes it the default tool for shortest-path questions is that the *first* time BFS reaches any node, it has done so via a shortest path measured in edge count — no path discovered later can be shorter, because BFS exhausts every path of length `k` before considering any path of length `k+1`. The mechanical discipline that makes this work correctly is marking a node visited **at the moment you enqueue it**, not when you dequeue it, because otherwise the same node can be queued multiple times before it's ever processed, degrading complexity badly. Recognize BFS from "level order," "shortest path" or "minimum number of steps/moves" on an unweighted graph, "nearest occurrence of X," or any grid/implicit-state problem where every transition costs the same one "step." The two things that separate a working BFS from a broken one are the visited-at-enqueue-time discipline and, for level-by-level problems, snapshotting the queue's size before draining each level rather than looping `while queue` without a level boundary.

## Why this gets asked

The interviewer is testing whether "shortest path" or "minimum steps" reflexively triggers BFS rather than DFS — DFS finds *a* path, not necessarily the shortest one, on the first discovery of any node, so using it for a minimum-steps question either requires exploring every path and comparing (needlessly expensive) or produces a wrong answer if a candidate assumes the first path DFS finds is optimal. This tests real infrastructure intuition: Lee's 1961 wire-routing algorithm for PCB design is literally BFS over a grid, and BFS remains the standard tool for unweighted shortest-path problems in real systems (network hop-count routing, dependency-reachability queries, "nearest available resource" searches). The sharper follow-up that separates levels is multi-source BFS — seeding the queue with *every* starting point simultaneously at level 0 rather than looping single-source BFS once per source — because the naive per-source approach is correct but asymptotically much worse (`O(k * (V+E))` for `k` sources instead of `O(V+E)` total), and recognizing when a state space is an *implicit* graph (word transformations, puzzle configurations) rather than a literal one is the next level up from that.

## Lineage: past → present → future

**What came before.** Before BFS was formalized and named, maze-solving and shortest-path problems in unweighted graphs were often approached ad hoc or via exhaustive path enumeration. E. F. Moore described what is recognizably BFS in 1959 for finding the shortest path out of a maze; C. Y. Lee independently published essentially the same wave-propagation idea in 1961 for automated wire routing in circuit design, where it's still referred to as "Lee's algorithm" in EDA (electronic design automation) contexts — a real production use predating its interview-pattern framing by decades. The pain that both were solving: depth-first exhaustive search either doesn't guarantee shortest paths or requires comparing all paths, which is wasteful when all you need is "closest by hop count."

**Where it stands now.** BFS is the unambiguous default for shortest path / minimum steps on unweighted graphs and grids; there's no disagreement about the algorithm itself. What's live in practice is choosing the right generalization when edge weights aren't uniformly 1: plain BFS gives wrong answers on weighted graphs, Dijkstra's algorithm is the general answer for non-negative weights, but when weights are restricted to `{0, 1}` (a common special case — "free" transitions mixed with unit-cost ones), the **0-1 BFS** variant (a deque, pushing 0-weight transitions to the front and 1-weight transitions to the back) achieves the same result as Dijkstra in `O(V+E)` instead of `O((V+E) log V)`, and recognizing that special case is treated as a meaningfully senior signal. Multi-source BFS (Rotting Oranges, Walls and Gates, 01 Matrix) is now a standard expected variant, not an advanced trick.

**Where it's heading.** Bidirectional BFS — growing search frontiers simultaneously from both the start and the goal, stopping when they meet — is increasingly the expected answer for large implicit state spaces (Word Ladder at scale, puzzle-solving) because it cuts the effective search space from `O(b^d)` to roughly `O(2 * b^(d/2))` for branching factor `b` and depth `d`, a difference that matters enormously once `d` is large. Expect continued emphasis on recognizing *implicit* graphs (states you generate on the fly via transition rules, not literal adjacency lists) as BFS targets, since that recognition — not the queue mechanics — is what's actually being tested at senior level.

## Mental model

```
Level-order BFS from node A:

        A
       / \
      B   C
     / \   \
    D   E   F

queue: [A]                    visited: {A}
-- snapshot size=1, process A, enqueue B, C
queue: [B, C]                  visited: {A,B,C}
-- snapshot size=2, process B (enqueue D,E), process C (enqueue F)
queue: [D, E, F]               visited: {A,B,C,D,E,F}
-- snapshot size=3, process D, E, F (no children)
queue: []                      done

Levels discovered, in order: [A], [B,C], [D,E,F]
-- this is exactly a level-order traversal, and also exactly the
   shortest-path-in-edges distance from A to every other node.
```

Grid BFS (4-directional), multi-source seeding for "distance to nearest gate":

```
Grid (G = gate/source, . = open, # = wall):

  G  .  .
  .  #  .
  .  .  G

Seed the queue with BOTH gates at distance 0 simultaneously (not one at a time):
queue: [(0,0,dist=0), (2,2,dist=0)]

BFS expands both frontiers in lockstep -- every cell gets the TRUE minimum
distance to its NEAREST gate, computed in one O(rows*cols) pass, instead of
running a separate single-source BFS per gate and taking the min afterward.
```

## Recognition heuristics

- **"Level order traversal"** of a tree — BFS by definition; the queue-size-snapshot trick is what turns plain BFS into level-aware BFS.
- **"Shortest path" / "minimum number of steps or moves"** on an unweighted graph, grid, or implicit state space — BFS guarantees the first-discovery path is shortest by edge count; DFS does not.
- **"Nearest occurrence of X" from every other cell/node simultaneously**, or any problem with multiple valid starting points that "spread" at the same rate (Rotting Oranges, Walls and Gates, 01 Matrix) — seed the queue with *all* sources at distance 0 before the first expansion, rather than looping single-source BFS once per source.
- **Grid movement problems (4-directional or 8-directional) asking for minimum moves** — treat the grid as an implicit graph, cells as nodes, adjacency as edges, run standard BFS.
- **A "state" that's generated by a transition rule rather than stored in an adjacency list** — Word Ladder (each transformed word is a neighbor), Sliding Puzzle (each board configuration reachable by one tile move is a neighbor), Open the Lock (each single-wheel turn is a neighbor) — these are implicit graphs; BFS still applies, but neighbor generation is computed on the fly.
- **All edge weights equal, or restricted to `{0, 1}`** — plain BFS for uniform weights; the 0-1 BFS deque variant (push 0-cost transitions to the front, 1-cost to the back) when weights are exactly 0 or 1, avoiding a full Dijkstra's `log V` factor.

**Anti-signal:** if edge weights vary arbitrarily (not uniform, not restricted to `{0,1}`), plain BFS gives a wrong shortest-distance answer — that calls for Dijkstra (non-negative weights) or Bellman-Ford (negative weights allowed), not BFS.

## Template code (Python, Java, Go)

Generic level-order BFS with the queue-size-snapshot trick — the reusable skeleton for the whole family:

**Python**
```python
from collections import deque

def bfs_levels(root) -> list[list]:
    """Level-order traversal of a tree. O(n) time, O(n) space (queue + output)."""
    if not root:
        return []
    result = []
    queue = deque([root])
    while queue:
        level_size = len(queue)          # snapshot BEFORE draining this level
        level_values = []
        for _ in range(level_size):      # process exactly this many nodes
            node = queue.popleft()
            level_values.append(node.val)
            for child in (node.left, node.right):
                if child:
                    queue.append(child)  # no explicit visited set needed for a tree (no cycles)
        result.append(level_values)
    return result

def bfs_shortest_path(graph: dict, start, target) -> int:
    """Shortest path length (edge count) in an unweighted graph. O(V+E) time, O(V) space."""
    if start == target:
        return 0
    visited = {start}
    queue = deque([(start, 0)])
    while queue:
        node, dist = queue.popleft()
        for neighbor in graph[node]:
            if neighbor == target:
                return dist + 1
            if neighbor not in visited:
                visited.add(neighbor)    # mark visited at ENQUEUE time, not dequeue time
                queue.append((neighbor, dist + 1))
    return -1   # target unreachable
```

**Java**
```java
public List<List<Integer>> bfsLevels(TreeNode root) {
    List<List<Integer>> result = new ArrayList<>();
    if (root == null) return result;
    Queue<TreeNode> queue = new LinkedList<>();
    queue.offer(root);
    while (!queue.isEmpty()) {
        int levelSize = queue.size();          // snapshot before draining this level
        List<Integer> levelValues = new ArrayList<>();
        for (int i = 0; i < levelSize; i++) {
            TreeNode node = queue.poll();
            levelValues.add(node.val);
            if (node.left != null) queue.offer(node.left);
            if (node.right != null) queue.offer(node.right);
        }
        result.add(levelValues);
    }
    return result;
}

public int bfsShortestPath(Map<Integer, List<Integer>> graph, int start, int target) {
    if (start == target) return 0;
    Set<Integer> visited = new HashSet<>();
    visited.add(start);
    Queue<int[]> queue = new LinkedList<>();
    queue.offer(new int[]{start, 0});
    while (!queue.isEmpty()) {
        int[] cur = queue.poll();
        for (int neighbor : graph.get(cur[0])) {
            if (neighbor == target) return cur[1] + 1;
            if (!visited.contains(neighbor)) {
                visited.add(neighbor);              // mark visited at enqueue time
                queue.offer(new int[]{neighbor, cur[1] + 1});
            }
        }
    }
    return -1;
}
```

**Go**
```go
func bfsLevels(root *TreeNode) [][]int {
	var result [][]int
	if root == nil {
		return result
	}
	queue := []*TreeNode{root}
	for len(queue) > 0 {
		levelSize := len(queue) // snapshot before draining this level
		levelValues := make([]int, 0, levelSize)
		for i := 0; i < levelSize; i++ {
			node := queue[0]
			queue = queue[1:]
			levelValues = append(levelValues, node.Val)
			if node.Left != nil {
				queue = append(queue, node.Left)
			}
			if node.Right != nil {
				queue = append(queue, node.Right)
			}
		}
		result = append(result, levelValues)
	}
	return result
}

func bfsShortestPath(graph map[int][]int, start, target int) int {
	if start == target {
		return 0
	}
	visited := map[int]bool{start: true}
	type item struct{ node, dist int }
	queue := []item{{start, 0}}
	for len(queue) > 0 {
		cur := queue[0]
		queue = queue[1:]
		for _, neighbor := range graph[cur.node] {
			if neighbor == target {
				return cur.dist + 1
			}
			if !visited[neighbor] {
				visited[neighbor] = true // mark visited at enqueue time
				queue = append(queue, item{neighbor, cur.dist + 1})
			}
		}
	}
	return -1
}
```

## Complexity, derived

Every vertex is enqueued at most once — enforced by marking it visited at the moment of enqueueing, which prevents it from being added to the queue again through a different path — so the total number of dequeue operations across the whole run is bounded by `V`. Each time a vertex is dequeued, its adjacency list is scanned once to find neighbors, and summed across all vertices this touches every edge at most twice (once from each endpoint, for an undirected graph) or once (for a directed graph): **O(V + E) time** overall. Space is **O(V)** for the queue (at most all vertices in flight in the worst case, e.g. a star graph) plus **O(V)** for the visited set. For level-order traversal specifically, taking a `level_size = len(queue)` snapshot before draining costs nothing extra asymptotically — it's still one pass — but it's what correctly partitions the single flat queue into discrete levels; without it you cannot tell where one level ends and the next begins. Multi-source BFS seeding `k` sources simultaneously is still **O(V + E)** total, versus **O(k * (V + E))** for running `k` independent single-source BFS passes and combining results — the difference is entirely in whether the queue starts with one node or many, not in any change to the traversal logic itself.

## The 5 variants interviewers actually ask

1. **Binary Tree Level Order Traversal (LC102).** The base pattern: queue-size snapshot per level, no visited set needed (trees have no cycles).
2. **Rotting Oranges (LC994) — multi-source BFS on a grid.** Seed the queue with every initially rotten orange at minute 0 simultaneously; each BFS layer represents one minute elapsing; the answer is the number of layers processed until no fresh oranges remain reachable (or −1 if some fresh orange is never reached).
3. **Word Ladder (LC127) — BFS on an implicit graph.** Each word is a node; an edge exists between two words differing by exactly one letter. Modification: neighbors aren't stored anywhere — generate them on the fly (try every position, every letter substitution, check membership in the word set) or precompute wildcard-pattern buckets (`h*t` -> `{hot, hat, ...}`) to avoid `O(26 * L)` per-word neighbor generation blowing up at scale.
4. **01 Matrix / Walls and Gates (LC542 / LC286) — multi-source BFS for "nearest occurrence."** Seed the queue with every zero-cell (or every gate) simultaneously at distance 0; standard BFS expansion computes, in one pass, the true minimum distance from each cell to its *nearest* qualifying source — critically different from running separate single-source BFS per source and taking a min afterward, which is correct but far more expensive.
5. **Sliding Puzzle (LC773) / Open the Lock (LC752) — BFS over an implicit configuration state space.** Each board configuration (or 4-digit lock combination) is a node; each single legal move (slide the blank tile, turn one wheel) is an edge to a new configuration; BFS from the start configuration to the goal configuration gives the minimum number of moves. Modification: the state space can include explicitly forbidden states (Open the Lock's "deadends") that must be excluded from the visited/frontier set before starting.

## Common bugs

- **Marking a node visited when it's dequeued instead of when it's enqueued.** This is the single most damaging bug in this pattern: without enqueue-time marking, the same node can be pushed onto the queue multiple times (once via each path that reaches it) before it's ever processed, and in a dense graph this degrades complexity well past `O(V+E)` — in the worst case toward `O(V*E)` — because the same node's neighbors get scanned repeatedly.
- **Using `while queue` without a level-size snapshot** when level boundaries matter (level-order traversal, "minimum steps" where you need the step count, not just reachability) — without `level_size = len(queue)` captured before the inner loop, you can't tell where one level ends and the next begins.
- **Looping single-source BFS once per source** for a "nearest occurrence of X" problem instead of seeding all sources into the queue simultaneously — produces a correct answer, but at a real complexity cost (`O(k*(V+E))` instead of `O(V+E)`) that interviewers specifically probe for.
- **Reaching for DFS/recursion out of habit on a shortest-path or minimum-steps question.** DFS finds *a* path on first discovery, with no guarantee it's the shortest one — using it correctly for shortest path requires exploring all paths and comparing, which is both more code and worse complexity than just using BFS to begin with.
- **Inefficient neighbor generation on implicit graphs.** Word Ladder specifically: generating neighbors by comparing every candidate word in the dictionary to the current word (`O(N * L)` per word) instead of generating all `26 * L` single-letter variations of the current word and checking dictionary membership (`O(26 * L)` per word), or precomputing wildcard buckets — the naive version times out on large dictionaries.
- **Applying plain BFS to a graph with non-uniform edge weights.** BFS only gives correct shortest distances when every edge costs the same; if weights vary (even just `{0,1}`), plain BFS produces wrong distances unless you specifically use the 0-1 BFS deque variant (for `{0,1}` weights) or Dijkstra (general non-negative weights).

## Interview questions

### Q1 — Binary Tree Level Order Traversal (LC102)
**Testing:** the base queue mechanics and the level-size-snapshot trick.
**Answer:** Standard queue-based BFS; snapshot `len(queue)` before draining each level to group nodes correctly. O(n) time, O(n) space.
**Follow-up trap:** *"Do it with O(1) extra space beyond the output" (Morris-style constraint)* — not achievable for BFS the way it is for DFS-based in-order traversal; BFS fundamentally needs queue-proportional space to hold an entire level's frontier, so the honest answer is "not without changing the traversal order," not forcing a workaround.

### Q2 — Minimum Depth of Binary Tree (LC111)
**Testing:** whether BFS's early-termination property beats DFS's exhaustive-then-compare approach.
**Answer:** BFS level by level; return the current depth the instant you first dequeue a leaf node (no children) — that's provably the minimum depth since BFS reaches all nodes at depth `d` before any at depth `d+1`.
**Follow-up trap:** *"Why is BFS strictly better here than DFS?"* — DFS must explore every root-to-leaf path and take the minimum afterward (visiting nodes that BFS would never need to touch, e.g. a long unbalanced branch), whereas BFS can stop the moment it finds the very first leaf, which in a lopsided tree can be a large practical saving even though both are `O(n)` worst case.

### Q3 — Rotting Oranges (LC994)
**Testing:** multi-source BFS as a genuinely different setup from single-source BFS.
**Answer:** Seed the queue with all initially rotten cells at minute 0; each full BFS layer = one minute; count layers until the queue empties, checking afterward whether any fresh orange remains unreached (return −1 if so).
**Follow-up trap:** *"Why not just run BFS from each rotten orange separately and combine?"* — correct but wasteful: `O(k * rows * cols)` for `k` initially rotten oranges versus `O(rows * cols)` for a single multi-source pass; also more complex to combine "time each cell first rotted" correctly across independent runs.

### Q4 — Walls and Gates (LC286)
**Testing:** the "nearest occurrence" multi-source pattern in its cleanest form.
**Answer:** Seed the queue with every gate simultaneously at distance 0; standard BFS fills in each empty room's true distance to its nearest gate in one `O(rows * cols)` pass.
**Follow-up trap:** *"What if you instead ran BFS from every empty room looking for the nearest gate?"* — that inverts source and target unnecessarily and requires `O(rooms * (rows*cols))` work in the worst case; seeding from the (typically far fewer) gates and expanding outward is the efficient direction.

### Q5 — Word Ladder (LC127)
**Testing:** recognizing an implicit graph and generating neighbors efficiently.
**Answer:** BFS where each node is a word and neighbors are all one-letter-different words present in the dictionary; generate neighbors by trying all `26 * L` single-character substitutions and checking set membership, not by scanning the whole dictionary per word.
**Follow-up trap:** *"The dictionary has a million words and the path is 20 steps deep — how do you speed this up further?"* — bidirectional BFS, growing frontiers simultaneously from both the start and end words and stopping when they meet, reduces the effective search space from `O(26^depth)`-ish growth to roughly `O(2 * 26^(depth/2))`, a substantial practical difference at scale.

### Q6 — Word Ladder II (LC126)
**Testing:** whether you can extend BFS to recover *all* shortest transformation sequences, not just the length.
**Answer:** Run BFS layer by layer, but instead of a simple visited set, track each word's parent(s) at the layer where it was first discovered (a word can have multiple valid parents at the same shortest distance); once the target is found, backtrack through the parent map to reconstruct all shortest paths.
**Follow-up trap:** *"Why can't you mark a word visited and never revisit it, the way you would for the length-only version?"* — you still must prevent revisiting words from *later* layers (to preserve the shortest-path guarantee and avoid cycles), but you must allow *multiple parents at the same layer*, since more than one word at distance `d` might transform into the same word at distance `d+1`; marking visited immediately upon first discovery, mid-layer, would suppress some valid shortest paths.

### Q7 — Shortest Path in Binary Matrix (LC1091)
**Testing:** 8-directional grid BFS, a straightforward variant of the base pattern.
**Answer:** Standard BFS from the top-left cell, all 8 neighbor directions, counting layers until the bottom-right cell is reached; return −1 if unreachable or if the start/end cell itself is blocked.
**Follow-up trap:** *"Can you use A* here instead, and would it help?"* — A* with an admissible heuristic (e.g., Chebyshev distance for 8-directional movement) can explore fewer nodes in practice by prioritizing promising directions, but it does not improve the worst-case asymptotic complexity over BFS for an unweighted grid; it's a practical speedup, not an asymptotic one.

### Q8 — Sliding Puzzle (LC773)
**Testing:** BFS over an implicit, combinatorial state space rather than a literal graph.
**Answer:** Encode each board configuration as a string/tuple; BFS from the start configuration, generating neighbor configurations by simulating every legal blank-tile slide; return the layer count at which the goal configuration is first reached.
**Follow-up trap:** *"The state space could in principle be huge — how do you bound it here?"* — for a fixed small board (2x3 in LC773), the total number of distinct configurations is bounded by `(rows*cols)!`, a small fixed constant (720 for 6 tiles), so BFS over the full reachable state space is tractable; for larger boards this approach stops scaling and would need IDA* or pattern-database heuristics instead.

### Q9 — Number of Islands (LC200)
**Testing:** whether you recognize BFS/DFS are interchangeable here, since there's no shortest-path requirement.
**Answer:** BFS (or DFS) flood-fill from each unvisited land cell, marking the entire connected component visited, incrementing an island counter once per fresh flood-fill start.
**Follow-up trap:** *"Why doesn't it matter whether you use BFS or DFS here, when it clearly mattered for Rotting Oranges?"* — this problem only needs connected-component membership, not distance or step count; BFS's shortest-path guarantee is irrelevant when the question is just "is this cell reachable from that cell," so either traversal order works identically well, both `O(rows*cols)`.

### Q10 — Open the Lock (LC752)
**Testing:** BFS over a state space with explicitly forbidden states.
**Answer:** Each 4-digit combination is a node; each of the 8 single-wheel turns (one digit up or down, per wheel) is an edge; BFS from `"0000"` to the target, excluding deadend combinations from ever entering the visited/frontier set.
**Follow-up trap:** *"What if the starting combination `0000` is itself a deadend?"* — check this before starting BFS at all and return −1 immediately; forgetting this edge case means the algorithm can incorrectly explore from a state the problem says is explicitly forbidden.

### Q11 — Design a 0-1 BFS for a graph with edges weighted only 0 or 1
**Testing:** whether you know the deque-based generalization of BFS for the `{0,1}`-weight special case, and why it beats Dijkstra here.
**Answer:** Use a deque instead of a plain queue: when relaxing an edge of weight 0, push the neighbor to the *front*; when relaxing an edge of weight 1, push it to the *back*. This maintains the same "process in non-decreasing distance order" invariant Dijkstra provides, but in `O(V+E)` instead of `O((V+E) log V)`, because it avoids the need for a priority queue.
**Follow-up trap:** *"Why can't you just run plain BFS and pretend weight-0 edges don't count?"* — plain BFS's queue is strictly FIFO and doesn't distinguish edge weights at all, so treating a 1-weight edge the same as a 0-weight one produces wrong distances the moment paths of different weighted lengths compete; the deque's front/back push distinction is precisely what recovers Dijkstra-correct ordering without its `log V` overhead.

### Q12 — Bidirectional BFS conceptual question
**Testing:** whether you understand *why* bidirectional search is asymptotically better, not just that it exists.
**Answer:** Standard single-source BFS to a known target explores roughly `O(b^d)` nodes for branching factor `b` and target depth `d`. Growing two frontiers simultaneously — one from the start, one from the target — and stopping when they meet cuts this to roughly `O(2 * b^(d/2))`, because each frontier only needs to reach the halfway point.
**Follow-up trap:** *"When does bidirectional BFS NOT help, or even hurt?"* — when the target isn't known in advance (you can't grow a frontier from something you don't have), when the branching factor is small enough that the constant-factor overhead of managing two frontiers and checking for intersection outweighs the asymptotic win, or when the graph is directed and edges can't be traversed backward from the target without a separate reverse-adjacency structure.

## Red flags that fail you

- Marking nodes visited at dequeue time instead of enqueue time, allowing duplicate enqueues and blowing up complexity on dense graphs.
- Using `while queue` without a level-size snapshot on a problem that explicitly needs level/step counts.
- Looping single-source BFS once per source on a "nearest occurrence" problem instead of seeding all sources simultaneously.
- Reaching for DFS on a shortest-path or minimum-steps question without acknowledging it doesn't guarantee optimality on first discovery.
- Applying plain BFS to a graph with non-uniform edge weights and getting a distance answer that's silently wrong.
- Not recognizing a puzzle/word-transformation problem as an implicit graph requiring on-the-fly neighbor generation.

## Cheat card

```
CORE PROPERTY   first discovery of any node via BFS = shortest path by edge count (unweighted)
VISITED RULE    mark visited at ENQUEUE time, never at dequeue time -- prevents duplicate enqueues
LEVEL TRACKING  level_size = len(queue) BEFORE draining; process exactly that many, then re-snapshot
COMPLEXITY      O(V + E) time, O(V) space (queue + visited set) -- each vertex enqueued once
MULTI-SOURCE    seed ALL sources into the queue at distance 0 simultaneously, not one at a time
                (O(V+E) total vs O(k*(V+E)) for k separate single-source runs)
IMPLICIT GRAPH  Word Ladder / Sliding Puzzle / Open the Lock -- generate neighbors on the fly
NOT THIS        non-uniform edge weights -> plain BFS gives WRONG distances; need Dijkstra
0-1 BFS         weights in {0,1}: deque, push 0-weight to FRONT, 1-weight to BACK -- O(V+E), no heap
BIDIRECTIONAL   grow frontiers from both start AND target; O(b^d) -> O(2*b^(d/2)) when target is known
TREE BFS        no visited set needed (no cycles); grid/graph BFS always needs one
DFS VS BFS      DFS finds A path first, not necessarily shortest; BFS guarantees shortest by construction
```
