# 15 ML System Designs: Feed Ranking, Ads CTR, Fraud, and the Rest

> **Track:** T10 System Design · **Time:** 4.0h · **Prereqs:** `T10-design-method` · **Updated:** 2026-08-01
> **Module id:** `T10-ml-designs` · **Tags:** practice

## The 30-second version

An ML system design round is the generic design method (`T10-design-method`) with two artifacts swapped in: the API contract becomes a **label definition**, and the data model becomes a **feature list with a leakage audit**. Everything downstream, model choice, serving architecture, metrics, follows from those two the same way architecture follows from schema in a conventional round. Most candidates lose the round in the first five minutes by jumping to "I'd use a gradient-boosted tree" before anyone has said what the tree predicts or how the training label was actually produced, and the label is almost never the naive thing the prompt implies: "will this transaction be fraud" is actually "will this transaction generate a chargeback within 90 days," a definition with a 90-day delay, a chargeback-only blind spot, and a merchant-dispute noise floor baked into the ground truth before a single feature is computed. The interviewer is scoring whether you interrogate the label before the architecture, name the specific feature that leaks the future into the past, and explain why your offline metric will diverge from the online one, not whether you can draw a two-tower diagram from memory.

## Why this gets asked

Because the interviewer has shipped a model that looked correct offline and did nothing, or worse, actively hurt a metric, online, and the postmortem always traces to one of three things: the label was measuring something adjacent to the real target, a feature was computed with information that would not exist at serving time, or the offline evaluation set was drawn from the very policy the new model was meant to replace, so it could never surface the policy's own blind spots. Interviewers who have lived a training-serving skew incident (a feature computed in Python at serving and Spark at training, silently drifting apart) ask about serving architecture specifically to find out whether you have ever operated the online half of a model rather than only trained the offline half. The round exists to filter for people who treat the ML system as a system with a probabilistic component, not a notebook with a REST wrapper.

## Lineage: past → present → future

**What came before.** Through the mid-2010s, ML system design interviews barely existed as a distinct round; a candidate was asked to build a model in a coding round or discuss a Kaggle-style problem, and production concerns were out of scope. The pain that created this module's whole subject was **the model that worked in the notebook and failed in production for reasons the notebook could never surface**: an offline AUC of 0.85 that translated to zero online lift because the training data was sampled from exactly the traffic the current ranker already favored (selection bias), or a fraud model whose "fraud" label was defined as a manual analyst flag that took three weeks to arrive, making the training set perpetually three weeks stale relative to the attack patterns it needed to catch. Google's internal "Rules of Machine Learning" (Zinkevich, circa 2017) crystallized the counter-doctrine that is now interview orthodoxy: most of the system is not the model, and most of the failures are pipeline and label failures, not algorithm failures. The two-stage retrieval-then-ranking architecture that every design below uses traces to the YouTube deep learning recommendations paper (Covington, Adams, Sargin, 2016), which established candidate generation plus ranking as the standard shape once catalog sizes passed the point where scoring every item per request was feasible.

**Where it stands now.** The consensus architecture for anything with a catalog larger than a few thousand items is two-stage: cheap high-recall retrieval (ANN over embeddings, typically a two-tower model, plus rule-based candidate sources) followed by expensive high-precision ranking (a DLRM-style deep model with feature crossing, often multi-task via a mixture-of-experts head predicting several correlated labels at once). Feature stores (Feast-pattern: an offline store for point-in-time-correct training joins, an online store for sub-10ms serving reads) are the standard answer to training-serving skew, though the honest 2026 position, and a live disagreement, is that a feature store guarantees the *values* are computed once but does not by itself guarantee the *code path* computing them is identical, so skew from divergent transformation logic between the batch and streaming implementations remains a real, commonly reported failure even with a feature store in place. The other live disagreement is **label windowing**: shorter windows (score fraud within 60 seconds using only signals available at authorization time) trade completeness for latency, and every one of the fifteen designs below has some version of this tradeoff, made explicit under "Problem framing." At companies with mature ML platforms, online learning (streaming gradient updates within minutes of an event) coexists with periodic batch retraining; the split is usually cost and blast-radius driven, not accuracy driven, since a bad online update degrades live traffic before anyone can roll it back.

**Where it's heading.** High confidence: **cost and calibration become graded explicitly**, mirroring the shift already documented in `T10-design-method` for conventional rounds, because a mis-calibrated probability feeding an auction or a threshold is a production incident, not an academic footnote. Medium confidence: **generative retrieval and LLM-as-ranker** components are entering the standard question pool for feed and search designs, layered on top of the two-stage architecture rather than replacing it, since the latency and cost profile of an LLM call still rules it out as the sole ranker at request volumes above a few thousand QPS. Medium confidence: **unified, shared embeddings across tasks** (one user/item embedding space reused by ranking, retrieval, and ads) are displacing task-specific embeddings at the largest platforms, trading some per-task accuracy for infrastructure simplicity and cross-task cold-start transfer. Low confidence, speculative: fully online (no batch retrain step) production ML for the ranking-heavy designs in this module; the operational risk of an unreviewable, continuously-updating model in a regulated or revenue-critical path is still considered too high at most companies as of 2026.

## Mental model

Every design below runs through the same nine-slot template, in the same order, because each slot's output is what the next slot needs, exactly the way `T10-design-method`'s eight phases chain requirements into numbers into API into schema into architecture.

```
 1. PROBLEM FRAMING   the prediction target, AND the concrete rule that produces
                       the label. "Fraud" is not a label. "Chargeback filed within
                       90 days of authorization" is a label.
 2. REQUIREMENTS       functional + non-functional + 3 clarifying Qs that would
                       change the design if answered differently
 3. SCALE              QPS, catalog size, feature volume -- arithmetic shown
 4. FEATURES           each one paired with its leakage risk, the way a schema
                       is paired with its partition key
 5. MODEL + SERVING    derived from 3 and 4, not recalled; latency budget stated
 6. METRICS            offline metric, online metric, and the NAMED reason they
                       will diverge
 7. THE HARD PART      what the question is actually testing, one sentence
 8. FAILURE MODES      cold start / feedback loop / position bias / drift,
                       each with an OBSERVABLE symptom
 9. FOLLOW-UPS         3, with answers, that a strong interviewer asks next
```

The one property that makes this different from a conventional design round: **the label is upstream of everything, including the requirements phase**, because a label with a 90-day resolution window makes "real-time detection" a contradiction you must resolve (you cannot train on ground truth that does not exist yet, so real-time systems train on a *proxy* label and accept its error). Get the label wrong and every number, feature, and metric downstream is answering a question nobody asked.

```
   label definition ──▶ tells you what the training set can even contain
   (with its delay)     tells you which features are legal at serving time
                            │
                            ▼
   features + leakage ──▶ tells you whether offline metrics are trustworthy
   audit                   at all (a leaked feature inflates offline AUC and
                            cannot survive serving, where the leak is absent)
                            │
                            ▼
   model + serving   ──▶ is now DERIVED: catalog size forces two-stage,
                          latency budget forces model size, label delay
                          forces the training cadence
                            │
                            ▼
   metrics           ──▶ the offline/online GAP is itself the finding;
                          naming why they diverge is worth more than either
                          number alone
```

## How it actually works

### 1. Feed ranking

**Asked at:** Widely reported at Meta, LinkedIn, Pinterest, and X/Twitter as the canonical ML system design prompt ([Meta ML System Design Interview Questions and Guide, David Foster](https://davidfosterhq.medium.com/meta-ml-system-design-interview-questions-and-guide-2026-39a79bbc2c0b), [Hello Interview, ML System Design](https://www.hellointerview.com/learn/ml-system-design/in-a-hurry/introduction) — accessed 2026-08-01) · **Time:** 45 min

**Problem framing** — Predict a score used to rank candidate posts for a user's home feed. **The label is where this fails.** Raw click or like is the naive answer and it is wrong: optimizing click alone rewards clickbait and outrage, since those reliably generate a tap. Production systems train on a **weighted composite of actions** captured in a fixed post-impression window (commonly 10-30 minutes for fast signals, extended to 24-48 hours for slower ones like shares and reports): like = +1, comment = +4, share = +8, hide = -10, report = -100, with weights set by a value model reflecting long-term retention research, not by the engagement team's quarter. The label is therefore a **design decision with a delayed, partially-observed ground truth**, not an observed fact.

**Requirements** — FR: return a ranked list of ~50 posts from a candidate pool of 500-5,000 per request. NFR: p99 end-to-end latency budget ~200ms shared across retrieval and scoring; personalization at hundreds of millions of DAU; freshness within seconds for breaking content. Clarifying questions: (1) "Is the north star time-spent or 'meaningful social interactions'?" — these optimize for different, sometimes opposing, label weightings. (2) "Chronological-plus-boost or fully learned ranking?" — changes whether a chronological prior is a feature or the entire baseline you must beat. (3) "Is exploration (new authors, new topics) a hard constraint or something the model should discover?" — an unconstrained engagement-maximizing model will starve new authors of any signal within weeks.

**Scale** — Assume 500M DAU × 10 feed opens/day = 5×10⁹ requests/day ÷ 1×10⁵ s ≈ 50,000 QPS average, ×3 peak ≈ 150,000 QPS. Each request scores a candidate pool: even after retrieval trims 5,000 down to ~500, that is 500 × 150,000 = 75,000,000 scores/sec if done in one pass, which no single model tier can absorb inside a 200ms budget. This is the arithmetic that forces the two-stage answer in the next section, not a stylistic preference for it.

**Features** — and the leakage risk in each: user-author historical engagement rate over the trailing 7 days (leakage risk: if the window is computed inclusive of the current session rather than strictly before impression time, the model sees the outcome it is predicting); author's all-time CTR computed via a nightly batch job that is not point-in-time joined against the training label's timestamp, so a post from January is scored using an author CTR that includes engagement from March — classic non-point-in-time leakage; social-graph mutual-friend count (safe, static at request time); a "predicted engagement" score sourced from an upstream model trained on overlapping data, which is target leakage via model stacking and shows up as an offline AUC that looks implausibly good.

**Model + serving** — Two-stage. Retrieval merges multiple sources (chronological follow graph, embedding ANN via a two-tower model, trending/popularity) into a pool of ~1,000-5,000. A lightweight first-pass ranker (GBDT or small MLP, ~5ms) cuts the pool to ~150. A heavy final-pass ranker (a DLRM-style multi-task deep model with an MMoE head, one tower per action type) scores the 150 with full feature crossing, ~80ms batched on GPU. A re-ranking layer applies diversity and integrity rules (no more than 2 consecutive posts from one author, ads insertion, demotions) in ~10ms. Latency budget: retrieval 30ms + light rank 20ms + heavy rank 80ms + rerank 10ms ≈ 140ms inside the 200ms SLO. Training/serving skew risk here is specifically that feature transforms live in two code paths (Spark for training, an online feature service for serving); if the two diverge, offline AUC stays healthy while online engagement goes flat, which is the observable symptom of skew, not a crash.

**Metrics** — Offline: multi-task weighted log-loss per action, calibration error (predicted probability within ~2% of observed rate in each decile), NDCG@50 on held-out sessions. Online: the composite value-model score from an A/B test, guarded by time-spent, session length, hide rate, and complaint rate. **They diverge** for two reasons: offline evaluation only has labels for items the *current* production policy chose to show (off-policy bias, since unseen candidates have no ground truth), and feed effects compound over days through novelty and habituation that a single-session offline slice cannot capture.

**The hard part** — Collapsing "engagement" into one trainable scalar without steering the platform toward outrage and clickbait, while an unconstrained model simultaneously narrows the diversity of what gets shown, which degrades the very training distribution the next model version will learn from.

**Failure modes** — **Filter-bubble feedback loop**: symptom is author/topic entropy in served impressions trending down over weeks even while raw engagement holds flat, invisible unless diversity is tracked as its own metric. **Position bias**: symptom is the model overweighting position-1 CTR from logged training data, causing rank inversions once an item is moved to position 5 in production; fixed by including position as a training feature and zeroing it at serving, or by IPS-reweighting. **Cold start for new authors**: symptom is new-author content permanently scoring near the population mean because history-based features default to zero, requiring an explicit exploration bonus in candidate generation rather than a ranking-stage fix. **Delayed-label mismatch**: symptom is share-heavy content systematically under-ranked because the training label window closes before slow signals like shares arrive, visible as a gap between a content type's short-window and long-window engagement rate in monitoring.

**Follow-ups they will ask** — (1) *"How do you handle a mega-influencer with 50M followers in candidate retrieval?"* Decouple it from ranking: fanout-on-read for accounts above a follower threshold, merged into the candidate pool at request time, same pattern as the classic feed-fanout problem in `05-classic-designs`. (2) *"The model over-favors video because dwell time structurally runs longer for video — bug or not?"* It is a labeling bug: normalize dwell time by content-type-specific expected duration, or calibrate per format, otherwise the ranker cannibalizes photo and text content purely because of how the label is scaled, not because video is actually better. (3) *"How do you A/B test a ranking change when feed effects are correlated across a user's whole session?"* Randomize at the user level, not the impression level, and use interleaving experiments for a fast, low-variance read before committing budget to a slower multi-week A/B.

### 2. Ads CTR prediction

**Asked at:** Standard at Google, Meta, and Pinterest ads-adjacent ML roles; the production shape is documented directly by Google in a primary source ([On the Factory Floor: ML Engineering for Industrial-Scale Ads Recommendation Models, arXiv:2209.05310](https://arxiv.org/pdf/2209.05310), [Analytics Vidhya, 10 ML system design problems](https://www.analyticsvidhya.com/blog/2026/06/system-design-for-ml-interviews-real-problems-solved/) — accessed 2026-08-01) · **Time:** 45 min

**Problem framing** — Predict P(click | user, ad, context) to feed an auction that multiplies predicted CTR by bid. **The label** is "did this specific impression receive a click within an attribution window" (commonly 24 hours, sometimes 7 days for view-through), attributed to exactly one ad even when a user saw several in the same session — last-touch vs. multi-touch attribution is a modeling decision made before any feature exists, and it changes which ad "gets credit" for a click a user made after seeing three competitors' ads first.

**Requirements** — FR: score every (user, candidate ad) pair entering the auction; support advertiser targeting, budget pacing, and frequency caps upstream of the model. NFR: p99 latency under ~50-100ms because it sits inside a real-time auction, calibration is a hard requirement because the raw score multiplies a dollar bid. Clarifying questions: (1) "Is this a fresh cold-traffic ad or does it have impression history?" — determines whether you're scoring from features or from a prior. (2) "Single-click attribution or multi-touch?" — changes the label and the training join entirely. (3) "What's the budget-pacing interaction — does a model change here affect delivery pacing too?" — a CTR change can shift which ads exhaust budget fastest, an effect outside the model itself.

**Scale** — Billions of auctions/day at large ad networks; production CTR models train on more than 100 billion examples and serve at well over 100,000 requests/second ([Analytics Vidhya, ML system design](https://www.analyticsvidhya.com/blog/2026/06/system-design-for-ml-interviews-real-problems-solved/) — accessed 2026-08-01). Assume 2×10⁹ auctions/day, ~5 candidate ads scored per auction ⇒ 10¹⁰ scores/day ÷ 1×10⁵s ≈ 100,000 scores/sec average, ×3 peak ≈ 300,000/sec, which forces a model architecture cheap enough per-inference to hit that rate inside a 50-100ms budget alongside dozens of concurrent auction participants.

**Features** — and leakage: historical CTR of the (user, ad-category) pair, computed correctly only if the aggregation window ends strictly before the current impression's timestamp — a common bug is a rolling window computed nightly that silently includes same-day clicks, leaking the outcome. Advertiser bid amount itself (safe, known pre-auction). "Time since last click on this ad" (leakage risk: null-handling for never-clicked users must not default to a sentinel that correlates with the positive class, e.g., defaulting to 0 rather than a large number). Cross features like user-device × ad-category are fine but multiply feature-store cardinality and must be hashed, not leaked.

**Model + serving** — Historically logistic regression with hand-crafted crosses (Google's original 2013 FTRL-proximal work); now a DLRM-style architecture with embedding tables for high-cardinality categoricals (user id, ad id) combined via factorization-machine-style crossing with dense features, trained with online or near-online updates because ad inventory turns over hourly. Serving is a two-part split: an embedding lookup service (sub-millisecond, in-memory) plus a scoring service; the model is frequently retrained (hours, not weeks) because a static model goes stale within days as new campaigns launch, and the embedding tables themselves are updated incrementally rather than reloaded wholesale on every deploy.

**Metrics** — Offline: AUC, log-loss, and **calibration error is the metric that matters most here**: if the model says 5% CTR, the observed click rate on that decile should be within roughly a percentage point, because the auction multiplies this number directly into a bid, and a systematically over-calibrated model overpays advertisers into an unprofitable auction. Online: realized CTR, conversion rate, revenue per impression, advertiser ROI, and budget-pacing accuracy. They diverge because offline evaluation happens on the logged auction winner's outcome only (survivorship: you never see whether a losing ad would have converted), and because advertiser bidding behavior adapts to your model's own scores within days, a moving-target effect with no offline analogue.

**The hard part** — Calibration under extreme class imbalance (CTR is often under 1%) combined with the fact that the auction consumes the raw probability, not a rank, so miscalibration is a direct dollar cost rather than a UX inconvenience.

**Failure modes** — **Feedback loop**: symptom is CTR predictions ratcheting upward for ads that won early auctions purely because winning generates more training impressions for that ad, independent of true quality — corrected by importance-weighting training examples by their original selection probability (inverse propensity). **Position bias**: symptom is nearly identical to feed ranking — training data overrepresents top-slot clicks, requiring a position feature zeroed at serving. **Cold start for new advertisers**: symptom is a brand-new ad scoring near the category average with wide variance, requiring an explicit exploration budget the auction reserves, not a model fix. **Drift from seasonal advertiser behavior**: symptom is calibration error spiking every quarter-end as budget-exhaustion patterns shift, caught only by daily calibration monitoring, not weekly.

**Follow-ups they will ask** — (1) *"Why not just rank by predicted CTR alone?"* Because revenue is bid × CTR (eCPM), and ranking by CTR alone ignores advertiser willingness to pay, producing a socially-reasonable but revenue-poor auction; the interviewer wants you to name eCPM explicitly. (2) *"How do you handle an advertiser who games the frequency cap?"* That's a policy/rules-engine problem upstream of the model, not something CTR prediction should compensate for; conflating the two is the trap. (3) *"Your model under-predicts CTR for a brand-new ad format. Why?"* The embedding table for that categorical has no learned representation yet; back off to a coarser feature (category-level average) until the ad accumulates enough impressions to warrant its own embedding, and say explicitly what "enough" means (a stated impression-count threshold, not a vibe).

### 3. Fraud detection

**Asked at:** A standard prompt at PayPal, Stripe-adjacent fintechs, and card networks; documented as a prep case study in dedicated ML interview courses ([Educative, Grokking the Machine Learning Interview — fraud detection](https://www.educative.io/courses/grokking-the-machine-learning-interview/problem-statement-B14W9JZljKx), [TheLinuxCode, Top 25 ML system design interview questions](https://thelinuxcode.com/top-25-machine-learning-system-design-interview-questions-2026-ready-guide/) — accessed 2026-08-01) · **Time:** 45 min

**Problem framing** — Predict whether a transaction is fraudulent, to either block it at authorization time or flag it for review. **The label is the single hardest part of this design.** "Fraud" is not observed; the actual ground truth is almost always "a chargeback was filed and upheld within 90-120 days of the transaction," which means: (a) confirmed labels for today's transactions do not exist for up to four months, (b) unreported fraud (a victim who never disputes the charge) is a false negative baked permanently into the label, and (c) merchant-initiated disputes for non-fraud reasons (buyer's remorse, delivery disputes) pollute the positive class with a different phenomenon entirely. Any design that does not name this delay and this noise floor has not engaged with the actual problem.

**Requirements** — FR: score a transaction at authorization time and return allow/challenge/block; a slower path re-scores using post-authorization signals. NFR: p99 latency under 100-300ms at authorization (a slow fraud check is a lost sale), extremely high precision requirement on the "block" action since a false positive is a declined legitimate customer, which is itself a revenue and trust cost. Clarifying questions: (1) "Is this card-present or card-not-present fraud?" — different feature sets and attack patterns entirely. (2) "What's the acceptable false-positive rate on legitimate transactions?" — this is a business tradeoff, not a modeling one, and it sets the operating threshold. (3) "Do we have access to a labeled review queue, or only confirmed chargebacks?" — analyst-reviewed flags arrive faster than chargebacks and can be a nearer-term proxy label, at the cost of analyst bias.

**Scale** — Assume a mid-size payments platform: 50M transactions/day ÷ 1×10⁵s ≈ 500 TPS average, ×5 peak (holiday shopping) ≈ 2,500 TPS, each requiring a score within the authorization latency budget. Base fraud rate is typically well under 0.5%, so a 50M/day platform has on the order of 100,000-250,000 fraud-labeled transactions/day at most, and confirmed-chargeback labels for only a fraction of those arrive same-day.

**Features** — and leakage: transaction velocity (number of transactions from this card/device in the last 10 minutes) — safe if computed from a streaming aggregator that only sees data up to the current transaction. Merchant category code and transaction amount — safe. **Device fingerprint reused across accounts** is a strong signal but must be computed without touching any post-transaction event (a common leak is including "was this transaction later refunded," which happens only *because* it was flagged, creating circular causality). "Time since account creation" is safe; "number of chargebacks this card has ever had" is dangerous unless strictly point-in-time joined, since a naive join using the account's *current* chargeback count leaks all future chargebacks into every historical training row for that account.

**Model + serving** — A two-model cascade is the standard production answer: a cheap, deterministic rules/heuristics layer (velocity limits, blocklists, geographic impossibility checks) blocks obvious fraud in under 5ms with zero model inference, followed by a gradient-boosted tree (XGBoost/LightGBM) producing a calibrated risk score for everything the rules pass, with a graph-based signal (shared device/IP/address across accounts) computed offline and joined as a feature rather than run as a live graph query at authorization time, because graph traversal at 2,500 TPS inside a 100ms budget is not feasible without heavy precomputation. High-risk-but-uncertain scores route to a human review queue rather than an automatic block, since the cost asymmetry (declining a good customer vs. approving a bad one) usually favors a human in the loop at the threshold's edge.

**Metrics** — Offline: precision-recall curve and PR-AUC (not ROC-AUC, because the extreme class imbalance makes ROC-AUC look good even for a weak model), with a fixed operating point chosen by business-set cost ratios between false positives and false negatives. Online: realized chargeback rate weeks later, false-positive-driven customer complaint rate, and manual review queue throughput. **They diverge severely** because the offline label set is itself incomplete (unreported fraud) and delayed (chargebacks take months), so a model's "true" online performance is only knowable long after it has already been serving traffic, which is why shadow deployment and delayed backtesting are standard here in a way they are not for feed ranking.

**The hard part** — Building and validating a model whose ground truth will not be fully known for months, while the fraud patterns it needs to catch evolve on a timescale of days, which means the offline evaluation you have today systematically understates performance against next month's attacks.

**Failure modes** — **Label delay causing stale training data**: symptom is the model's precision on *new* attack patterns visibly lower than its precision on the training-period attack mix, because the freshest 90 days of transactions have incomplete labels and are underrepresented in training. **Adversarial adaptation / feedback loop**: symptom is a fraud pattern that worked last month suddenly dropping in volume the week after a model update, followed by a new pattern appearing that specifically avoids the features your model weighted most heavily — fraudsters probe the model. **Feature leakage from post-decision signals**: symptom is an offline AUC above 0.98 that looks too good, almost always traceable to a feature computed after the fraud decision was already effectively made. **Threshold drift**: symptom is the review queue backing up or the block rate spiking after a routine model retrain, because the score distribution shifted even though the underlying threshold policy did not move with it.

**Follow-ups they will ask** — (1) *"How do you train a model when today's labels won't be confirmed for 90 days?"* Use a nearer-term proxy label (analyst review flag, or an early-chargeback signal at 30 days) for fast iteration, and periodically backtest the deployed model against the fully-resolved 90-day label to catch drift the proxy missed; state explicitly that the proxy and the true label can disagree. (2) *"A fraud ring creates 500 new accounts sharing one device fingerprint. How does your per-transaction model catch this?"* It doesn't, by construction; this is why a graph-based signal (shared device/IP/payment-instrument clusters) is joined in as a precomputed feature rather than expected to emerge from per-transaction features alone. (3) *"Precision or recall — which do you optimize for?"* Neither in isolation; you optimize the threshold against the business's stated cost ratio between a false block (lost sale, customer trust) and a false approve (chargeback cost, card-network penalties), and that ratio, not a fixed F1 target, is what should be asked for during requirements.

### 4. Recommendations (the 8-service recsys platform)

**Asked at:** The canonical prompt at Netflix, YouTube, Amazon, and Spotify, and the design this candidate has actually shipped end to end at platform scale ([Hello Interview, video recommendations breakdown](https://www.hellointerview.com/learn/ml-system-design/problem-breakdowns/video-recommendations), [DataInterview, recommendation systems interview questions](https://www.datainterview.com/blog/recommendation-systems-interview-questions) — accessed 2026-08-01) · **Time:** 45-60 min

**Problem framing** — Predict a personalized relevance score for (user, item) pairs across a catalog too large to score exhaustively per request. **The label is a stack of proxies, not one thing**: implicit signals (view, click, completion, dwell time, add-to-cart) each measure a different notion of "relevance," and a system trained on click alone recommends clickbait thumbnails, while one trained on completion alone under-recommends anything long-form to new users who have not yet built a completion habit. Production systems train multiple heads on multiple proxy labels and combine them at serving time with business-tuned weights, exactly the same move as feed ranking's value model, because "did the user like it" is never directly observed.

**Requirements** — FR: return top-N personalized items for a home page, a "for you" rail, or a query-independent surface. NFR: p99 latency 100-200ms for the full pipeline; must handle both a returning user with years of history and a first-session user with none; freshness matters differently by surface (a "continue watching" rail must be instant, a "you might also like" rail can be minutes stale). Clarifying questions: (1) "What's the primary business metric — session length, conversion, or long-term retention?" — these can conflict, and a model optimized purely for session length can select for autoplay-bait. (2) "How is cold start handled for a user's very first session — onboarding survey, demographic prior, or pure popularity fallback?" — determines whether cold start is a modeling problem or a product-flow problem. (3) "Is there an existing shared vector search or feature-store service, or does this platform need to build one?" — directly determines scope: this is the seam decision from `T14-star-bank`'s S10, deciding whether vector search is a shared service other consumers reuse or a component private to this one.

**Scale** — Assume 2M+ users, catalog of 100k-1M items, each user session requesting a ranked list against the full catalog. Naively scoring every item per request is 2M users × 1M items = 2×10¹² pairs, infeasible; retrieval must cut this to a candidate pool of a few hundred before ranking, the same two-stage forcing function as feed ranking, derived from catalog size rather than from a request-rate calculation this time. At ~25% engagement uplift as a target metric, the system needs an offline evaluation harness sized to detect that uplift with statistical confidence before it ever reaches a live A/B, which itself requires an event pipeline processing on the order of tens of millions of interaction events per day.

**Features** — and leakage: user's historical category affinity computed over a trailing window ending strictly before the current session (leakage risk: same-session interactions bleeding into the affinity feature computed for ranking *within* that session, which is subtly different from the cross-session leakage in feed ranking because here the model may be re-scoring mid-session). Item popularity computed with proper decay (an item's all-time popularity is a weak, stale feature; a 7-day trailing popularity with recency decay is stronger and less prone to over-favoring old catalog). Collaborative-filtering-derived embeddings trained on the full interaction matrix including the evaluation period is a leak specific to offline recsys evaluation: the embedding model must be retrained (or at minimum re-fit) using only pre-cutoff interactions, or the offline metric silently benefits from future co-occurrence the production system would not have had.

**Model + serving** — This is the platform's strongest story precisely because it decomposed by scaling profile rather than by data entity: a **vector search service** (shared, so other consumers resolve against one index rather than each embedding its own catalog), a **user-context service** aggregating recent behavior, a **user-event processor** ingesting the write-heavy interaction stream, a **recommendation engine** doing candidate generation (two-tower embedding retrieval plus collaborative-filtering candidates plus popularity fallback) and ranking (a GBDT or deep multi-task ranker over the merged pool), and separate batch services for user-profile processing and content-gap analysis. The read-heavy, latency-bound services (vector search, recommendation engine) are split from the write-heavy, throughput-bound ones (event processor) and the batch ones (profile processor), because putting all three in one process means scaling for the worst of the three and lets a bad batch job take down serving — this is the seam-line criterion, independent scaling and independent failure, not data-entity boundaries. Contextual multi-armed bandits (not a static supervised ranker) handle the scoring layer's continuous improvement, because a supervised ranker trained on logged interactions only ever reinforces what the *previous* policy already showed, starving new catalog items of any exposure to learn from — the bandit frames scoring as an exploration problem, with an explicitly bounded exploration rate so a paying tenant's users are never shown a majority-irrelevant slate in the name of exploration.

**Metrics** — Offline: recall@K and NDCG@K against a held-out interaction set, using **temporal splits, not random splits** (train on interactions before date T, evaluate on interactions after T; a random split leaks future co-occurrence patterns into training). Online: the ~25% engagement uplift figure must be defined with a stated metric (sessions? completions? add-to-carts?), a stated comparison design (holdout group vs. staged rollout vs. pre/post), and a stated window, because an uplift number with no denominator is not defensible under questioning. They diverge because offline recall@K rewards recommending items similar to what a user already engaged with, while online engagement often rewards controlled novelty (recommending something adjacent but new), a difference offline replay on logged data structurally cannot see since it only has labels for what was actually shown.

**The hard part** — Balancing exploitation (recommend what the model is confident about) against exploration (surface unseen or new items so the training data itself does not collapse into a feedback loop), while simultaneously deciding, honestly, whether eight independently-scaled services is solving a real scaling problem or paying an operational tax for boundaries that felt tidy at design time — the platform's own postmortem found that services which always deploy together are one service with extra network hops, not two well-decomposed ones.

**Failure modes** — **Cold start, new user**: symptom is a first-session user receiving a generic popularity-ranked list indistinguishable from every other new user, fixed with an onboarding signal (explicit category picks) or a fast-adapting contextual model rather than waiting for behavioral history to accumulate. **Cold start, new item**: symptom is a newly-published item receiving near-zero recommendations because it has no interaction history to generate collaborative-filtering signal, fixed with content-based features (text/image embeddings) bridging until enough interaction data exists. **Feedback loop / popularity bias**: symptom is the catalog's long tail asymptotically disappearing from recommendations over months even though nothing in the item catalog changed, because the ranker was trained on exposure data the ranker itself generated. **Position bias in the training log**: symptom is the model learning that position 1 causes clicks rather than that clicked items were merely placed there, corrected the same way as feed ranking, with a position feature zeroed at serving or IPS-weighted training.

**Follow-ups they will ask** — (1) *"Why eight services and not a monolith?"* Never defend it as obviously correct: the decomposition criterion was independent scaling and independent failure, and the honest cost is eight deploy pipelines, eight dashboards, and cross-service tracing to answer a one-line question; the real answer names which two services you would consider merging today if they always deploy together. (2) *"How do you know the ~25% engagement uplift is real and not seasonal or novelty-driven?"* Name the measurement method explicitly (holdout cohort held out over the same calendar window, not a pre/post comparison that confounds with a seasonal effect), and if a true holdout was not available, say so and name why (tenant contracts, rollout mechanics) rather than implying rigor that was not there. (3) *"How would a contextual bandit's exploration budget interact with an enterprise tenant's contractual content-relevance expectations?"* Bound exploration explicitly and lower it for smaller or single-tenant catalogs, because unconstrained exploration in a B2B product surfaces irrelevant content to a paying tenant's employees, which becomes a support escalation, not just a lower offline metric.

### 5. Search ranking

**Asked at:** A staple e-commerce ML design prompt at Amazon, Etsy, and eBay-style marketplaces, with the underlying method documented directly by practitioners ([Learning to Rank for E-Commerce Search, OTTO tech blog](https://www.otto.de/jobs/en/technology/techblog/blogpost/1-learning-to-rank-for-e-commerce-search.php), [Final Round AI, product ranking system for Amazon](https://www.finalroundai.com/interview-questions/designing-amazon-ranking-system) — accessed 2026-08-01) · **Time:** 45 min

**Problem framing** — Given a query and a set of matching items, predict a relevance/purchase-likelihood score to order the results. **The label** is not "relevant," which is not observed; production systems use a graded relevance proxy built from a blend of click, add-to-cart, and purchase, discounted by position (since a click on result 8 is stronger relevance evidence than a click on result 1, which may have been clicked simply for being first), commonly modeled as pairwise or listwise preferences (LambdaMART-style) rather than a pointwise regression target, because "is item A more relevant than item B for this query" is the judgment that actually generalizes.

**Requirements** — FR: given a query string, return a ranked page of results within the retrieved candidate set. NFR: p99 latency under 100-150ms including the lexical/semantic retrieval step; ranking quality must hold across a long tail of rare queries that individually have almost no historical click data. Clarifying questions: (1) "Is this head-query-dominated (a small number of queries account for most volume) or long-tail-dominated?" — determines whether per-query learned features or purely generalizable item/query features carry the ranking. (2) "Are results purchase-optimized or relevance-optimized when they conflict?" — a cheaper, more relevant item and a pricier, more profitable item can rank differently depending on the answer. (3) "Is personalization in scope, or is this query-only ranking?" — personalized re-ranking is a materially different, heavier system layered on top of a base ranker.

**Scale** — Assume an e-commerce catalog of 50M items and 500M searches/day ÷ 1×10⁵s ≈ 5,000 QPS average, ×3 peak ≈ 15,000 QPS. Each query typically matches thousands of candidate items lexically before ranking narrows to the ~50 shown, so the retrieval stage (inverted index plus optional dense retrieval) must return a bounded candidate set (commonly capped at 500-1,000) before the learning-to-rank model scores it, the same catalog-size-driven two-stage forcing function seen in recsys and feed ranking.

**Features** — and leakage: query-item historical CTR (leakage risk: computed per exact query string without normalizing for query volume, so rare queries get noisy, overconfident historical CTR estimates that a naive point-in-time join treats as equally trustworthy as a head query's stable estimate — not classic future-leakage but a variance-leakage that inflates offline metrics on rare queries). BM25 lexical match score (safe, deterministic at request time). Item conversion rate needs a point-in-time join identical to the recsys popularity feature, or historical purchases from after the training window leak in. Personalized features (user's past category affinity) carry the same session-boundary leakage risk as recommendations.

**Model + serving** — A lexical retrieval stage (inverted index / BM25, or a hybrid with dense embedding retrieval for semantic matches like "warm coat" matching "insulated jacket") produces a candidate set, followed by a learning-to-rank model (LambdaMART is still the durable, production-proven default for this shape of pointwise/pairwise features, with deep listwise rankers increasingly common at the largest marketplaces) scoring and ordering the final page. Query understanding (spell correction, synonym expansion, category classification of the query itself) sits upstream of retrieval, not inside the ranker, since it changes which candidates are even retrieved. Business rules (in-stock filtering, sponsored placement insertion) apply as a post-ranking layer, kept separate from the learned score so a promotions change does not require retraining the ranker.

**Metrics** — Offline: NDCG@10 and MRR against human-graded or click-derived relevance judgments. Online: conversion rate, revenue per search, zero-result-page rate, and query abandonment rate. They diverge because a ranker can improve NDCG against click-derived labels while conversion stays flat or drops, since clicks and purchases are correlated but not identical signals (a user clicks to compare price, not to buy), and because offline judgments for the long tail of queries are sparse or entirely synthetic (LLM-graded), while online performance on those same queries is where most of a marketplace's actual query volume lives.

**The hard part** — Ranking well on the long tail of queries that individually have almost no historical interaction data, where the model must generalize from item and query *features* rather than from a learned per-query prior, which is the opposite skill from ranking the small number of head queries that dominate naive offline metrics.

**Failure modes** — **Zero-result queries treated as a ranking problem**: symptom is a query returning results ranked reasonably but all irrelevant, when the actual failure is in retrieval/recall, not ranking — conflating the two wastes effort tuning a ranker that has nothing good to rank. **Position bias**: identical mechanism to feed ranking and ads, symptom is training data overweighting top-position clicks, requiring a position feature zeroed at serving. **Popularity feedback loop**: symptom is best-sellers entrenching further because they receive more impressions, hence more clicks, hence higher learned relevance, regardless of whether a newer, better item exists — corrected with exploration slots or explicit freshness boosts. **Query drift**: symptom is ranking quality degrading for a seasonal query ("swimwear") that spikes in volume and shifts in intent (from "buy" browsing in spring to "clearance" browsing in fall) faster than the training window refreshes.

**Follow-ups they will ask** — (1) *"Pointwise, pairwise, or listwise — which and why?"* Pairwise (LambdaMART-style) is the durable default because it directly optimizes the thing that matters (is A more relevant than B) without requiring an absolute relevance score that is hard to define, and it handles the graded-relevance-proxy label cleanly; listwise methods can do slightly better on NDCG directly but cost more to train and debug. (2) *"How do you rank a query with zero historical click data?"* Fall back to content-based and lexical-match features only (BM25 score, category match, item quality signals like rating and return rate), with historical-interaction features simply absent rather than defaulted to a misleading zero, and flag the query as long-tail for separate monitoring. (3) *"Sponsored results are mixed into organic ranking. How does that interact with your ranker?"* They should not interact: the learned ranker orders organic results only, and a separate auction-driven layer inserts sponsored placements afterward according to policy (e.g., no more than one sponsored result per three organic), because conflating ad revenue into the relevance model's training signal corrupts the very ground truth the ranker is supposed to be learning.

### 6. Personalized notifications

**Asked at:** Reported as a growing category at consumer-engagement-heavy companies (Duolingo, LinkedIn, DoorDash-style re-engagement teams); the underlying send-time-optimization technique is documented in Duolingo's public bandit work referenced across ML system design prep material ([ByteByteGo, personalized news feed / notification systems](https://bytebytego.com/courses/machine-learning-system-design-interview/personalized-news-feed) — accessed 2026-08-01) · **Time:** 40 min

**Problem framing** — Predict, for a given user and candidate notification, both **whether to send it at all** and **when** to send it, to maximize a long-term engagement metric while minimizing unsubscribes. **The label** for "should we have sent this" is a delayed, counterfactual quantity: you only observe the outcome (opened, ignored, disabled notifications entirely) for notifications you actually sent, so the label for the *decision itself* is confounded with the send-time and content choices already made by the current policy — you cannot directly observe what would have happened had you not sent it, or had you sent it at a different time, without a randomized holdout.

**Requirements** — FR: given a queue of candidate notifications for a user, decide which to send, in what order, and at what time, respecting a per-user daily cap. NFR: decisions must be made within seconds of a candidate event (a "your friend just posted" notification loses most of its value after an hour); the system must degrade gracefully to a static schedule if the personalization service is unavailable. Clarifying questions: (1) "Is the objective session re-engagement, or a specific conversion (e.g., completing a lesson, finishing a purchase)?" — different objectives reward different content and timing entirely. (2) "Is there a hard daily/weekly send cap per user, and is it a product decision or something the model should learn?" — an unconstrained model will send more than users tolerate, since more sends usually increase short-term opens even as they increase long-term unsubscribes. (3) "What's the cost of a false negative (a notification we should have sent but suppressed) vs. a false positive (one that annoys the user into disabling notifications entirely)?" — these costs are wildly asymmetric and change the operating threshold.

**Scale** — Assume 50M users receiving a candidate pool of 5-10 notification opportunities/day each, requiring a send/suppress/timing decision for each ⇒ 50M × 7 ≈ 3.5×10⁸ decisions/day ÷ 1×10⁵s ≈ 3,500 decisions/sec average. Unlike feed ranking, the send-time-optimization sub-problem is naturally modeled as a per-user bandit over a small discrete action space (a handful of time-of-day buckets), which is computationally far cheaper than scoring a large catalog, so the bottleneck here is typically the event-triggering pipeline's latency, not model inference throughput.

**Features** — and leakage: user's historical open rate by hour-of-day (leakage risk: if computed over a window that includes the very notification being scored, the model effectively sees its own future outcome baked into the feature — must be strictly trailing). Time since last notification sent (safe). Device timezone and typical active hours (safe, slowly changing). A "predicted engagement with this content" score from an upstream content-ranking model is fine as an input feature only if that upstream model was trained on a disjoint time period from the notification-decision model's evaluation set, otherwise you get the same target-leakage-via-stacking risk seen in feed ranking.

**Model + serving** — Two coupled decisions handled as a **contextual bandit**, not a static supervised classifier, because the exploration/exploitation problem here is unusually explicit: you must actually try sending at different times to learn a user's true responsiveness curve, and a supervised model trained only on past sent-and-observed notifications can never learn that a user would have engaged more at 7am if you have never sent one at 7am. Duolingo's public description of this as a "sleeping, recovering bandit" (each time slot is an arm that becomes unavailable once used for the day and recovers the next day) using Thompson sampling is the reference architecture. Serving is a lightweight per-user policy lookup (precomputed daily or updated incrementally), not a heavy real-time model, because the state space per user is small.

**Metrics** — Offline: predicted-open-rate calibration and a bandit-specific offline policy evaluation (inverse propensity scoring against the logged exploration policy, since you cannot naively replay a counterfactual timing decision). Online: open rate, downstream conversion attributable to the notification, and critically, the **unsubscribe/notification-disable rate**, which must be tracked as a hard guardrail rather than a secondary metric, since it is irreversible for that user. They diverge because a model tuned purely to maximize short-term open rate systematically under-weights the slow-building cost of notification fatigue, which only shows up in aggregate disable rates weeks later, well outside a typical online experiment's observation window.

**The hard part** — Learning a per-user timing and content-selection policy from data that is only available for the actions the current policy already took, which requires deliberate randomized exploration, while bounding that exploration so users are not annoyed into disabling notifications during the learning phase.

**Failure modes** — **Notification fatigue feedback loop**: symptom is open rate holding steady or even rising over a few weeks while the disable rate climbs, because the model correctly maximizes the short-term metric it's trained on while overreaching on send volume; only visible if disable rate is monitored on its own weekly trend line, not folded into an aggregate engagement score. **Cold start for new users**: symptom is a brand-new user receiving either a generic high-frequency default schedule (annoying) or a generic low-frequency one (under-engaging) because no personal responsiveness curve exists yet, requiring a fast-converging prior from cohort-level data rather than a per-user cold value. **Timezone/DST drift**: symptom is send-time accuracy degrading twice a year exactly at DST transitions if the "hour of day" feature is computed in server time rather than resolved to the user's local time at send time. **Content-timing confound**: symptom is an apparent "best send time" that is actually an artifact of which content type happens to be queued most often at that hour, corrected by randomizing content and timing independently during the exploration phase rather than jointly.

**Follow-ups they will ask** — (1) *"How do you explore send times without annoying users during the learning phase?"* Cap the exploration budget explicitly (e.g., no more than one exploratory off-schedule send per week per user) and bias exploration toward lower-stakes notification types first, treating the exploration rate itself as a tunable, monitored parameter rather than a fixed constant. (2) *"A user disables notifications. What happens to their bandit state?"* It should be retired, not reset silently; re-enabling notifications later should not resume from a policy trained on pre-disable behavior without re-validating it, since the disable event itself is strong evidence the previous policy was wrong for that user. (3) *"How is this different from an email marketing send-time tool?"* The bandit here is per-user and adapts continuously from behavioral feedback; most generic email tools use a cohort-level heuristic (e.g., "send at the user's historical average open hour") without true counterfactual exploration, so they cannot discover a timing preference the user has never been tested against.

### 7. Spam and abuse detection

**Asked at:** A standard trust-and-safety ML design prompt, with the production architecture documented directly by Meta researchers at USENIX Security ([Deep Entity Classification: Abusive Account Detection for Online Social Networks, USENIX Security 2021](https://www.usenix.org/system/files/sec21summer_xu.pdf), [CalibreOS, graph-aware spam detection](https://www.calibreos.com/learn/mlsd-spam-detection) — accessed 2026-08-01) · **Time:** 45 min

**Problem framing** — Predict whether an account, message, or action is abusive (spam, fake account, coordinated inauthentic behavior). **The label** is unusually adversarial compared to every other design here: confirmed labels come from a mix of user reports (noisy, sometimes retaliatory), moderator review (slow, expensive), and post-hoc platform bans (a strong but very delayed signal, since ban decisions often wait for enough accumulated evidence). Worse, the label is actively contested: a sophisticated abuser optimizes their behavior specifically to avoid whatever the current model flags, so the positive class this quarter's model was trained on is partially obsolete by the time it ships, an adversarial-drift problem the other 14 designs in this module do not share to the same degree.

**Requirements** — FR: score accounts and individual actions (posts, messages, sign-ups) for abuse risk, feeding automated action (rate-limit, shadow-restrict, block) or a human review queue. NFR: sign-up-time scoring must complete in under ~100ms to not degrade onboarding UX; action-level scoring (a posted message) has a looser budget since it can run asynchronously before the message is fully distributed. Clarifying questions: (1) "Is this account-level risk, content-level risk, or both, and do they share a model?" — a fake-account classifier and a spam-message classifier use largely disjoint features and often should be separate models joined at decision time. (2) "What's the tolerance for false positives against legitimate high-volume users (bots providing a legitimate service, power users)?" — a purely volume-based signal conflates the two. (3) "Is coordinated, multi-account abuse in scope, or only single-account behavior?" — coordinated abuse requires graph-based features an isolated per-account model structurally cannot see.

**Scale** — Assume a platform with 500M accounts and 50M new sign-ups/month, plus a much larger volume of individual actions (posts, messages) needing per-action scoring, on the order of 10⁹/day. A meaningful fraction of new sign-ups at scale are automated (industry reports for large social platforms have cited double-digit percentages of daily sign-up attempts as automated abuse during targeted attack windows), so the sign-up-scoring path alone can see spikes of 10-50× its baseline QPS during a coordinated attack, which is itself the load-testing scenario this design must survive, not an edge case.

**Features** — and leakage: account age and velocity of actions since creation (safe, deterministic). IP/device fingerprint reuse across accounts (a legitimate strong signal, but leakage risk exists if the aggregation of "how many accounts share this fingerprint" is computed using the full dataset including accounts created after the one being scored, which retroactively inflates the signal for early accounts in a cluster that hadn't yet been joined by the rest of the ring at scoring time — a point-in-time violation specific to graph features). Content similarity to known spam templates (safe if the template library itself is versioned and the training/serving code shares the exact same matching logic). "Was this account later banned" as a feature for scoring *other* accounts in the same cluster is fine only if computed with a strict time cutoff; used carelessly it silently imports the outcome of the very investigation the model is meant to automate.

**Model + serving** — A cascade similar to fraud: a fast rules/heuristics layer (known bad IP ranges, disposable email domains, velocity limits) filters obvious cases in single-digit milliseconds, followed by a supervised classifier (gradient-boosted trees or a deep model) on a rich per-entity feature vector, augmented by a **graph-based propagation layer** run offline (not per-request) that computes cluster-level risk scores from shared-attribute graphs (device, IP, payment instrument, contact list overlap) and joins those scores in as features — this is the specific architectural move the design must produce, because per-entity heuristics structurally miss coordinated clusters where any single account looks unremarkable in isolation. Confirmed high-confidence spam clusters feed back into training labels faster than individual account-level appeals resolve, which is one of the few places in this module where the platform-generated label (a ban) is treated as more trustworthy than a user report.

**Metrics** — Offline: precision-recall on held-out labeled clusters, with **separate evaluation slices for known attack patterns vs. novel ones**, since aggregate PR-AUC can look excellent while the model is actually only catching last quarter's attack style. Online: confirmed-abuse rate among flagged accounts (precision proxy), false-positive appeal rate among legitimate users caught in the net, and, critically, **the volume of abuse never flagged at all**, estimated via periodic manual audits of a random sample rather than derived from the model's own output (a model cannot self-report its blind spots). They diverge because the offline label set is generated in part by the current model's own flagging (any account the model never flagged was never reviewed, so it can never appear as a confirmed positive), a selection-bias loop unique to adversarial detection systems.

**The hard part** — Building a system whose target keeps adapting specifically to defeat it, which means static offline validation systematically overstates future performance, and requires treating model refresh cadence and adversarial-robustness testing as first-class parts of the design rather than an afterthought bolted onto a fraud-style architecture.

**Failure modes** — **Adversarial adaptation**: symptom is a sharp drop in a specific attack signature's flag rate immediately after a model update ships, followed within days by a new pattern engineered to avoid the updated model's top features — the mirror image of the fraud design's version of this, but faster-moving. **Coordinated-cluster blind spot**: symptom is individually-unremarkable accounts collectively executing an obvious abuse pattern (mass fake reviews, vote manipulation) that no single account's score ever crosses threshold for, only visible via the graph-propagation layer. **False-positive cascade on legitimate power users**: symptom is a spike in appeals from high-volume but legitimate accounts (customer-service bots, high-frequency sellers) immediately after a velocity-threshold tightening, indicating the model conflated volume with intent. **Label contamination from retaliatory reports**: symptom is precision on user-reported abuse dropping in specific community contexts (e.g., contentious topics) where reports are used as a harassment tool against legitimate accounts, requiring report-source reputation weighting rather than treating all reports as equally trustworthy.

**Follow-ups they will ask** — (1) *"How do you catch a coordinated ring where each individual account looks clean?"* Per-account features cannot see it by construction; a shared-attribute graph (device, IP, payment method, contact overlap) with cluster-level risk propagation is the only architecture that surfaces it, computed offline on a schedule, not per-request. (2) *"Your false-positive rate is technically low but complaints are rising. Why?"* Aggregate false-positive rate can hide concentrated harm: check whether false positives cluster in a specific user segment (a particular language, region, or account type) rather than being uniformly distributed, since a uniformly-low aggregate rate is compatible with a segment experiencing a much higher, business-critical rate. (3) *"How often should this model retrain, and why more often than the fraud model?"* Because the adversary here actively probes and adapts to the deployed model within days, not months, unlike a fraud pattern that is comparatively opportunistic; retrain cadence should be tied to observed attack-pattern half-life, measured empirically, not set to a fixed weekly or monthly schedule out of habit.

### 8. Dynamic pricing

**Asked at:** A recurring prompt at Uber, Lyft, and other on-demand marketplaces under the "surge pricing" framing ([Final Round AI, surge pricing system design](https://www.finalroundai.com/interview-questions/surge-pricing-system-design), [EnjoyAlgorithms, how Uber uses ML for surge pricing](https://www.enjoyalgorithms.com/blog/how-uber-use-machine-learning/) — accessed 2026-08-01) · **Time:** 45 min

**Problem framing** — Predict the price multiplier (or absolute price) that clears supply and demand in a local market over the next short interval. **The label** here is unusual: there is no ground-truth "correct price" ever observed, because you only ever see the outcome of the price you actually charged (a censored/counterfactual problem, similar in spirit to the notification design's bandit framing but continuous-valued). The nearest thing to a label is a **realized outcome metric** — did supply and demand clear at this price (measured by wait time, cancellation rate, and driver acceptance rate) — which makes this fundamentally an optimization-under-uncertainty problem wrapped around a demand-forecasting model, not a single supervised-learning target.

**Requirements** — FR: compute and publish a price multiplier per geographic cell, updated on a short cycle. NFR: updates every 1-5 minutes is the standard production cadence; the system must be robust to sudden demand shocks (a large public event) and resistant to gaming (drivers going offline en masse to trigger surge, then returning). Clarifying questions: (1) "What's the acceptable volatility — can the price swing 3x in two minutes, or must changes be smoothed?" — abrupt swings damage user trust even if they are technically optimal. (2) "Is this rider-facing price alone, or does it also need to move driver incentives (bonuses) to affect supply, not just demand?" — a two-sided lever changes the model from pure demand-side pricing to a supply-and-demand joint optimization. (3) "How do we prevent the model from learning to induce artificial scarcity signals?" — a poorly constrained objective can find that suppressing driver-visible supply increases apparent demand pressure and hence revenue, which is an outcome nobody wants shipped.

**Scale** — Assume a market divided into geographic cells (H3 hexagons or similar) recomputing prices every 2 minutes: 10,000 active cells globally × updates every 120s ≈ 83 price computations/sec, trivial in raw throughput but each computation aggregates a local supply/demand forecast from potentially thousands of driver and rider events in that cell over the trailing window, so the real load is the streaming aggregation feeding the model, not the model's own QPS. A major city can have order 10⁵ ride requests/day; the pricing model itself, unlike the CTR or feed models, is evaluated at the geographic-cell granularity, not per-request, which is the key scale difference from every design above it in this module.

**Features** — and leakage: current open-ride-request count in the cell and current available-driver count (both safe, real-time). Historical demand at this time-of-day/day-of-week (safe if computed with proper seasonality windows and no future data). "Driver acceptance rate at the current price" fed back into the very model computing that price is a **closed feedback loop, not classic leakage**, but functionally similar: if the model updates too quickly on its own recent price's effect, small noise in early acceptance data can create price oscillation, so this feature needs deliberate smoothing or a cooldown, distinct from the future-leakage problem in the other 14 designs. Weather and event-calendar data (safe, external, known in advance for planned events, leakage-prone only if the "event happened" flag is populated retroactively for training data in a way that would not have been known at prediction time for a same-day event).

**Model + serving** — A demand-forecasting model (time-series, often gradient-boosted trees or a probabilistic forecaster over historical + real-time signals) predicts near-term ride requests per cell; a supply-forecasting model predicts near-term available drivers; the two combine through a **pricing function**, not a black-box end-to-end model, because the pricing function itself must satisfy business constraints (bounded multiplier range, smoothness caps between consecutive updates, floor/ceiling by regulation in some markets) that are far easier to enforce as an explicit post-model rule layer than to hope a purely learned model respects implicitly. Serving is a scheduled batch recomputation per cell (every 1-5 minutes) rather than a per-request inference call, since the price is published to a shared cache all ride-requests in that cell read from, not computed fresh per rider.

**Metrics** — Offline: forecast accuracy (MAPE or similar) for the demand and supply models independently. Online: the metrics that actually matter are two-sided and can conflict — rider cancellation rate (a proxy for "price too high"), driver acceptance rate and average driver earnings (a proxy for "price too low to attract supply"), and market-clearing time (how long a rider waits for a match). They diverge because a forecasting model can be numerically accurate on average demand while the pricing function built on top of it still produces poor market-clearing outcomes at the tails (unexpected surges the forecast systematically underestimates precisely because they are unprecedented), and because forecast accuracy says nothing about price *volatility*, which is a UX and trust metric the forecasting metric never captures.

**The hard part** — There is no supervised label for "the correct price" at all; the entire design is a demand/supply forecasting problem wrapped in a constrained optimization layer, and conflating "improve the forecast" with "improve the pricing outcome" is the trap, since a perfectly accurate demand forecast still requires a separate, defensible answer for what multiplier to charge given that demand.

**Failure modes** — **Feedback-loop price oscillation**: symptom is the price multiplier flipping between high and low every update cycle in a cell, because driver supply reacts to the *previous* price with a lag the model doesn't account for (drivers see high surge, flock in, price drops, drivers leave, price rises again), fixed with damping/smoothing constraints on the update rate, not with a "better" model. **Gaming via artificial scarcity**: symptom is a cluster of drivers going offline simultaneously right before a price update, then returning once surge triggers, detectable via anomalous synchronized availability-drop patterns and mitigated by rate-limiting how much single-interval driver-count drops can move price. **Cold demand cells**: symptom is a newly-served geographic area or an unusual time window (3am in a small city) having too little historical data for the demand forecaster, producing wildly unstable price predictions, requiring a fallback to a coarser regional or population-density-based prior. **Regulatory cap interaction**: symptom is a computed price hitting a jurisdiction's legal surge cap and the system needing an explicit clamp, which if implemented incorrectly (clamping after publishing rather than before) creates a discontinuity that looks like a pricing bug to users mid-ride.

**Follow-ups they will ask** — (1) *"How do you prevent surge pricing from feeling exploitative to users during genuine emergencies?"* This is a policy decision layered on top of the model, not a modeling fix: cap multipliers explicitly during flagged emergency events (detected via news/event-calendar integration or manual override), and treat the cap as a hard business rule the pricing function must respect regardless of what the forecast implies. (2) *"Drivers claim the app under-prices short trips relative to long trips at the same surge level. Is that a pricing bug or a base-fare structure issue?"* Separate the surge multiplier (demand/supply-driven) from the base fare structure (distance/time-driven); conflating them in one model makes every pricing complaint ambiguous about which component is at fault, so keeping them as separate, independently-debuggable layers is itself a design decision worth stating. (3) *"How would you A/B test a change to the pricing model when price directly affects the market you're trying to measure?"* Standard user-level randomization does not work because pricing has market-level spillover (a rider in the treatment group not getting a ride affects supply available to a control-group rider in the same cell); the standard answer is geographic/market-level randomization (switchback experiments, alternating the whole city or cell between treatment and control over time) rather than individual-level A/B.

### 9. ETA prediction

**Asked at:** A named, primary-sourced design at DoorDash and Uber ([Precision in Motion: Deep Learning for Smarter ETA Predictions, DoorDash Engineering](https://careersatdoordash.com/blog/deep-learning-for-smarter-eta-predictions/), [Improving ETAs with Multi-Task Models, Deep Learning, and Probabilistic Forecasts, DoorDash Engineering](https://careersatdoordash.com/blog/improving-etas-with-multi-task-models-deep-learning-and-probabilistic-forecasts/) — accessed 2026-08-01) · **Time:** 45 min

**Problem framing** — Predict the time until an event completes: a delivery arrives, a ride ends, a route segment is traversed. **The label** is the actual observed completion time, which sounds clean compared to fraud or spam, but it is not: the label is only observable after the fact and is contaminated by events *outside* the thing you are modeling (a driver stopping for gas, a restaurant running behind on food prep, a rider changing the drop-off address mid-trip), so the "true" travel-time signal is entangled with several other processes that a naive single-target regression conflates into one noisy number. DoorDash's production framing addresses this directly by decomposing the label into a **base travel-time distribution plus a decision layer** that adjusts for operational factors (batching, prep-time buffers) rather than training one end-to-end regressor on the raw observed timestamp gap.

**Requirements** — FR: given current state (route, current prep/pickup status, live traffic), return an ETA, continuously updated as the trip progresses. NFR: an ETA shown to a user must be right-sized on both sides — too optimistic causes cancellations when it's missed, too pessimistic causes complaints and lost orders; latency for a single ETA computation must be low (tens of milliseconds) since it's recomputed frequently during an active trip. Clarifying questions: (1) "Is this a point estimate or does the product need a confidence range (e.g., '15-25 min')?" — a probabilistic forecast is a materially different modeling target than a point regression. (2) "Does the ETA need to account for batching (multiple orders on one trip) or is it single-trip?" — batching couples multiple deliveries' ETAs together, which a per-trip model alone cannot represent. (3) "How is the ETA re-evaluated mid-trip — full recomputation or an incremental update?" — affects whether you need a stateless per-request model or a stateful tracking model.

**Scale** — Assume a food-delivery platform with 5M orders/day, each order's ETA recomputed roughly every 30-60 seconds while active (an active trip lasts ~30 minutes) ⇒ roughly 5M × 30-60 recomputations/order ≈ 1.5-3×10⁸ ETA computations/day ÷ 1×10⁵s ≈ 1,500-3,000 computations/sec average, each needing sub-100ms latency since it's on a live-tracking UI path. The underlying route/traffic data feeding these computations (live GPS pings from drivers) is a much higher-volume streaming problem, on the order of one ping every few seconds per active driver across potentially hundreds of thousands of concurrent active trips at peak.

**Features** — and leakage: historical average speed on this route segment at this time of day (safe if computed from a trailing window ending before the current trip). Live GPS-derived current speed (safe, real-time). Restaurant's historical prep-time distribution (leakage risk: if computed inclusive of the order currently being estimated, especially for a slow-moving restaurant queue where "today's average so far" partially reflects the very order you're predicting). Traffic-service ETA as an input feature (safe, external signal, but must be point-in-time — using a traffic snapshot taken after the trip completed, rather than the one available at prediction time, is a subtle backtest-only leak that inflates offline accuracy).

**Model + serving** — DoorDash's documented production pattern is instructive: a **base model** (increasingly a deep multi-task model with time-series features) outputs a predicted *distribution* over completion time, not a single point, feeding a separate **decision layer** that solves the actual business optimization (what number to *show* the user, which may deliberately differ from the model's raw mean to account for asymmetric costs of under- vs over-promising, and which handles multi-order batching logic the base model doesn't need to know about). Gradient-boosted trees (XGBoost, LightGBM) remain a strong, latency-cheap baseline for the base travel-time model at logistics companies including DoorDash, Uber, and Lyft, with deep multi-task and probabilistic-forecast models layered in for the segments where GBDTs plateau. This separation, forecasting distribution vs. deciding what to display, is the specific architectural insight the design should surface, analogous to fraud's rules-plus-model cascade: two components solving two different problems, not one model doing both.

**Metrics** — Offline: quantile loss or CRPS (continuous ranked probability score) against the predicted distribution, plus simple MAE/RMSE on the point estimate for comparability. Online: the metrics that actually matter are downstream business ones — order cancellation rate (a proxy for "ETA was too pessimistic and the user gave up"), post-delivery complaint rate about lateness (a proxy for "ETA was too optimistic"), and driver/rider wait-time SLO adherence. They diverge because a model can have excellent MAE on average while being systematically biased on the tails that matter most (the 20-minute-late outlier that drives complaints is exactly the case average error metrics wash out), which is why DoorDash's own framing explicitly separates accuracy from the multi-objective decision the business actually needs made.

**The hard part** — The observed label is entangled with operational factors (batching decisions, restaurant queue state, a driver's personal routing choices) that are not properties of "how long does this route take," so a model trained naively on raw completion time learns to predict operational noise as if it were travel-time signal, and the real design work is separating the two rather than tuning the regressor.

**Failure modes** — **Systematic optimism bias**: symptom is cancellation rate spiking specifically for a route segment or restaurant where the model has been recently, repeatedly wrong short, traceable to a feature (like prep-time) not adapting fast enough to a real operational slowdown (a restaurant short-staffed today). **Cold start for a new route or new restaurant**: symptom is wildly variable ETA accuracy for a location with under a week of order history, requiring a fallback to a coarser regional or category-level prior (similar restaurants nearby) rather than an unconstrained per-location estimate. **Traffic-data staleness**: symptom is ETA accuracy degrading specifically during rapidly-changing conditions (a sudden accident, a storm) where the traffic feed's own update latency (a minute or more) lags reality, visible as a spike in error variance correlated with external traffic-incident feeds, not a steady degradation. **Batching interaction**: symptom is individual-order ETAs becoming systematically wrong the moment an order gets batched with another, if the base per-trip model was never trained on batched-trip examples separately.

**Follow-ups they will ask** — (1) *"Would you show users the model's raw predicted mean, or something else?"* Something else, deliberately: the cost of being late is usually higher (cancellations, complaints, refunds) than the cost of being a few minutes early, so the displayed number is typically a calibrated upper quantile of the predicted distribution (e.g., the 75th percentile) rather than the mean, chosen and tuned as a business decision separate from the forecasting model itself. (2) *"How do you evaluate an ETA model when the true 'travel time absent all operational noise' is never observed?"* You can't fully; you evaluate what you can observe (total completion time) while trying to decompose error attribution (was the miss in prep-time forecasting or route-time forecasting) via intermediate checkpoints (time-to-pickup vs. time-from-pickup-to-dropoff), each independently validated where instrumented. (3) *"Two orders get batched onto one trip. How does that change your ETA?"* The base per-segment travel-time model doesn't need to change, but the decision layer does: it must sequence the stops, allocate the aggregate trip time across both orders' individual promised windows, and this is exactly why DoorDash's documented architecture keeps the decision layer separate from the base forecasting model — a single end-to-end regressor has no natural place to inject batching logic.

### 10. Churn prediction

**Asked at:** A standard applied-ML case study across subscription and marketplace companies, with the framing consistently emphasized in prep material ([BuildML, cracking ML system design case studies](https://buildml.substack.com/p/data-science-interview-guide-cracking), [Rohan Paul, predicting user churn](https://www.rohan-paul.com/p/ml-interview-q-series-predicting) — accessed 2026-08-01) · **Time:** 40 min

**Problem framing** — Predict which users are likely to stop using a product or cancel a subscription, so the business can intervene. **The label is a definitional choice disguised as an obvious fact**: "churn" for a subscription product might mean cancellation (a clean, observable event) or it might mean silent disengagement (no login in 30 days, still paying), and for a non-subscription product there is no cancellation event at all, only a chosen inactivity threshold that is itself arbitrary (why 30 days and not 45?) and directly determines both the size of the positive class and how far in advance the model can plausibly predict it. The interviewer wants to hear that you would ask what action the business takes on a churn prediction before finalizing the label, because a model driving a retention discount campaign needs a very different label horizon (predict churn 30+ days out, while there's time to intervene) than one driving a support-team prioritization queue (predict churn imminent this week).

**Requirements** — FR: produce a churn-risk score per user/account on a recurring cadence (daily or weekly), feeding a retention campaign, a customer-success outreach queue, or a product experiment. NFR: does not need sub-second latency (this is a batch-scored problem, not a live-request one), but does need a stable, explainable score since it typically drives a human-facing business action (a retention offer, a support call) where "why did the model flag this account" is a real operational question, not academic interpretability theater. Clarifying questions: (1) "What action does the business take on a churn prediction, and how far in advance does that action need lead time?" — this single answer sets the label's prediction horizon. (2) "Is 'churn' contractual (cancellation) or behavioral (inactivity), and who owns that definition?" — a definition owned by product/business, not invented by the ML team, or it will be second-guessed after the fact. (3) "Is this B2C (individual users) or B2B (accounts with multiple seats), where one disengaged user does not mean the account is churning?" — B2B churn is an account-level aggregate label built from user-level signals, a materially different problem.

**Scale** — Assume 10M active subscription accounts scored weekly ⇒ 10M scores/week, a batch job, not a real-time serving problem, so the throughput requirement is closer to "complete within an overnight window" (say, under 4 hours) than a QPS figure. The training set is bounded by how far back usage history is retained and how many complete churn/non-churn observation windows exist; for a churn horizon of 90 days, only accounts with at least 90 days of subsequent history can be labeled, which silently excludes the newest cohort of accounts from every training run — a data availability constraint, not a modeling choice, worth stating explicitly.

**Features** — and leakage: usage frequency trend over the trailing 60 days (safe if computed strictly before the label observation window begins). **Chronological train/test splitting is mandatory, not optional, and its absence is the single most common leakage bug reported in churn prep material**: a random split lets the model train on a user's month-6 behavior and evaluate on their month-3 behavior, implicitly leaking future usage patterns backward. Support-ticket volume (a strong churn signal, but a ticket opened *because* the user is already canceling is a leak if the ticket-scoring window overlaps the churn event itself, rather than ending strictly before the observation window that defines "not yet churned"). Payment-failure history (safe, and often one of the strongest legitimate signals precisely because it precedes rather than follows disengagement).

**Model + serving** — Gradient-boosted trees (XGBoost/LightGBM) are the durable default here, not because churn is architecturally simple, but because the feature set is tabular, moderately sized, and interpretability (which features drove this account's score) matters for the human-facing action downstream, an argument for GBDT-plus-SHAP over a deep model that a churn design should make explicitly rather than defaulting to "deep learning" out of habit. For accounts where *when* they'll churn matters as much as *whether*, survival analysis (Cox proportional hazards, or a discrete-time survival model) is the better-fitting tool than binary classification, since it directly models time-to-event rather than forcing an arbitrary fixed horizon. Serving is a nightly or weekly batch scoring job writing scores to a table the CRM/outreach system reads, not a request-time inference path.

**Metrics** — Offline: ROC-AUC and precision-recall at the operating threshold the retention team will actually act on (not an arbitrary 0.5 cutoff), calibration if the score feeds a prioritization ranking rather than a binary decision. Online: the metric that matters is **incremental retention lift from the intervention triggered by the score**, measured via a holdout group that receives no intervention despite being flagged high-risk, not the churn rate among flagged users alone (a high churn rate among flagged users just confirms the model found risky accounts; it says nothing about whether the resulting retention campaign actually saved any of them). They diverge sharply here because a model can have excellent offline discrimination while the business intervention built on top of it has zero effect (e.g., a retention discount offered to users who were never going to churn regardless, wasting margin with no counterfactual benefit) — this is fundamentally an uplift-modeling problem hiding inside a classification framing, and naming that distinction is the senior signal.

**The hard part** — The model's job is not "predict churn accurately," it's "identify users where an intervention will change the outcome," which is a different, harder target (uplift/causal, not purely predictive) than the binary classification framing the prompt implies, and most candidates never surface this distinction.

**Failure modes** — **Chronological leakage inflating offline metrics**: symptom is an implausibly high offline AUC (0.95+) on a problem domain where 0.75-0.85 is the realistic ceiling, almost always traceable to a random rather than time-based split. **Targeting users who would have stayed anyway**: symptom is a retention campaign with a high "success rate" among targeted users but no measurable lift over a held-out control, indicating the model found correlates of loyalty (low risk, would-stay-regardless) rather than correlates of save-ability. **Definition drift**: symptom is the model's precision degrading after a product change (a new free tier, a pricing change) shifts what "inactive for 30 days" actually means behaviorally, without anyone updating the label definition to match. **B2B account-aggregation error**: symptom is an account flagged as churning because one power user left, while the remaining five seats are healthy and the account renews anyway, indicating the account-level label was built by naively averaging or taking the max of user-level signals rather than modeling the account's actual renewal decision-maker.

**Follow-ups they will ask** — (1) *"Your model has 0.92 AUC. Should you be suspicious?"* Yes, immediately: on most churn problems that is a sign of leakage (a random split, or a feature capturing post-churn behavior like a payment-method-removal event that only happens once someone has already decided to leave) before it's a sign of a great model. (2) *"How do you know your retention campaign actually works, versus just correlating with users who were fine anyway?"* You need a held-out control group of high-risk-flagged users who receive no intervention, and measure lift against them; without that control, "the campaign worked" and "we identified loyal users by accident" are indistinguishable from the data alone. (3) *"Should this be classification or survival analysis?"* If the business only needs a risk-ranked list to prioritize a fixed number of outreach slots, classification with a well-chosen horizon is simpler and sufficient; if the business needs to know *when* to intervene (this account will likely churn in 2 weeks vs. 8 weeks, changing which offer applies), survival analysis directly models the time-to-event and should be named as the better-fitting tool even if it's more work to stand up.

### 11. Content moderation

**Asked at:** A regular trust-and-safety ML design prompt, with the human-in-the-loop routing pattern documented in dedicated prep write-ups ([Codelit, content moderation system design: scaling trust and safety](https://codelit.io/blog/content-moderation-system-design), [DesignGurus, real-time AI content moderation at scale](https://designgurus.substack.com/p/system-design-case-study-how-to-design-7c1) — accessed 2026-08-01) · **Time:** 45 min

**Problem framing** — Predict whether a piece of content (text, image, video) violates a specific policy (hate speech, nudity, violence, misinformation), to auto-remove, auto-approve, or route to human review. **The label** is unusually fragmented compared to every other design here: there is no single "violates policy" label, there are dozens of *separate* policy categories each with their own definition, their own enforcement threshold, and their own labeling guideline that changes as policy evolves (a term considered borderline last year may be explicitly banned this year after a policy update), meaning the training data's label distribution is non-stationary by design, not by drift accident, and a shipped model's labels can become partially obsolete the same week the policy team updates guidelines.

**Requirements** — FR: score newly-posted content against each active policy category before or shortly after it becomes visible; route borderline or severe cases to human reviewers with enough context to decide quickly. NFR: latency budget differs sharply by severity — content flagged as likely severe (e.g., graphic violence) should be actioned before wide distribution, ideally sub-second, while lower-severity borderline content can tolerate a slower async review path measured in minutes. Clarifying questions: (1) "Pre-publish blocking or post-publish takedown?" — pre-publish blocking needs a much tighter latency budget and a much higher precision bar, since a false positive there is a visible, immediate censorship complaint. (2) "How many distinct policy categories, and do they share a model or need separate classifiers?" — a single multi-label model versus a bank of specialized classifiers is a real architectural fork with different retraining and audit implications. (3) "What's the appeals process, and does an overturned appeal feed back into training data?" — appeals are a rare but high-quality labeled signal (a human explicitly disagreeing with the model) that most designs under-use.

**Scale** — Assume a platform posting 100M pieces of content/day requiring at least a first-pass automated score across the active policy set ÷ 1×10⁵s ≈ 1,000 items/sec average, ×3-5 peak for viral events ≈ 3,000-5,000/sec. Even a modest 0.1% escalation rate to human review is 100,000 items/day requiring human attention, which sizes the review-team capacity as a hard constraint on the model's precision requirement: a small increase in the automated system's false-escalation rate translates directly into review-queue backlog, a resource cost as real as any compute bill.

**Features** — and leakage: text-classifier score from a policy-specific fine-tuned model (safe, computed at request time). Account history (prior violations, account age) — a legitimately strong signal, but leakage risk if "number of prior violations" is computed inclusive of violations discovered *after* the content in question was posted, particularly for content near an account's ban trigger, where a naive current-count join can leak the eventual ban decision backward onto earlier posts by the same account. Virality/reach signals (a highly-shared piece of content is both more consequential to get right and more likely to have accumulated more user reports by the time it's re-scored, which can create circular reinforcement: reports drive re-scoring, re-scoring drives action, action is then treated as confirming the reports were correct without independent verification).

**Model + serving** — A tiered architecture is the production standard: fast, cheap classifiers (often smaller fine-tuned models or even hash-matching against known-violating content via perceptual hashing for images) handle the large volume of clear-cut cases in milliseconds; borderline or high-severity cases route to progressively more expensive analysis (larger models, potentially an LLM-based reasoning pass for nuanced text) before finally reaching a human reviewer for genuinely ambiguous cases. This tiering exists because running the most accurate, most expensive model on all 100M+ daily items is not economically viable, and because a large fraction of content is unambiguous and does not need it, the same cost-shaped forcing function seen in every design in this module that mentions a cascade. Active learning, prioritizing genuinely uncertain cases for human labeling rather than random sampling, is standard because human review capacity is the scarcest resource in the whole pipeline.

**Metrics** — Offline: precision-recall per policy category against human-labeled ground truth, since a single aggregate metric across dozens of unrelated policy categories (hate speech vs. spam vs. graphic violence) hides which specific category is underperforming. Online: automated action accuracy (measured via a sampled human audit of automated decisions, since the model cannot grade its own precision), appeal overturn rate (a directly-measured false-positive proxy), and time-to-action for severe content. They diverge because offline evaluation happens against a labeling guideline that may already be stale by the time the model ships (policy updates happen faster than full retrain-and-validate cycles), and because online, the model interacts with a human review layer whose own consistency varies, so "the model's true precision" is entangled with reviewer agreement rates in a way no offline set alone can isolate.

**The hard part** — The label itself is a moving target defined by an evolving policy document, not a stable phenomenon in the world, so validating that a shipped model still reflects current policy is an ongoing process requirement, not a one-time launch gate, and the design must include how policy changes propagate into retraining, not just how content flows through the pipeline.

**Failure modes** — **Policy drift without retrain**: symptom is precision degrading specifically on newly-banned categories of content that postdate the last training run, while precision on stable, long-established categories (well-known slurs, explicit imagery) stays flat, a category-specific degradation pattern that an aggregate metric hides. **Adversarial evasion**: symptom is violating content using deliberate misspellings, image perturbations, or coded language to slip past text/image classifiers, visible as a rising gap between user-report volume and automated-detection volume for a specific evasion pattern. **Review-queue backlog cascading into stale actions**: symptom is severe content sitting in the human-review queue for hours during a viral spike because escalation volume exceeded reviewer capacity, meaning the tiering thresholds need to shift dynamically with observed queue depth, not stay fixed. **Context-blindness**: symptom is a classifier trained on isolated content pieces flagging clearly satirical, journalistic, or counter-speech content (quoting a slur to condemn it) as violating, because the model has no access to the surrounding context a human reviewer would use instantly.

**Follow-ups they will ask** — (1) *"How do you handle a brand-new policy category with zero labeled training data?"* Bootstrap with keyword/rule-based heuristics and route everything the heuristic flags to human review, deliberately over-escalating at first to generate labeled data quickly, then train a model once enough reviewed examples accumulate; do not wait for a "proper" labeled dataset before launching any automated assistance. (2) *"An appeal gets overturned. What should happen to that piece of content's original training label?"* It should feed back as a correction, since an overturned appeal is a rare, high-confidence human disagreement with the model's decision, but the design must guard against a small number of successful bad-faith appeals systematically poisoning the label for genuinely-violating content, so appeal-sourced corrections typically need a higher confirmation bar than a standard reviewer label. (3) *"How would an LLM change this architecture versus a fine-tuned classifier bank?"* An LLM-based reasoning pass can handle the context-blindness failure mode (distinguishing satire or counter-speech from genuine violation) that fixed classifiers structurally cannot, but at materially higher per-item cost and latency, which is exactly why it belongs in the tiered architecture's slower, borderline-case lane rather than as a replacement for the fast first-pass classifiers.

### 12. Similar-item retrieval

**Asked at:** A common e-commerce and media-platform prompt ("customers who viewed this also viewed"), with production implementations documented directly by Pinterest and Allegro.com ([Pinterest's Embedding Based Retrieval](https://mlops.substack.com/p/pinterests-embedding-based-retrieval), [Suggest, Complement, Inspire: Two-Tower Recommendations at Allegro.com, ACM RecSys 2026](https://arxiv.org/pdf/2508.03702) — accessed 2026-08-01) · **Time:** 40 min

**Problem framing** — Given an anchor item, retrieve the K most similar or complementary items from a large catalog, fast enough to run inline on a product page. **The label** requires an explicit choice most candidates skip past: "similar" for a retrieval carousel usually means co-engagement (items frequently viewed, added-to-cart, or purchased together in the same session), not visual or textual similarity, which is a genuinely different signal — two items can be visually near-identical (two black t-shirts) and never co-occur in purchase behavior because a shopper buys one or the other, not both, so a model trained on raw visual embedding distance will recommend substitutes when the product actually wants complements, or vice versa, depending on which carousel ("also viewed" vs. "frequently bought together") is being served.

**Requirements** — FR: given an item id, return the top-K most similar/complementary items in real time as a product page renders. NFR: p99 latency well under 50-100ms since it's inline on a page load, not a background batch job; must handle a catalog with continuous churn (new items daily, discontinued items needing removal from results). Clarifying questions: (1) "Is the target 'similar' (substitutes) or 'complementary' (frequently bought together)?" — these need different training objectives and often different models entirely, not one model serving both intents. (2) "Is retrieval query-item-based only, or does it also personalize by the viewing user?" — pure item-to-item similarity is a much simpler, fully precomputable problem than user-conditioned similarity. (3) "How fast must a brand-new item start appearing in other items' similar-item lists?" — determines whether nightly batch recomputation of the index is acceptable or a near-real-time index update path is required.

**Scale** — Assume a catalog of 50M items with a similar-item lookup requested on a meaningful fraction of the platform's page views: 500M page views/day × 30% showing a similar-items carousel ≈ 1.5×10⁸ lookups/day ÷ 1×10⁵s ≈ 1,500 QPS average, ×3 peak ≈ 4,500 QPS. Precomputing embeddings for 50M items at, say, 256 dimensions in float32 is 50M × 256 × 4B ≈ 51GB, which comfortably fits an in-memory ANN index on a modest cluster, the arithmetic that justifies precomputed embeddings plus ANN over any form of live pairwise comparison.

**Features** — and leakage: co-view/co-purchase session pairs used to train the embedding model (safe if session windows are bounded and don't span an unreasonably long period that starts conflating unrelated shopping trips). Item metadata (category, brand, price band) used as auxiliary features in a hybrid model (safe, static). A critical leakage risk specific to this design: if the embedding model is trained and evaluated using the same time period's co-occurrence data without a temporal holdout, offline retrieval-quality metrics will look better than the model's true generalization to *new* item pairs that hadn't co-occurred yet at training time, which is exactly the case (a newly-launched item) the system most needs to handle well.

**Model + serving** — The standard architecture is a **two-tower model** (one tower embeds the anchor item, a second tower embeds candidate items, trained so co-engaged pairs land close in the shared embedding space), with item embeddings precomputed offline and loaded into an ANN index (HNSW or similar) for sub-10ms nearest-neighbor lookup at request time. Because "similar" and "complementary" are different objectives, production systems at scale (Allegro's documented Similarity-TT approach is a direct example) train **separate two-tower models per carousel intent** rather than one model trying to serve both, accepting the cost of maintaining multiple embedding spaces and indexes in exchange for each one actually optimizing the objective it's shown against. New items get an embedding the moment their metadata and any early interaction signal is available, joining the index on the next scheduled rebuild (commonly hourly to daily) rather than instantly, which is the specific latency-vs-freshness tradeoff this design must state explicitly.

**Metrics** — Offline: recall@K and precision@K against held-out co-engagement pairs, using a **temporal holdout** (evaluate on pairs that co-occurred after the training cutoff) to avoid the leakage described above. Online: click-through rate on the similar-items carousel, and more importantly, incremental conversion attributable to the carousel (did showing it actually drive an additional purchase, not just redirect a purchase the user would have made anyway via search). They diverge because offline recall@K rewards recommending items that historically co-occurred with the anchor, which is necessarily biased toward well-established, frequently-co-viewed items, while the online carousel's actual commercial value is often highest when it successfully surfaces a *less obvious* complementary item the user wouldn't have found via search, a case offline co-occurrence metrics structurally underweight.

**The hard part** — Deciding, and building separately for, "similar" versus "complementary" rather than assuming one embedding space serves both, because the two objectives can point in opposite directions for the same anchor item, and a model that conflates them produces a carousel that satisfies neither intent well.

**Failure modes** — **Substitute/complement conflation**: symptom is a "frequently bought together" carousel surfacing near-identical substitute products (two similar phone cases) instead of genuinely complementary ones (a case plus a screen protector), traceable to training on a co-view signal (which favors substitutes, since shoppers compare similar items) rather than a co-purchase signal (which favors complements). **Cold start for new items**: symptom is a newly-listed item having no embedding-quality co-engagement signal yet, defaulting to a content-based (text/image) embedding fallback until enough interaction data accumulates, and this fallback must be flagged so it isn't silently mixed with interaction-based embeddings that carry a different notion of similarity. **Popularity concentration**: symptom is the same handful of best-selling items appearing in an implausibly large fraction of *other* items' similar-item lists, because they co-occur with almost everything by sheer volume, corrected by normalizing co-occurrence counts against each item's overall popularity (e.g., PMI-style weighting) rather than using raw co-occurrence frequency. **Stale index after catalog churn**: symptom is discontinued items still appearing in similar-item results for hours or days after removal from sale, if the ANN index rebuild cadence doesn't match the catalog's actual churn rate.

**Follow-ups they will ask** — (1) *"Why two separate models instead of one shared embedding space with different post-processing?"* Because the training objective itself differs (co-view vs. co-purchase supervision), and forcing one embedding space to satisfy both means every architecture and hyperparameter choice is a compromise between two different notions of "close," which in practice underperforms two purpose-built models even though it costs more to maintain two indexes. (2) *"How do you keep the index fresh without rebuilding it constantly?"* Incremental index updates (adding new item embeddings without a full rebuild) for additions, combined with a scheduled full rebuild on a slower cadence to reflect embedding-model updates and prune discontinued items, rather than treating "rebuild the whole index" as the only update mechanism. (3) *"A user complains the 'similar items' are all more expensive than the anchor. Bug or intended?"* Check whether price was included as a feature or constraint at all; if the embedding space is trained purely on co-engagement with no price-band awareness, it can legitimately surface a premium complement, so decide explicitly whether price-band filtering belongs as a hard constraint in retrieval or a soft re-ranking signal, rather than treating it as an accident to be patched reactively.

### 13. A/B testing platform

**Asked at:** A staff-plus infrastructure design prompt at any company with a mature experimentation culture (Meta, Netflix, Airbnb, Microsoft, LinkedIn) ([interviewing.io, FAANG system design mock: A/B experimentation platform](https://interviewing.io/mocks/faang-system-design-a-b-experimentation-platform), [DataInterview, A/B testing interview questions](https://www.datainterview.com/blog/ab-testing-interview-questions) — accessed 2026-08-01) · **Time:** 45 min

**Problem framing** — This is an infrastructure design, not a predictive-model design, and saying so explicitly at the start is itself the correct move: there is no trained model whose label needs defining. The nearest equivalent to "the label" is **the metric definition and the statistical test that decides significance**, and getting that wrong is the platform's version of the label-leakage failure that dominates every other design in this module: a poorly-specified guardrail metric, or a significance test run without correcting for the number of metrics and variants being checked, produces a confidently-wrong "ship it" decision exactly the way a leaked feature produces a confidently-wrong offline AUC.

**Requirements** — FR: assign users to variants consistently and stickily, serve the correct experience per assignment, collect exposure and outcome events, and compute statistical significance on demand or on a schedule. NFR: assignment must be deterministic and consistent for a given user across sessions and services (the same user must always land in the same variant); the platform must support many concurrent experiments without them contaminating each other's read on the same metrics; result computation must scale to companies running hundreds of concurrent experiments. Clarifying questions: (1) "Server-side assignment, client-side, or both?" — server-side is generally correct for anything affecting backend behavior or requiring tamper-resistance; client-side is common for UI-only experiments but is bypassable and less trustworthy for anything revenue-sensitive. (2) "Is this randomizing individual users, or does the experiment need cluster-level randomization (geographic markets, as in the dynamic-pricing design above)?" — determines the unit of randomization, which is not always "user." (3) "What's the false-discovery-rate tolerance across the whole experimentation program, not just per-experiment?" — a company running 500 concurrent experiments at a 5% per-test false-positive rate will see roughly 25 false "wins" ship in an average week if nothing corrects for multiple testing at the program level.

**Scale** — Assume 500 concurrent experiments across a platform with 200M DAU, each user potentially bucketed into several experiments simultaneously ⇒ the assignment service needs to resolve a consistent hash for every user on effectively every request touching an experimented surface, which at web-scale QPS (tens of thousands to hundreds of thousands of requests/sec) must be a stateless, deterministic hash computation (e.g., `hash(user_id + experiment_id) mod 100 < allocation_pct`), not a database lookup, because a lookup at that request volume would need its own massive caching layer just to reproduce what a hash function gives for free. Event volume for exposure and outcome logging at that DAU scale is on the order of billions of events/day, sized identically to a general analytics-pipeline ingestion problem.

**Features** — not applicable in the predictive-modeling sense; the analogous "leakage risk" concept here is in **metric computation**, not feature computation: computing an experiment's outcome metric using data from users who were exposed to the experiment surface but not actually assigned by this experiment's randomization (a common bug when multiple experiments target overlapping surfaces) inflates or deflates the read the same way a leaked feature inflates offline AUC, and it is caught the same way, by auditing that the population feeding the metric computation exactly matches the population the randomization actually assigned.

**Model + serving** — There is no ML model in the classic sense; the architecture is a **variant assignment service** (stateless, deterministic hashing, consulting an experiment-config store for allocation percentages and targeting rules), an **exposure/event logging pipeline** (streaming ingestion, typically Kafka-backed, writing to a columnar analytics store), and a **stats engine** computing significance, commonly using sequential testing methods (e.g., always-valid p-values, mSPRT-based approaches) rather than a single fixed-horizon t-test, because product teams routinely peek at results before the pre-registered sample size is reached, and naive repeated significance testing on the same accumulating data inflates the false-positive rate with every peek. A feature-flagging system is usually the same underlying assignment mechanism reused for non-experimental rollouts (staged deploys, kill switches), which is worth naming as a deliberate architectural overlap rather than two separate systems.

**Metrics** — There is no offline/online divergence in the usual ML sense here; the platform's own equivalent failure is the gap between a **statistically significant** result and a **practically meaningful** one: at large enough sample sizes, a platform running hundreds of millions of DAU can detect a statistically significant 0.02% change in a metric that has zero business relevance, so the platform needs a stated minimum-detectable-effect and practical-significance threshold built into how results are surfaced, not just a raw p-value. The platform must also track its own health metrics: sample-ratio mismatch (SRM) detection, which catches broken randomization by checking whether the observed variant split actually matches the configured allocation (a chi-squared test on assignment counts), is the single most important automated guardrail check the platform runs on every experiment, because an SRM invalidates every other metric the experiment reports.

**The hard part** — Building a system that makes it *hard* to accidentally p-hack: sequential testing correction, automated SRM detection, and program-level false-discovery-rate management are the parts that separate a real experimentation platform from a dashboard that computes a t-test, and none of them are visible in a naive architecture diagram of "assign variant, log event, compute stats."

**Failure modes** — **Sample ratio mismatch**: symptom is the observed variant split (e.g., 48/52 instead of a configured 50/50) diverging from the configured allocation by more than chance, almost always caused by a bug in the assignment or logging path (one variant's page loads slower and disproportionately loses users before an event fires) rather than randomization itself, and any experiment with a significant SRM must have its results discarded regardless of what the outcome metric shows. **Peeking-induced false positives**: symptom is a disproportionate number of experiments showing significance right around a round-number sample size or a Friday-before-a-launch-deadline, indicating fixed-horizon significance testing being checked repeatedly rather than a proper sequential method. **Interaction effects between concurrent experiments**: symptom is an experiment's result flipping sign depending on which other concurrent experiments a user happened to also be bucketed into, invisible unless the platform explicitly tracks and can slice by co-assignment. **Network-effect contamination**: symptom is a social or marketplace feature's measured effect looking artificially small or large because treatment and control users interact with each other (a treated user's friend, in the control group, is indirectly affected), the same spillover problem named in the dynamic-pricing design, requiring cluster-based randomization instead of individual-level assignment for any feature with cross-user interaction.

**Follow-ups they will ask** — (1) *"How do you prevent someone from just re-running the significance test every day until it turns green?"* Use a sequential testing method (always-valid inference) explicitly designed to control the false-positive rate under repeated looks, and surface a single "peek-safe" p-value in the UI rather than a fixed-horizon one that only means what it claims to mean if checked exactly once. (2) *"Two experiments both touch the checkout page. How do you stop them from contaminating each other?"* Either mutual exclusion (a user can only be in one of the two at a time, enforced by the assignment service's layering/namespace config) or explicit factorial design if both need to run simultaneously and their interaction is itself worth measuring; silently allowing overlap without deciding which is the default bug this question is testing for. (3) *"Why would a company-wide experimentation platform need a false-discovery-rate policy at all, if each individual test is at 95% confidence?"* Because running many independent tests at a 5% per-test false-positive rate guarantees a predictable number of false "wins" ship in aggregate (roughly 5% of all null-effect tests, which at 500 concurrent low-signal experiments is a real, recurring number of features shipped for no real reason), and a mature platform corrects for this at the program level, not just within each individual experiment's own p-value.

### 14. Feature store

**Asked at:** A recurring ML-infrastructure design prompt, with the core failure mode it exists to prevent documented directly in practitioner write-ups ([Chalk, What Is a Feature Store?](https://chalk.ai/blog/what-is-a-feature-store), [Why Feature Stores Didn't Fix Training-Serving Skew, dev.to](https://dev.to/synapcores/why-feature-stores-didnt-fix-training-serving-skew-fad), [System Design Space, Feature Store & Model Serving](https://system-design.space/en/chapter/feature-store-model-serving/) — accessed 2026-08-01) · **Time:** 40 min

**Problem framing** — Another infrastructure design, not a predictive model; the system's entire purpose is to make sure a feature's value is computed identically whether it's being read for training (a bulk historical join) or for serving (a single low-latency lookup). **The closest analogue to "the label"** here is the **point-in-time correctness contract**: for a given (entity, timestamp) pair, the store must return the feature value exactly as it would have existed at that timestamp, not the value as of today, and violating this contract silently reintroduces the future-leakage problem that every predictive design in this module names as its single most common bug, except now it's a platform-level bug affecting every model built on top of the store rather than one team's mistake.

**Requirements** — FR: register a feature definition once, compute it, and serve it correctly to both an offline training job (bulk, point-in-time joined) and an online inference path (single-entity, sub-10ms, latest value). NFR: online reads under ~10ms p99; offline joins over millions to billions of historical rows must complete within a batch job's time budget (hours, not real-time); feature freshness varies by feature (some update every few seconds from a stream, others nightly from a batch job), and the store must represent that heterogeneity rather than forcing everything onto one cadence. Clarifying questions: (1) "Which features are batch-computed and which are streaming, and does the store need to unify both under one registration API?" — determines whether this is fundamentally a dual-pipeline system from day one or a single-pipeline system extended later. (2) "Do consuming teams need to discover and reuse existing features, or is this store scoped to one model's pipeline?" — a shared, discoverable feature catalog is a materially bigger scope (naming conventions, ownership, deprecation policy) than a private feature cache for one team. (3) "What's the acceptable staleness for the online store per feature category?" — a user-demographic feature can be hours stale; a real-time fraud-velocity feature cannot be more than seconds stale, and one storage tier rarely serves both well.

**Scale** — Assume a platform with 50 registered feature groups shared across 20 models, entities numbering in the hundreds of millions (users, items), each with dozens of feature values ⇒ the online store alone is sized like a large key-value cache (hundreds of millions of keys × a few KB each, comfortably in the hundreds-of-GB to low-TB range, typically Redis or DynamoDB), while the offline store is sized like a data warehouse (historical feature values retained for months to years for reproducible training, easily reaching tens of TB to PB scale on cheap columnar storage like Parquet on S3). Online read QPS is driven by the sum of every consuming model's serving QPS, commonly tens of thousands to hundreds of thousands of requests/sec in aggregate across a large platform, each request needing a batched multi-feature lookup (a model rarely reads one feature; it reads a vector of 50-200 at once), which is why the online store's API is a batched multi-get, not a single-key get.

**Features** — not applicable in the predictive sense; the platform's version of "leakage risk" is architectural: a feature whose **transformation logic is implemented twice** (once in the batch/offline pipeline, once in the streaming/online pipeline, in different languages or frameworks, as is common when Spark computes offline features and a Python or Java service computes online ones) is the single most-cited real-world cause of training-serving skew, and a feature store that stores two independently-computed *values* for the same logical feature without unifying the *code* that produces them has not actually solved the problem it claims to solve, which is exactly the critique the dev.to source above makes explicit.

**Model + serving** — The standard architecture, following the Feast pattern, is two stores behind one logical feature-definition API: an **offline store** (a Hive-partitioned or Delta Lake table structure keyed by entity id and event timestamp, supporting point-in-time-correct joins for training set generation) and an **online store** (Redis or DynamoDB, keyed by entity id, holding only the current value per feature). A feature's transformation is registered once, ideally compiled to run identically in both a batch engine (Spark) and a streaming engine (Flink or a lightweight service) rather than hand-written twice, which is the harder, more valuable engineering investment that a feature store's marketing rarely emphasizes but that determines whether skew is actually prevented or just relabeled as "the online store" and "the offline store" disagreeing less visibly. Materialization jobs periodically push the latest computed values from the offline pipeline into the online store for features that don't need streaming freshness, while genuinely real-time features are written directly by a stream processor.

**Metrics** — The platform's health metrics replace "offline vs. online model metric divergence" with: **online-offline value parity** (sampling live online-store reads and comparing them against what an offline point-in-time query would have returned for the same entity/timestamp, which should match within a tight tolerance and any systematic gap is the skew bug made visible before a model ever trains on it), feature freshness lag (time between an event occurring and its feature value being queryable), and feature adoption/reuse rate across teams (a proxy for whether the "shared catalog" half of the value proposition is actually happening, versus every team still building private pipelines around the store).

**The hard part** — A feature store guarantees a feature's *value* is stored once; it does not automatically guarantee the *code* computing that value is shared between training and serving, and conflating "we have a feature store" with "we have solved training-serving skew" is the specific, commonly-made mistake this design question is testing whether you'll repeat.

**Failure modes** — **Skew from divergent transformation code, not divergent storage**: symptom is online-offline value parity checks failing for a specific feature despite both stores technically working correctly, traceable to the batch job's transformation logic (e.g., a null-handling default, a rounding rule) differing subtly from the streaming service's implementation of "the same" feature. **Point-in-time join violation in the offline store**: symptom is offline training-set generation silently joining a feature's *current* value against a historical label timestamp instead of the value as of that timestamp, producing the future-leakage bug at platform scale rather than one team's mistake, typically caught only when a model's offline metrics mysteriously outperform every online result. **Online store staleness for a feature registered as "streaming" but actually updated in batch**: symptom is a fraud-velocity-style feature silently serving hours-old values during a traffic spike because the "streaming" pipeline backpressures or falls behind, and the model consuming it has no way to know its input is stale unless freshness lag is monitored and alertable per feature, not just per pipeline. **Feature sprawl with no ownership**: symptom is dozens of near-duplicate features (`user_7d_ctr`, `user_ctr_7day`, `ctr_trailing_week`) registered by different teams because the catalog has no discoverability or deprecation process, defeating the reuse goal that justified building a shared store in the first place.

**Follow-ups they will ask** — (1) *"You have a feature store. Why would training-serving skew still happen?"* Because the store guarantees one place to *read* a feature's value, not one place the value is *computed*; if the batch pipeline and the streaming pipeline each implement the transformation independently, they can silently diverge, and the fix is sharing the actual transformation code (or compiling one definition to both runtimes), not just sharing storage. (2) *"How do you backfill a brand-new feature for historical training data?"* Run the feature's transformation against the historical event log for the full retention window, writing point-in-time-correct values into the offline store, which is often the most expensive and error-prone operation in the whole system because it requires the transformation logic to be correctly time-travel-safe against data that may have schema or semantics that changed over the backfill period. (3) *"A model's online performance drops right after a feature-store migration. How do you debug it?"* Start with an online-offline value parity check for every feature the model consumes, since a migration is exactly when transformation logic most commonly gets reimplemented and silently diverges, and this single check localizes the bug to a specific feature far faster than re-examining the model itself.

### 15. ML training platform

**Asked at:** An ML-infrastructure-track prompt, distinct from applied ML system design, documented as its own interview category by practitioners who've sat both sides of it ([Yuan Meng, Preparing for ML Infra System Design Interviews](https://www.yuan-meng.com/posts/ml_infra_interviews/), [Patrick Halina, ML Systems Design Interview Guide](http://patrickhalina.com/posts/ml-systems-design-interview-guide/) — accessed 2026-08-01) · **Time:** 45 min

**Problem framing** — Design the internal platform that other ML teams use to train, track, and promote models to production; this is infrastructure for building models, not a model itself. **The nearest equivalent to "the label"** is the platform's **definition of a reproducible, successful training run**: exact code version, exact data snapshot, exact hyperparameters, and exact environment must all be captured together, because a model that "worked" in an untracked, unreproducible run is functionally useless the moment someone needs to explain, audit, or retrain it, which is the platform-level version of every other design's insistence that the label must be a precisely defined, not assumed, quantity.

**Requirements** — FR: accept a training job specification, provision compute, execute it against a versioned dataset, track metrics and artifacts, register the resulting model, and support promoting a registered model to a serving environment. NFR: must support both small CPU jobs and large multi-GPU distributed training; must isolate one team's job from starving another team's job of shared GPU capacity; must make a training run fully reproducible months later for audit or debugging. Clarifying questions: (1) "Is this platform for a small number of large, long-running training jobs (foundation-model-style) or a large number of small, frequent retraining jobs (a fraud model retrained hourly)?" — these have almost opposite scheduling and resource-allocation needs. (2) "Does the platform own feature computation too, or does it consume from an existing feature store?" — scope boundary that determines whether this design overlaps with Design 14. (3) "What's the model promotion process — fully automated based on an eval gate, or does a human always sign off before a model reaches production?" — determines whether the platform needs a hard automated gate or just a structured review queue.

**Scale** — Assume a mid-size ML organization running 200 concurrent training jobs at peak across a shared GPU cluster of a few hundred to low-thousands of GPUs, with job queue wait time as the primary user-facing latency metric (not request QPS, since this is not a request-serving system) — a healthy platform target is jobs starting within minutes of submission for typical priority, with an explicit priority/preemption policy for urgent jobs, since GPU scarcity means naive FIFO scheduling starves smaller, faster-iterating teams behind one team's week-long job. Metadata volume (experiment tracking: metrics logged per step, per run) can reach millions of logged data points per large training run, sized like a time-series database workload layered on top of the compute-scheduling problem.

**Features** — not applicable in the predictive sense; the platform's equivalent concern is **experiment and artifact lineage**: every registered model must be traceable back to the exact code commit, data version, and hyperparameters that produced it, and a gap in that lineage (a model trained from a Jupyter notebook that was never checked in, or a dataset snapshot that was mutated in place after training) is the platform-level version of a leaked feature, an untraceable, unreproducible artifact silently entering production that nobody can debug or roll back with confidence later.

**Model + serving** — The standard shape: a **job orchestration layer** (Kubernetes-based, often with a scheduler like Kueue or a vendor equivalent handling GPU-aware bin-packing and preemption) accepting job specs referencing a container image, a data version, and a hyperparameter config; an **experiment tracking service** (MLflow-pattern: logging metrics, parameters, and artifacts per run, queryable and comparable across runs); a **model registry** (versioned models with stage transitions: staging, production, archived, each transition audited); and a **serving handoff** that packages a registered model for the inference-serving system (which may be one of this module's other designs' serving layers) without requiring a manual, error-prone artifact copy between teams. Distributed training support (data-parallel and, for the largest jobs, model-parallel) needs the orchestration layer to be aware of network topology (co-locating a distributed job's workers to minimize cross-rack communication), which is invisible in a naive "just schedule N containers" design and is exactly the kind of operational depth that separates a working prototype from a platform other teams trust with production models.

**Metrics** — The platform's own health metrics stand in for offline/online model metrics: **GPU utilization** (a low aggregate utilization despite a long job queue is the classic symptom of a scheduling or bin-packing problem, not a capacity problem, and the two require completely different fixes), **job queue wait time by priority tier**, **training-to-serving lead time** (how long from "model registered" to "model actually serving production traffic," which if too long defeats the purpose of fast iteration), and **reproducibility rate** (what fraction of registered models can actually be re-run from their recorded lineage and produce a matching result, which should be close to 100% and is worth auditing periodically rather than assuming). These diverge from what any individual model team cares about (their own model's accuracy) in the same way a data center's health metrics diverge from any single tenant's application metrics: the platform's job is enabling many other teams' correctness, not owning any one team's model quality itself.

**The hard part** — Building shared infrastructure that must serve wildly different workloads (a five-minute hyperparameter sweep job and a week-long distributed foundation-model run) fairly, on the same finite GPU pool, without either starving the small frequent jobs behind the big ones or fragmenting capacity so badly that the big jobs can never get a large enough contiguous allocation, which is a scheduling and resource-fairness problem more than an ML problem, and treating it as an ML problem is the trap.

**Failure modes** — **GPU fragmentation**: symptom is aggregate cluster utilization reported healthy (say 70%) while large distributed jobs still can't get scheduled, because the free capacity is scattered in small non-contiguous chunks across many nodes rather than in one allocatable block, invisible in a naive utilization dashboard that doesn't also track allocatable-contiguous-capacity. **Silent non-reproducibility**: symptom is a team unable to reproduce a six-month-old production model's exact behavior when investigating an incident, traced to an unpinned dependency version, a mutable data path that was overwritten since, or a hyperparameter that was tuned interactively outside the tracked job spec. **Priority inversion**: symptom is a low-priority but long-running job holding GPUs that a high-priority urgent retrain needs, if the scheduler supports priority levels but not actual preemption, meaning priority is advisory rather than enforced. **Silent metric-logging gaps mid-run**: symptom is a training run's tracked loss curve having unexplained gaps or resets, usually from a worker restart after a transient failure that wasn't checkpointed and resumed correctly, corrupting the ability to compare that run fairly against others in the experiment-tracking dashboard.

**Follow-ups they will ask** — (1) *"Aggregate GPU utilization is 70% but teams complain about long queue times. What's going on?"* Almost certainly fragmentation, not a raw capacity shortage: check allocatable-contiguous-capacity, not just aggregate busy-vs-idle, and consider whether the scheduler needs bin-packing awareness or whether workloads need to be split into smaller, more schedulable units. (2) *"How do you guarantee a model registered today can be exactly reproduced in six months?"* Pin everything the job spec references (container image digest, not a mutable tag; a specific data snapshot version, not "latest"; the exact commit hash, not a branch name) at submission time, and periodically audit a sample of registered models by actually attempting to re-run them from their recorded lineage, since an untested reproducibility guarantee is not a guarantee. (3) *"Should this platform also own feature computation, or consume from a separate feature store?"* Consume from a separate feature store if one exists (Design 14), because conflating training-job orchestration with feature computation couples two systems with very different scaling profiles and failure domains, the identical seam-boundary argument the recsys platform design makes for splitting services by scaling and failure characteristics rather than by convenience.

## Build it from scratch

The one piece of code every ML system design round can plausibly ask you to write live is **point-in-time-correct feature joining**, because it is the single mechanical operation that prevents the leakage named in thirteen of the fifteen designs above. A naive join uses the feature table's *current* state; a correct one uses an `as-of` join against the feature's value at the label's timestamp.

```python
import pandas as pd

def point_in_time_join(labels: pd.DataFrame, features: pd.DataFrame,
                        entity_col: str, label_ts_col: str,
                        feature_ts_col: str) -> pd.DataFrame:
    """
    labels:   one row per (entity, label_timestamp, label)
    features: one row per (entity, feature_timestamp, feature_value) --
              a full history of feature snapshots, NOT just the latest value.
    For each label row, attach the most recent feature value whose
    feature_timestamp is <= the label's timestamp. This is what prevents
    a feature computed "today" from leaking into a label from three months ago.
    """
    labels = labels.sort_values(label_ts_col)
    features = features.sort_values(feature_ts_col)
    # merge_asof requires both frames sorted on the join key and does
    # exactly the "most recent value not after this timestamp" semantics
    joined = pd.merge_asof(
        labels, features,
        left_on=label_ts_col, right_on=feature_ts_col,
        by=entity_col, direction="backward",   # feature must be <= label time
    )
    return joined

# untested sketch: production point-in-time joins operate over billions of
# rows and run on Spark (merge_asof has no direct Spark equivalent; the
# standard pattern is a window function: LAST_VALUE(feature_value) OVER
# (PARTITION BY entity_id ORDER BY feature_ts RANGE BETWEEN UNBOUNDED
# PRECEDING AND CURRENT ROW) joined against label_ts, with a feature_ts
# upper bound filter applied before the window to keep it from scanning
# the whole history per row.
```

The interviewer follow-up this invites: *"What happens if a feature's `feature_ts` column is wrong, say it's stamped with the write time instead of the event time?"* Then every join built on it silently leaks, because a feature written to the store five minutes after the event it describes will still appear "available" at the event's timestamp under a naive join. This is why event-time versus processing-time is a real distinction to name, not pedantry: it is the exact mechanism behind several of the "leakage risk" callouts above (author CTR, restaurant prep-time, account violation counts).

A second buildable piece, for the two-stage retrieval-then-ranking architecture common to designs 1, 4, 5, and 12, is the ANN retrieval step:

```python
# untested sketch: illustrates the shape, not a production ANN implementation.
# Real systems use FAISS, ScaNN, or a managed vector DB (see T06 for index internals).
import numpy as np

def brute_force_topk(query_vec: np.ndarray, item_vecs: np.ndarray, k: int) -> np.ndarray:
    """O(N*d) baseline that motivates why ANN indexes exist at all:
    at 50M items x 256 dims this is 50M * 256 ~= 1.3e10 multiply-adds
    PER QUERY, which at even 4,500 QPS (Design 12's peak) is nowhere
    close to feasible without an approximate index (HNSW/IVF)."""
    sims = item_vecs @ query_vec  # cosine sim if vectors are pre-normalized
    return np.argpartition(-sims, k)[:k]
```

Full index-internals mechanics (HNSW graph construction, IVF cell partitioning, quantization tradeoffs) live in `T06-vector-index-internals`; this module's job is knowing *when* the two-stage architecture is forced by the numbers, not re-deriving ANN from scratch.

## How it's done in production

| Design pattern | Framework/managed version | What it adds over the from-scratch version |
|---|---|---|
| Point-in-time feature joins | Feast, Tecton, Databricks Feature Store | Point-in-time correctness enforced by the platform API itself, not by every team remembering to use `merge_asof` correctly |
| Two-tower retrieval | TensorFlow Recommenders, FAISS/ScaNN serving | Production-grade ANN indexing, quantization, and incremental index updates |
| Multi-task ranking | MMoE / PLE architectures in TF or PyTorch | Shared representations across correlated labels (like/comment/share) without one task dominating gradient updates |
| Sequential significance testing | Statsig, Eppo, Optimizely, or an in-house always-valid-inference engine | Peeking-safe p-values and automated sample-ratio-mismatch detection out of the box |
| Experiment/model tracking | MLflow, Weights & Biases | Reproducibility (code + data + hyperparameter lineage) as a first-class, queryable artifact |
| GPU job scheduling | Kubernetes + Kueue, Slurm, Ray | GPU-aware bin-packing, preemption, and gang-scheduling for distributed jobs |
| Contextual bandits | Vowpal Wabbit, custom Thompson-sampling services | Off-policy evaluation and exploration-budget enforcement without hand-rolled regret bounds |

### What breaks in production, across all fifteen designs

| Symptom | Cause | Fix |
|---|---|---|
| Offline metric looks implausibly good (AUC > 0.95 on a hard problem) | Label or feature leakage, usually a non-point-in-time join | Audit every feature's timestamp semantics; re-run with a strict temporal split |
| Online metric flat or negative despite a strong offline win | Off-policy bias: offline eval only has labels for what the current policy already showed | Shadow-deploy and compare against a randomized holdout before trusting offline alone |
| A specific content/item category quietly disappears from results over weeks | Feedback loop: exposure data trains the next model, narrowing what gets shown | Track diversity/exposure-entropy as its own monitored metric, not just aggregate engagement |
| Model looks fine in a controlled test, degrades within days in production | Adversarial adaptation (fraud, spam) or a stale label proxy (churn, delayed chargebacks) | Shorten retrain cadence to match the attack/drift half-life, measured empirically |
| A feature-store migration silently drops model quality | Transformation logic reimplemented, not shared, between batch and streaming paths | Online-offline value-parity checks per feature, run continuously, not just at migration time |
| A/B test shows significance right when someone checks it repeatedly | Fixed-horizon significance test used under repeated peeking | Sequential (always-valid) testing methods |
| High aggregate GPU utilization, long training queues | Fragmentation, not a capacity shortage | Track allocatable-contiguous-capacity, not just busy/idle ratio |

## Tradeoffs & when NOT to use it

- **Do not reach for a deep multi-task ranker when a GBDT and a well-defined label would do.** Churn and ETA base-forecasting are both cases where GBDTs remain the durable, cheaper, more interpretable default; naming "I'd start with XGBoost and only reach for a deep model once I have evidence the tabular baseline has plateaued" is a stronger senior signal than opening with a neural architecture.
- **Do not build a two-stage retrieval-and-rank pipeline for a small catalog.** If there are a few thousand items or fewer, scoring all of them directly is cheaper to build, debug, and reason about than a retrieval stage that exists purely to solve a scale problem you don't have; the two-stage architecture in this module is derived from catalog-size and QPS arithmetic each time, not assumed.
- **Do not treat a feature store as solved training-serving skew.** As Design 14 makes explicit, a feature store guarantees shared storage, not shared transformation code; skew from divergently-implemented logic is a commonly reported failure even with a feature store deployed, and the fix is unifying the transformation, not adding more infrastructure around it.
- **Do not run a classification model where the business question is actually causal.** Churn is the clearest example: a model that ranks who is likely to leave is a different, easier problem than a model that identifies who an intervention will actually save, and shipping the former while the business acts as if it has the latter produces a retention program with no measurable lift.
- **Do not use fixed-horizon significance testing for a program running many concurrent experiments with variable check-in cadence.** It is cheap to build and wrong under repeated peeking, which is how experimentation platforms actually get used in practice, not how they're used in a statistics textbook.
- **Do not fully automate a decision whose cost of a false positive is high and asymmetric with a false negative** (blocking a legitimate transaction, banning a legitimate account, auto-removing borderline content). A human-in-the-loop review tier for the model's uncertain region is not a failure to fully automate; it is the correct architecture when the two error types have very different costs.
- **Do not skip the label-definition conversation to get to the architecture faster.** Every failure mode in this module traces back to a label or feature timing assumption nobody stated out loud; the 5 minutes spent forcing a precise label definition is the single highest-leverage move in the entire round, more valuable than any amount of architecture detail.

## Interview questions

### Q1 — Across any of these designs, what's the first question you ask before discussing the model?
**Testing:** whether label-first thinking is a habit or something you only did for the design you rehearsed.
**Answer:** How is the label actually produced, including its delay and its blind spots. "Fraud" is a chargeback filed 90 days later; "churn" is an arbitrary inactivity threshold someone chose; "relevant" is a blend of click, add-to-cart, and purchase discounted by position. Naming the concrete production mechanism behind the label, unprompted, before any architecture discussion, is the single highest-value thing you can do in the first five minutes.
**Follow-up trap:** *"Why does that matter more than the model architecture?"* Because a leaked or mis-defined label produces a model that is confidently wrong in a way no amount of architecture sophistication can fix; you cannot out-engineer a bad target.

### Q2 — Give me a feature that looks safe but is actually a leak, from any design.
**Testing:** whether "leakage" is a memorized vocabulary word or an operational check you actually run.
**Answer:** Author's all-time CTR computed via a nightly batch job not point-in-time joined against the training label's timestamp (feed ranking): a post from January gets scored using an author CTR that already includes engagement from March, because the join used "current" CTR rather than "CTR as of January." The tell is that it requires no obviously wrong code, just a join that isn't temporally aware, which is why it survives code review so often.
**Follow-up trap:** *"How would you catch this in an existing pipeline without re-deriving every feature by hand?"* Run an automated point-in-time value-parity check: for a sample of historical training rows, recompute each feature strictly as of that row's label timestamp and compare against what training actually used; any systematic mismatch is a leak, found without manually auditing every feature's code.

### Q3 — When would you use a two-stage retrieval-and-rank architecture, and when is it overkill?
**Testing:** whether the architecture is derived from numbers or recalled as a template.
**Answer:** Derive it from catalog size and request volume: if scoring every candidate item per request, at your actual QPS, fits comfortably inside the latency budget on the hardware you'd actually provision, a single-stage ranker is simpler to build and debug and you should use it. The two-stage split earns its complexity only when the arithmetic (as in Design 1's 75,000,000 scores/sec figure) makes single-stage scoring infeasible.
**Follow-up trap:** *"Your catalog just grew 100x overnight after an acquisition. What changes?"* Recompute the arithmetic, don't assume the old architecture still fits; a 100x catalog growth can push a single-stage design past the point where it needs retrieval, or push an existing two-stage design's retrieval-candidate-pool size past what the ranking stage's latency budget can absorb, forcing a second look at the retrieval cutoff parameter, not just "add more servers."

### Q4 — How do you decide the right offline metric when the online metric is what actually matters?
**Testing:** whether you understand offline metrics as a proxy, not a target.
**Answer:** Pick the offline metric that most directly correlates with the actual online decision the model drives, and validate that correlation empirically rather than assuming it: NDCG for a ranking that will be read top-to-bottom, calibration error for a score that feeds an auction or a threshold, PR-AUC rather than ROC-AUC under extreme class imbalance. Then treat every offline metric as provisional until an online experiment confirms the direction of effect, because offline evaluation structurally cannot see effects like habituation, adversarial adaptation, or feedback loops that only appear over days or weeks of live traffic.
**Follow-up trap:** *"Your offline metric improved but the A/B test showed no effect. Ship it or not?"* Not automatically either way: investigate whether the offline metric's improvement is concentrated in a slice the online test wasn't powered to detect (a rare but high-value segment), or whether the offline metric was measuring something the online population doesn't actually experience the same way (off-policy bias); "the numbers disagree" is a finding to explain, not a tiebreak to resolve by picking your preferred number.

### Q5 — Design the labeling strategy for a problem where ground truth takes 90 days to arrive.
**Testing:** whether you can operate a model in the gap between "we shipped it" and "we know if it worked."
**Answer:** Use a nearer-term proxy label for fast iteration (an analyst-review flag or an early-signal event that correlates with but precedes the final label), train and deploy against the proxy, and separately run a periodic backtest against the fully-resolved 90-day label to measure how much the proxy and the true label actually disagree. Treat the proxy-to-true-label gap itself as a tracked metric, since if it widens, the proxy has stopped being trustworthy and iteration needs to slow down until you understand why.
**Follow-up trap:** *"What if the proxy label systematically misses a whole category the true label would catch?"* That's the real risk with any proxy, and it is exactly why the periodic backtest against the true label exists: a proxy built from analyst review, for instance, will systematically miss sophisticated fraud analysts have never learned to recognize, so backtesting isn't a formality, it's the only way to discover that blind spot before an attacker exploits it at scale.

### Q6 — A model's precision and recall both look fine offline, but a specific user segment is disproportionately affected by false positives. How do you catch this?
**Testing:** whether you evaluate aggregate metrics only or also check for concentrated harm.
**Answer:** Slice every offline and online metric by relevant segments (language, region, account age, content category) rather than trusting the aggregate number, because a uniformly-low aggregate false-positive rate is fully compatible with one segment experiencing a much higher, business-critical rate, as named explicitly in the spam/abuse and content-moderation designs above. This requires deciding which segments matter *before* shipping, not discovering the disparity from a support-ticket spike afterward.
**Follow-up trap:** *"Slicing by every possible segment sounds like it doesn't scale. How do you choose which ones?"* Prioritize segments with known historical sensitivity (protected classes, low-resource languages, new users, small-business accounts) and any segment where the underlying feature distribution differs meaningfully from the training population's, since that's exactly where a model trained on the majority distribution is most likely to generalize poorly.

### Q7 — How do you A/B test a change when the treatment for one user can affect the outcome for another (a marketplace or social feature)?
**Testing:** whether standard user-level randomization is understood as a default with real limits, not a universal tool.
**Answer:** Individual-level randomization breaks under network effects and marketplace spillover (the dynamic-pricing and A/B-platform designs both name this): a treated rider's unfilled request changes supply available to a control rider in the same market. The fix is cluster-based randomization, geographic markets, social-graph communities, or time-based switchback designs, so the unit of randomization matches the unit where the spillover actually happens.
**Follow-up trap:** *"Switchback experiments (alternating the whole market between treatment and control over time) have their own problem. What is it?"* Carryover effects: users and the system itself retain state from the previous period (a driver who repositioned based on yesterday's surge pattern, a cached price from the prior window), so periods need to be long enough and often need a buffer/burn-in window discarded between switches, or the comparison is contaminated by the immediately preceding condition.

### Q8 — Design the retraining cadence policy across these fifteen systems. Are they all the same?
**Testing:** whether retrain cadence is understood as a derived decision, not a fixed operational default.
**Answer:** No, and the driver differs by design: ads CTR retrains near-continuously because inventory turns over hourly; spam/abuse needs a cadence tied to the empirically-measured half-life of an attack pattern, which can be days; churn retrains weekly to monthly because behavioral drift is slow and the label horizon is long; a feature store's transformation code should almost never need to "retrain" at all, since the risk there is code divergence, not model staleness. The generalizable rule: cadence should be set by how fast the label's underlying reality changes relative to how fast you can detect that it changed, not by a calendar default inherited from a different system.
**Follow-up trap:** *"Your monitoring shows no metric degradation. Do you still need to retrain?"* Possibly yes, for an adversarial system specifically: the absence of a visible metric drop can mean the attacker hasn't yet found the current model's blind spot, not that no blind spot exists, which is why spam/fraud designs pair scheduled retraining with proactive adversarial testing rather than relying purely on reactive, drift-triggered retraining.

### Q9 — What's the single most common reason an ML system design candidate loses points at the staff level specifically, versus the senior level?
**Testing:** calibration of what separates the levels in this specific round.
**Answer:** Staying inside one model's boundary when the real answer requires naming the system-level consequence: a senior answer designs a good churn classifier; a staff answer notices the business is asking a causal question (who will an intervention save) and reframes the deliverable, or notices that eight independently-scaled services is a real ongoing operational cost and says so unprompted rather than defending the architecture as obviously correct.
**Follow-up trap:** *"Isn't reframing the question risky if the interviewer wanted the literal answer?"* State both: answer the literal question first so you don't look like you're dodging it, then explicitly flag the reframe as an additional consideration ("and separately, worth noting: this is really an uplift problem, here's why that changes what 'success' means"), so the interviewer sees the depth without ever feeling like their actual question went unanswered.

### Q10 — How would you explain, to a non-ML stakeholder, why an online experiment is necessary when the offline numbers already look great?
**Testing:** communication of a technical distinction to a business audience, a principal-level skill this module's designs repeatedly require.
**Answer:** Offline numbers measure whether the model got better at predicting what already happened; the business question is whether *doing something different* because of the model makes things better going forward, and those are genuinely different questions, the same way a great weather forecast doesn't itself prevent rain, it only tells you when to bring an umbrella, and you still need to check whether people actually did.
**Follow-up trap:** *"The stakeholder says the A/B test is just slowing down shipping a model we already know is better. How do you respond?"* Name a concrete case where offline-looked-great and online-did-nothing happened (feedback loops in recommendations, off-policy bias in any ranking system) as a plain-language cautionary example rather than a statistics lecture, and frame the test's cost as insurance against shipping something that quietly does nothing, or worse, actively degrades a metric nobody was watching closely enough to catch until the postmortem.

### Q11 — Two of your fifteen designs (dynamic pricing, feed ranking) both have feedback loops. Are they the same failure mode?
**Testing:** whether you can distinguish superficially similar failure modes by mechanism, not just by name.
**Answer:** No: feed ranking's feedback loop is a *training-data* loop (the model's own exposure decisions shape what data the next model trains on, narrowing diversity over time), while dynamic pricing's feedback loop is a *market* loop (the price itself changes driver behavior within minutes, which changes the input the next price computation sees), operating on a completely different timescale and requiring a completely different fix, exposure-diversity monitoring for one, price-update damping/smoothing for the other.
**Follow-up trap:** *"Could the same technical fix, damping or smoothing, work for both?"* Not directly: feed ranking's fix is structural (change what data enters training, via exploration), while pricing's fix is about rate-of-change of the *decision* itself, not the training data; applying pricing's damping approach to feed ranking would slow down how fast rankings change without addressing that the training data itself is still biased toward what was previously shown.

### Q12 — If you could only build one guardrail across all fifteen systems before anything else, what would it be?
**Testing:** prioritization under the constraint that you cannot build everything, a staff-level discriminator this module shares with `T10-design-method`.
**Answer:** An automated point-in-time-correctness check on every feature used in training, because leakage is the single most common, most silent, and most expensive-to-discover-late failure across every predictive design in this module (11 of the 15), and it is the one failure category where the offline metric actively lies to you rather than merely diverging from the online one, meaning you don't even get the warning sign a metric gap would normally provide.
**Follow-up trap:** *"That doesn't help the three infrastructure designs (A/B platform, feature store, ML training platform). What's their equivalent?"* Sample-ratio-mismatch detection for the experimentation platform, online-offline value-parity checks for the feature store, and reproducibility auditing for the training platform, three different mechanisms, but the same underlying principle: build the automated check that catches a silent, structural correctness violation before a human would ever think to look for it.

## Red flags that fail you

- Naming a model architecture before anyone has defined the label.
- Treating "click" as a self-evidently correct label for anything (feed, ads, search) without naming why raw click optimizes for the wrong thing.
- Proposing a two-stage retrieval-and-rank pipeline without doing the arithmetic that would force it.
- Reporting an offline AUC/accuracy number with no mention of how the train/test split was constructed (random vs. temporal).
- Treating ROC-AUC as sufficient under known extreme class imbalance (fraud, spam) instead of PR-AUC.
- Saying "we'd retrain the model" as a generic fix for any failure mode without naming what changed that retraining would fix.
- Describing a feature store and implying it alone prevents training-serving skew.
- Proposing individual-level A/B randomization for a feature with an obvious network or marketplace spillover effect.
- Never mentioning calibration for any system whose score feeds a threshold, auction, or dollar amount.
- Defending an architectural decision (eight services, a specific model family) as obviously correct with no stated cost.
- Confusing "the model is accurate" with "the intervention it drives works" (the churn/uplift distinction).

## Cheat card

```
UNIVERSAL 9-SLOT TEMPLATE (in order, each feeds the next)
  1 label + delay/proxy   2 requirements + 3 clarifying Qs   3 scale (numbers shown)
  4 features + leakage    5 model+serving (derived)          6 offline vs online metric GAP
  7 the hard part         8 failure mode + OBSERVABLE symptom  9 3 follow-ups

TWO-STAGE FORCING FUNCTION   catalog_size x QPS too big for single-pass scoring
  → retrieval (ANN/rules, cheap, high recall) → ranking (heavy model, high precision)
  seen in: feed, ads, recsys, search, similar-item retrieval

LABEL TRAPS (the recurring interview trap)
  fraud    = chargeback filed within ~90 days, NOT "is fraud"
  churn    = an arbitrary inactivity threshold, NOT an observed fact
  "relevant" = click+cart+purchase blend discounted by position, NOT one signal
  feed "engagement" = weighted composite (like/comment/share/hide), NOT raw click

LEAKAGE CHECKLIST
  is the feature's timestamp POINT-IN-TIME joined, or "current value"?
  does a feature encode a signal that only exists BECAUSE the label happened?
  is train/test split TEMPORAL, not random, wherever time matters?
  is an upstream model's score trained on overlapping data (stacking leak)?

OFFLINE vs ONLINE DIVERGE BECAUSE
  off-policy bias (only shown items have labels) · feedback loops (exposure
  shapes future training data) · slow effects (habituation, adversarial
  adaptation) offline evaluation windows can't see

FAILURE MODE VOCAB, WITH THE SYMPTOM THAT NAMES IT
  feedback loop      -> diversity/entropy metric declines while engagement flat
  position bias      -> model overweights position-1, inverts on re-rank
  cold start         -> new item/user permanently scores near population mean
  training/serving skew -> offline metric healthy, online flat/negative
  adversarial drift   -> a flag-rate drop right after ship, then a new pattern

METRICS BY CLASS-BALANCE
  extreme imbalance (fraud, spam, click)  -> PR-AUC + calibration, not ROC-AUC
  ranking (feed/search/ads)               -> NDCG@K, MRR + online guardrails
  regression (ETA, pricing)               -> quantile loss / CRPS, not just MAE
  infra (A/B, feature store, training)    -> health metrics: SRM, value-parity,
                                              GPU-contiguous-capacity, not model metrics

3 INFRA DESIGNS HAVE NO MODEL. Say so out loud, then map:
  A/B platform     "label" -> metric definition + significance test
  feature store    "label" -> point-in-time correctness contract
  training platform "label" -> reproducible-run definition (code+data+hparams pinned)
```
