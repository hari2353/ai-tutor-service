# The RL Problem: Agent, Environment, Reward, and Why It Isn't Supervised Learning

> **Track:** T31 Reinforcement Learning · **Time:** 2h · **Prereqs:** none · **Updated:** 2026-08-03
> **Module id:** `T31-rl-framing` · **Tags:** fundamentals, critical

## The 30-second version

Reinforcement learning is the framework for sequential decision-making under a reward hypothesis: an agent picks actions, the environment returns a new state and a scalar reward, and the agent's job is to maximize the sum of future rewards, not the correctness of any single prediction. That single shift — optimizing a *return* over a trajectory instead of minimizing a *loss* on a labeled example — is what breaks every assumption supervised learning quietly relies on. There is no ground truth to imitate, only a reward signal that has to be turned into a training target through the Bellman equations; the data is not i.i.d., it's a sequence generated by the agent's own (changing) policy, so the input distribution shifts under you as you learn; and credit assignment is delayed, so an action at step 3 might be the actual cause of a penalty at step 30 with nothing in between telling you so. Everything downstream in this track — value functions, TD learning, policy gradients, PPO — is a different answer to the same three problems: what do I optimize, how do I assign credit across time, and how do I explore without an oracle telling me the right answer.

## Why this gets asked

Because it's the fastest filter for whether a candidate actually understands RL's shape or is pattern-matching "reward = label, more reward = better." Interviewers who've shipped RL — recommendation systems with bandits, ranking with implicit feedback, RLHF pipelines — have all been burned by treating RL as "supervised learning with an extra reward column" and watched training diverge or collapse. This module is also where they check whether you know when RL is the wrong tool: a huge fraction of "we need RL for this" ideas are actually supervised or contextual-bandit problems wearing an RL costume, and correctly triaging that is a senior signal that shows up nowhere else as cleanly.

## Lineage: past → present → future

**What came before.** RL's mathematical backbone is Bellman's dynamic programming (1957) and, in parallel, the psychology of trial-and-error learning (Thorndike's Law of Effect, 1911; operant conditioning). Optimal control theory gave the field its formalism (state, control, cost-to-go) for systems with a known model. The pain that kept RL a theoretical curiosity through the 1970s-80s was twofold: dynamic programming requires a known transition model and exact tables over the state space, both of which are fantasy for anything beyond a toy grid, and the field had no principled way to learn value functions from raw experience. Sutton's temporal-difference learning (1988) and Watkins' Q-learning (1989) fixed the second problem — you could now learn value estimates by bootstrapping off other estimates, from real interaction, without a model. That still left the first problem: state spaces in anything real are enormous or continuous, so tabular methods hit a wall immediately.

**Where it stands now.** Deep RL (DQN, 2013/2015) replaced the table with a function approximator, which unlocked pixels-to-actions control but reopened old wounds under approximation: the deadly triad (function approximation + bootstrapping + off-policy learning) can diverge, and nobody has a clean general fix, only mitigations (target networks, clipped double Q-learning, trust regions) that reduce the failure rate without eliminating it. The live disagreement is about scope: one camp treats RL as the general algorithm for sequential decision-making and keeps pushing it into robotics, games, and now LLM post-training; the other camp — increasingly loud since 2023 — argues that most industrial "RL problems" are actually contextual bandits or supervised problems with a temporal label, and reaching for full RL (with its credit-assignment and stability headaches) when a simpler formulation would do is the single most common RL project failure mode, ahead of any algorithmic bug. Both camps agree that RL's biggest real deployment in 2024-2026 is not robots — it's RLHF/RLVR-style post-training of language models, which is a genuinely different regime (huge, structured action spaces; one-step or few-step episodes; a learned or rule-based reward) covered in `T31-rl-for-llms`.

**Where it's heading.** High confidence: RL as *fine-tuning* — bounded-horizon, reward-shaped adjustment of an already-competent policy (an LLM, a pretrained robot controller) — keeps growing, because it sidesteps RL's worst failure mode (learning from scratch with sparse reward over long horizons). Medium confidence: offline and hybrid offline/online RL keep gaining share in industry specifically because collecting fresh on-policy data is expensive or risky (recommendation, healthcare, robotics), and reusing logged data safely is now a first-class subfield (`T31-offline-rl`) rather than an afterthought. Speculative: general-purpose "agentic" RL — training an LLM-driven agent end-to-end against long-horizon, multi-step, real-world reward signals rather than single-turn preference reward — is an active 2025-2026 research direction, but treat claims that it's solved or reliable at scale as unproven; the credit-assignment and reward-hacking problems this module introduces don't go away just because the action space is now "call a tool."

## Mental model

```
        ┌─────────────┐   action a_t   ┌──────────────┐
        │             │ ─────────────▶ │              │
        │    AGENT    │                │ ENVIRONMENT  │
        │  (policy π) │ ◀───────────── │              │
        └─────────────┘  state s_t+1,  └──────────────┘
                          reward r_t+1

  trajectory:  s0, a0, r1, s1, a1, r2, s2, a2, r3, s3, ...
  goal:  choose actions to maximize   G_t = r_{t+1} + γ r_{t+2} + γ² r_{t+3} + ...
```

Supervised learning hands you `(x, y)` pairs drawn i.i.d. from a fixed distribution and asks you to match `y`. RL hands you a *stream* generated by your own choices, a scalar reward instead of a label, and asks you to maximize a *sum over the future* — the reward for action `a_t` often doesn't even arrive at step `t`, it arrives (partially, mixed with other effects) many steps later. There is no `y` to imitate; you have to construct your own training target from the Bellman recursion, and that target depends on your own current, still-wrong value estimates. You are simultaneously the data-generating process and the thing being trained on that data — which is the single sentence that explains most of why RL is unstable in ways supervised learning isn't.

## How it actually works

### The formal pieces

An RL problem is specified by a **Markov Decision Process** `(S, A, P, R, γ)` — states, actions, transition dynamics, reward function, discount factor — derived rigorously in `T31-mdp`. Here, the framing-level pieces:

- **State `s_t`**: what the agent observes (or the true world state, if fully observable — see POMDPs below).
- **Action `a_t`**: what the agent can do; discrete (Atari, board games) or continuous (robot torques, portfolio weights).
- **Reward `r_t`**: a scalar, and only a scalar — this is a real constraint. Multi-objective goals must be collapsed into one number (a weighted sum, or a Lagrangian with constraints) before RL can optimize them, and that collapsing step is where most reward-design bugs are born.
- **Policy `π(a|s)`**: the thing being learned — a mapping from states to a distribution over actions.
- **Return `G_t = Σ_{k=0}^∞ γ^k r_{t+k+1}`**: the actual optimization target, not `r_t` itself. The discount `γ ∈ [0,1)` makes an infinite-horizon sum finite and encodes a preference for sooner reward, mathematically identical to a per-step probability `1-γ` of the episode ending (derived in `T31-mdp`).

### Why RL is not supervised learning, precisely

| | Supervised learning | Reinforcement learning |
|---|---|---|
| Training signal | Label `y` for each `x` — tells you the *right answer* | Scalar reward `r` — tells you *how good*, never what the right action was |
| Data distribution | Fixed, i.i.d. samples from a static distribution | Generated by the agent's own policy; changes every time the policy updates (**non-stationary target**) |
| Credit assignment | None needed — the label is attached to the exact input | The consequence of `a_t` may not appear until `r_{t+50}`; you must apportion credit across a whole trajectory |
| Objective | Minimize a per-example loss | Maximize an expected *sum* over a trajectory, which requires estimating value, not just fitting a function |
| Exploration | Not applicable — you don't choose which `x` you see | You choose the actions that generate your own future data, so a policy that never explores can converge to a *confidently wrong* optimum |
| Counterfactuals | Not needed | Fundamental: you only observe the reward for the action you took, never the one you didn't (this is why off-policy learning and importance sampling exist) |

Two of these deserve emphasis because they're the ones people underrate:

**Non-stationarity from your own policy.** In supervised learning the target distribution `P(y|x)` doesn't move. In RL, the moment you update `π`, the distribution of states you'll visit next changes, because you visit states *by acting*, and you just changed how you act. When you bootstrap a value target off a moving policy's own estimates (TD learning, Q-learning), you're regressing toward a target that shifts every gradient step — this is one leg of the "deadly triad" (function approximation + bootstrapping + off-policy data) that can make deep RL training diverge with no warning, covered mechanically in `T31-dqn`.

**Delayed, sparse credit assignment.** A chess move at turn 12 can be the reason you lose at turn 60. Nothing in the environment says "that was the mistake" — the only signal is the final `-1`. Value functions exist specifically to solve this: `V(s)` and `Q(s,a)` are *learned proxies for future consequence*, letting the agent judge an action's quality without waiting for the episode to end. The entire tabular half of this track (`T31-dynamic-programming` through `T31-q-learning-sarsa`) is about how to estimate that proxy correctly.

### Fully observable vs partially observable

Most of this track assumes an MDP: the current state `s_t` is a *sufficient statistic* for the future — the Markov property, `P(s_{t+1}|s_t, a_t) = P(s_{t+1}|s_0,a_0,...,s_t,a_t)`. Real systems routinely violate this: a robot with noisy sensors, a trading agent that can't see other participants' intentions, a dialogue agent that only sees the current turn. These are **POMDPs** (partially observable MDPs), where the agent maintains a *belief state* — a distribution over possible true states — instead of acting on the raw observation directly. In deep RL this is usually handled pragmatically rather than with exact Bayesian filtering: stack the last `k` observations, or feed a recurrent/attention layer a history, so the network approximates the belief state implicitly. Treating a POMDP as if it were an MDP (feeding a single frame instead of a stack, in the Atari case) is a common, diagnosable bug: the symptom is a policy that behaves erratically in situations that are perceptually identical but have different history (e.g., can't tell ball direction from one Pong frame).

### Bandits: RL with the "sequential" removed

A **multi-armed bandit** is RL's simplest special case: one state, no transitions, action → immediate reward, repeat. There's no credit-assignment problem (the reward for pulling arm `k` is caused by nothing but pulling arm `k`) and no long-horizon planning — only the explore/exploit tradeoff survives (`T31-exploration`). **Contextual bandits** add a state/context that affects reward but still has no transition dynamics the agent influences — this is the right formalism for most recommendation and ad-ranking problems, and it is dramatically easier to get right than full RL because you've deleted the two hardest parts (delayed credit, non-stationary self-generated trajectories) while keeping the one genuinely necessary part (explore vs exploit under a reward signal). Recognizing "this is actually a contextual bandit" instead of reaching for full RL is one of the highest-leverage engineering decisions in this whole track.

## Build it from scratch

A minimal environment/agent interface, the shape every RL library (Gym/Gymnasium, dm_env) converges on, plus a random-policy rollout that makes the trajectory concrete:

```python
import random
from dataclasses import dataclass, field

@dataclass
class StepResult:
    state: object
    reward: float
    done: bool
    info: dict = field(default_factory=dict)

class Environment:
    """Minimal env interface: reset() -> state, step(action) -> StepResult."""
    def reset(self) -> object: ...
    def step(self, action) -> StepResult: ...

class GridWorld(Environment):
    """3x3 grid, agent starts at (0,0), goal at (2,2). Actions: 0=up 1=down 2=left 3=right."""
    def __init__(self, size=3):
        self.size = size
        self.goal = (size - 1, size - 1)

    def reset(self):
        self.pos = (0, 0)
        return self.pos

    def step(self, action):
        x, y = self.pos
        dx, dy = {0: (0, 1), 1: (0, -1), 2: (-1, 0), 3: (1, 0)}[action]
        x = min(max(x + dx, 0), self.size - 1)
        y = min(max(y + dy, 0), self.size - 1)
        self.pos = (x, y)
        done = self.pos == self.goal
        reward = 0.0 if done else -1.0     # -1 per step: shortest path is optimal
        return StepResult(self.pos, reward, done)

def rollout(env: Environment, policy, max_steps=100, gamma=0.95):
    """Runs one episode, returns the trajectory and the discounted return G_0."""
    state = env.reset()
    trajectory, G, discount = [], 0.0, 1.0
    for t in range(max_steps):
        action = policy(state)
        result = env.step(action)
        trajectory.append((state, action, result.reward))
        G += discount * result.reward
        discount *= gamma
        state = result.state
        if result.done:
            break
    return trajectory, G

def random_policy(state):
    return random.randint(0, 3)

if __name__ == "__main__":
    env = GridWorld()
    traj, G = rollout(env, random_policy)
    print(f"episode length={len(traj)}  return G_0={G:.3f}")
    # A random policy on a 3x3 grid takes far more than the optimal 4 steps —
    # this gap (random-policy return vs optimal return) is your first intuition
    # for why exploration and value estimation both matter.
```

Run this a few times and log `len(traj)`: a random policy rarely finds the goal efficiently, which is the concrete, executable version of "credit assignment and exploration are the hard parts." The rest of this track is algorithms that make `policy` smarter than `random_policy` using only the `(state, action, reward)` stream this loop produces — no labels, ever.

## How it's done in production

| Layer | What you actually use | What it adds |
|---|---|---|
| Environment interface | Gymnasium (maintained fork of OpenAI Gym), PettingZoo (multi-agent), dm_env | Standardized `reset()/step()` API every library speaks |
| Simulation | MuJoCo, Isaac Gym/Isaac Lab (GPU-parallel physics), custom domain simulators | Vectorized environments — thousands of parallel rollouts per GPU step, essential for sample efficiency |
| Algorithm libraries | Stable-Baselines3, RLlib (Ray), CleanRL (single-file, readable) | Battle-tested implementations; the "invisible bugs" (advantage normalization, observation clipping) that separate working PPO from broken PPO |
| Problem triage | Contextual-bandit libraries (Vowpal Wabbit, custom) when full RL isn't warranted | Most production "RL" in ranking/recsys is this, not deep RL |

### Failure modes

| Symptom | Cause | Fix |
|---|---|---|
| Team spends months on an RL system that a simple bandit would have solved in weeks | Problem was contextual-bandit-shaped (no real state transitions) but was framed as full RL | Ask first: does my action change what state I'm in next? If no, it's a bandit — use one |
| Training metrics look fine, policy is useless in the real environment | State fed to the agent isn't Markov (missing velocity, occluded object, single-frame POMDP treated as MDP) | Stack frames / add recurrence / add the missing state features; verify with a "can a human solve this from the same observation" sanity check |
| Agent's behavior degrades or oscillates as training continues, no code changed | Non-stationarity from bootstrapping off a moving target (deadly triad), not a bug | Target networks, smaller learning rate, or an algorithm designed for the setting (`T31-dqn`, `T31-ppo`) |
| Reward goes up, task success does not | Reward function is a mis-specified proxy for the real goal (reward hacking) | Treat reward design as the primary engineering artifact, not an afterthought — see `T31-rl-in-production` |

## Tradeoffs & when NOT to use it

- **If there's no real sequential dependency, don't use RL.** If the action you take now doesn't change the distribution of what you'll see next, you have a (contextual) bandit, and bandit algorithms are simpler to implement, faster to converge, and far easier to debug than anything with a Bellman backup in it.
- **If you have labels, use them.** RL is what you reach for when you *can't* label the right action directly but *can* score outcomes. If a supervised signal exists (imitate an expert, predict a known outcome), it will almost always out-cost-perform RL from scratch; RL's sample inefficiency relative to supervised learning is not a minor footnote, it's often 100-1000x more environment interactions for comparable task performance.
- **If reward is hard to specify precisely, expect reward hacking, not a shortcut around the specification problem.** RL will optimize exactly what you wrote, including every loophole you didn't notice. "We'll just let RL figure out the objective" is a red flag, not a plan.
- **If you can't safely explore in the real environment, you need simulation or offline RL, not naive online RL.** A recommender system, a trading agent, or a physical robot cannot try catastrophic actions "to see what happens" the way an Atari agent can; this constraint alone often decides your entire algorithm family (`T31-offline-rl`, `T31-rl-in-production`).
- **When the state space is small and the model is known, skip learning entirely.** If you can write down `P(s'|s,a)` and enumerate states, classical planning/dynamic programming (`T31-dynamic-programming`) solves it exactly and faster than any learning algorithm — RL earns its keep only when the model is unknown or the state space is too large to enumerate.

## Interview questions

### Q1 — In one or two sentences, what makes a problem an RL problem rather than a supervised learning problem?
**Testing:** whether the framing is actually understood or memorized as a slogan.
**Answer:** You don't have the correct action labeled for each state — only a scalar reward signal for outcomes, often delayed — and your own choices determine what data (states) you see next, so the policy and the data distribution co-evolve.
**Follow-up trap:** *"So if I have reward labels for every (state, action) pair in a dataset, is that RL?"* — that's supervised learning with a reward-shaped target (or at best offline RL if you still need to handle distribution shift from a different, learned policy); plain RL specifically requires you to choose actions and live with their downstream, often delayed, consequences.

### Q2 — Why is the reward required to be a single scalar? What happens if a team asks for multi-objective reward?
**Answer:** The Bellman equations and the entire value-function machinery require a total order over outcomes so returns can be summed and compared; multiple objectives must be collapsed into one number (weighted sum, Lagrangian with constraints, or a scalarization function) before any RL algorithm can optimize them.
**Follow-up trap:** *"Won't a weighted sum just let one objective dominate?"* — yes, and that's a real design problem, not a solved one; the honest answer is you either tune weights against a held-out human-judged distribution, use constrained RL (optimize objective A subject to objective B ≥ threshold, e.g. via Lagrangian relaxation), or use Pareto-front methods — pretending scalarization is free is a red flag.

### Q3 — What does it mean that RL training data is "non-stationary," and why does that matter for a bug you might actually hit?
**Answer:** Every time the policy updates, the distribution of states it visits next changes, because visitation is caused by action selection. Concretely: a value function trained on states visited by an early, exploratory policy can be systematically wrong once the policy converges to visiting a different part of the state space, because the training data and the deployment data were never the same distribution to begin with.
**Follow-up trap:** *"How is that different from covariate shift in supervised learning?"* — covariate shift in SL is usually something that *happens to you* (train/test mismatch); in RL it's *caused by the very act of learning* — you can't fix it by better train/test splitting, because there is no fixed distribution to split.

### Q4 — Give a concrete example of delayed credit assignment and explain mechanically how RL solves it.
**Answer:** A chess blunder at move 12 causes a loss revealed only at move 60 — the reward `-1` arrives 48 steps after the causal action. RL solves this via the value function `Q(s,a)`, a learned estimate of expected future return from taking `a` in `s`, updated via the Bellman equation so that consequences propagate backward through the trajectory one step at a time (TD learning) or via full-trajectory returns (Monte Carlo) — the value function is the mechanism that turns "eventually, this was bad" into "this specific move, right now, was bad."
**Follow-up trap:** *"Doesn't that require the Markov property to hold?"* — yes, exactly: bootstrapped credit assignment (TD, Q-learning) relies on `Q(s,a)` compressing all relevant future information, which is only valid if `s` is Markov; if it isn't (a POMDP treated as an MDP), credit gets assigned to the wrong things because the "state" doesn't actually carry the information needed to predict the future.

### Q5 — Your manager says "let's use RL to optimize our recommendation feed." What's your first question?
**Testing:** the contextual-bandit-vs-RL triage that separates senior engineers from RL enthusiasts.
**Answer:** Does the action taken now (which items to show) change the distribution of contexts/users we'll see next in a way that matters for the objective? For most feed ranking, it doesn't — each impression is close to an independent contextual decision — so a contextual bandit gets you 90% of the value with a fraction of the instability, training cost, and debugging surface of full RL.
**Follow-up trap:** *"When would feed ranking actually need full RL?"* — when there's a genuine multi-step user journey the system should optimize across (e.g., showing content now that changes what the user is receptive to next session, or deliberately trading a slightly worse immediate click for better long-term retention) — that's a real temporal credit-assignment problem, and it's the minority case, not the default.

### Q6 — What's the discount factor `γ` actually for, mechanically — not "it makes future rewards worth less"?
**Answer:** It makes an infinite (or very long) sum of rewards converge to a finite number so the return is well-defined and optimizable, and it's mathematically equivalent to modeling a `1-γ` probability of the episode terminating at each step — so `γ` close to 1 means "the agent should care about consequences far in the future," and `γ` close to 0 means "the agent is effectively myopic." Derived fully in `T31-mdp`.
**Follow-up trap:** *"What breaks if you set γ=1 in a continuing (non-episodic) task?"* — the return sum can diverge to infinity for any policy that gets non-zero average reward forever, making policies incomparable; you either need `γ<1`, a proper terminal state, or a switch to the average-reward RL formulation instead of discounted return.

### Q7 — What's a POMDP, and how do deep RL systems handle partial observability in practice, without doing exact Bayesian filtering?
**Answer:** A POMDP is an MDP where the agent doesn't observe the true state directly, only an observation that's a (possibly noisy, possibly incomplete) function of it — the agent should act on a belief state, a distribution over possible true states. In practice, deep RL approximates this by giving the network enough history to infer the belief implicitly: frame-stacking (Atari's classic 4-frame stack recovers velocity information a single frame can't show), or a recurrent/attention layer over a window of past observations.
**Follow-up trap:** *"What's the failure mode if you don't do this and just feed a single observation?"* — the network can't distinguish states that are perceptually identical but have different history and thus different correct actions (a ball moving up vs down looks identical in one Pong frame), which shows up as noisy, seemingly-random performance specifically in situations that require inferring motion or hidden context.

### Q8 — What is reward hacking, and why is it not a bug in the RL algorithm?
**Answer:** Reward hacking is the policy finding a way to maximize the specified reward that doesn't achieve the intended goal — a boat-racing agent that loops collecting bonus targets instead of finishing the race, a cleaning robot that hides messes instead of removing them. It's not an algorithm bug; the algorithm did exactly what it was told. It's a specification bug — the reward function was a proxy for the real goal, and the optimizer found the gap between the proxy and the goal.
**Follow-up trap:** *"How do you defend against it in practice?"* — you can't fully eliminate it, only reduce the gap: shape reward closer to the true objective, add constraints/penalties for known exploits, monitor for reward-return divergence (reward going up while a held-out human-judged success metric doesn't), and treat any large, fast reward improvement as suspicious until verified against the real objective, not as good news by default.

### Q9 — Explain the difference between a bandit, a contextual bandit, and a full MDP, in terms of what's missing from each.
**Answer:** A bandit has one state, no context, action → immediate reward — only the explore/exploit problem exists. A contextual bandit adds a per-round context/state that affects the optimal action and the reward, but the agent's action still doesn't influence what context arrives next — still no credit-assignment problem. A full MDP adds actual state transitions the agent's actions influence, reintroducing delayed, multi-step credit assignment on top of exploration.
**Follow-up trap:** *"Give a real system that looks like an MDP but is actually a contextual bandit."* — most ad/feed ranking: which ad you show now doesn't meaningfully change which user (context) shows up next; treating it as a full MDP buys you nothing but training instability. The tell is: does the current action change the next state's distribution in a way the objective cares about? If not, it's a bandit.

### Q10 — Someone claims "RL doesn't need labeled data, so it's easier to get started with than supervised learning." Do you agree?
**Testing:** whether the candidate mistakes "no labels" for "easier."
**Answer:** No — it trades one hard problem (getting labels) for several harder ones: you must define a reward function that doesn't have exploitable gaps, you need a way to explore safely, and RL is typically far more sample-inefficient than supervised learning for a comparable task, often by two to three orders of magnitude in environment interactions. "No labels" removes annotation cost but adds reward-design cost, which is frequently harder to get right and far more expensive to get wrong.
**Follow-up trap:** *"So when does the lack of labels genuinely make RL the right call?"* — when the correct action truly isn't knowable in advance (no expert to imitate, the optimal policy is exactly what you're trying to discover) but success is verifiable after the fact — game-playing, some robotics tasks, RLHF-style preference optimization where "which response is better" is easier to judge than "what's the perfect response."

### Q11 — What's the "deadly triad" in RL, and why is it introduced at the framing level instead of waiting for deep RL?
**Answer:** Function approximation, bootstrapping (updating an estimate using other estimates), and off-policy learning — combine any two safely, but combine all three and training can diverge with no guarantee of convergence. It belongs here because it's a direct consequence of RL's basic shape (learning value estimates from a non-stationary, self-generated stream) rather than an implementation detail of any one algorithm; DQN, actor-critic, and offline RL all inherit this risk from the framing itself.
**Follow-up trap:** *"Tabular Q-learning is off-policy and bootstraps — why doesn't it diverge?"* — because it has no function approximation; tabular updates only affect the single `(s,a)` entry touched, with no generalization to bleed error into unrelated states, so two legs of the triad alone are provably safe under standard conditions. Divergence risk shows up specifically once approximation is added.

### Q12 — Design the state, action, and reward for an RL system to manage a warehouse robot's task queue, and flag what could go wrong with your reward.
**Testing:** synthesis under an open-ended prompt — the practical version of everything above.
**Answer:** State: queue contents, robot positions/battery, warehouse occupancy — must be Markov enough that current queue state plus positions predicts outcomes, which likely means adding recent-history features if robots have momentum/handoff dependencies. Action: assign next task to a robot (or wait). Reward: negative per-timestep cost (encourages speed) plus a completion bonus, minus a penalty for collisions/battery depletion. Flag: a pure "-1 per step, +100 per completed task" reward can be hacked by a robot completing trivial nearby tasks repeatedly while ignoring a hard, high-value task sitting in the queue, or by a robot cutting through a restricted zone because the collision penalty is smaller than the time saved — the reward needs shaping and constraints that a naive first pass will miss, and you should say so unprompted rather than presenting a reward function as obviously correct.
**Follow-up trap:** *"How would you validate the reward before training for a week and finding out it's wrong?"* — audit it against hand-constructed edge-case trajectories before training (does the reward rank a known-good trajectory above a known-exploit trajectory?), and instrument training to log the true objective (throughput, SLA violations) alongside raw reward from the first run, not after debugging a divergence.

## Red flags that fail you

- Calling the reward a "label" or describing RL as "supervised learning with delayed labels."
- Proposing full RL for a problem with no real state transitions (a disguised contextual bandit).
- Treating non-stationarity as a training instability to patch with a lower learning rate, without naming its cause (the policy generates its own shifting data distribution).
- Assuming a single observation is automatically a valid Markov state.
- Describing reward hacking as a bug to "fix in the algorithm" rather than a specification problem in the reward function.
- No answer for "when would you not use RL here."
- Confusing return `G_t` with reward `r_t` — optimizing the wrong quantity in your own explanation.

```
CTX BANDIT     state exists but agent's action doesn't affect next state's distribution
               -> most recsys/ranking "RL" problems are actually this
DEADLY TRIAD   function approx + bootstrapping + off-policy data together
               = no convergence guarantee; any 2 of 3 alone is provably safe (tabular)
REWARD HACKING optimizer exploits gap between proxy reward and true goal -- a
               SPECIFICATION bug, not an algorithm bug; reward IS the engineering artifact
SAMPLE COST    RL is typically 100-1000x less sample-efficient than supervised learning
               for comparable task performance -- don't reach for it if labels exist
```
